# 实现质量门

依次完成以下三个维度的审查，每个维度形成独立结论后再进入下一个。

逐条核对已确认需求，判断 diff 是否为每一项已确认需求提供了对应的实现路径。缺
失整条功能路径、确认范围内的场景无对应代码、规格要求的错误情况无处理，均为需
求覆盖发现项。只检查实现路径是否存在，不重跑测试，不评价测试设计；只报告已确
认需求的缺口，不推断未明确的需求。

除需求覆盖外，审查改动触及的实现是否与需求的应有设计语义有偏差：不仅核对本 diff
是否为需求提供了实现路径，还判断被改动代码是否偏离其应有的设计语义（含既有设计）。
实现路径存在但语义被静默改变、绕过既有归属者或流程、把应并行的职责合并或把应分离
的职责混入，均为实现-需求偏差发现项。

审查改动引入的模块边界、职责归属、依赖方向、公开面、状态与缓存生命周期、失败
语义、性能形态和耦合。检查每项职责是否只有一个明确归属者、依赖是否指向预期方
向、状态是否由正确的归属者创建与退役，以及错误是否保持了文档化行为。排查同一
能力被多个模块重复维护、内部细节外泄、跨模块的隐式协调、互不兼容的生命周期假
设，以及让新旧两条架构路径同时生效的改动。

审查改动中的正确性、文档化的边界情况、可维护性、局部性能、测试质量、死代码、
过拟合、编码处理和校验完整性。性能方面，只报告可观察、有证据、与改动直接相关的
性能退化（复杂度上升、热路径分配/拷贝、无界循环/逐行查询、N+1、资源泄漏、缓存
失效）；假设性担忧仅作 P2 建议，不阻塞 PASS。测试应在直接拥有该行为的最低层验
证，只有当更高
层引入了不同的正常使用行为时，才需要在更高层重复覆盖。排查隐藏的分支、被合并
的职责、含义模糊的命名、被塞在一起的逻辑、无益地删除注释或错误处理、过期的兼
容路径，以及在原生 VCS 比较中缺失的已改动文件。优先选择小范围的局部修复或删
除，而不是引入新机制。

三个维度独立报告，互不压制。不重做方案层面的复杂度或可行性审查。
