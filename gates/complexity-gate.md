# 复杂度门

判断已实现的方案是否是对已确认需求"足够且最简"的回应。改动应只覆盖已确认需求；需求之外的内容属本门范围内的问题，无论它与需求无关，还是有关但引入不必要复杂、可以更简化的设计。任何新的抽象、文件、
类型、字段、状态、阶段、包装层、配置、脚本、报告、证据层或流程，都必须在现
有仓库以及可用的内置或原生能力中找不到归属者才能成立。判定"足够且最简"时，对改动
引入的每个新概念按以下顺序逐项核查，任一项成立即属过度设计：

先检查本次交付的完整实现 diff，逐项核对是否修改了已确认需求之外的功能或代码，
包括新增、修改和删除。以已确认需求、当前任务及明确授权为依据；技术审已有的范围
结论可作核对材料，未做技术审也不能省略检查，不以预先指定的文件名单代替功能范围判断。
对每项需求外改动，必须核实它与当前需求的具体关系、是否属于完成需求不可缺少的配套，
以及不做该改动会导致什么具体失败。涉及其他文件不自动等于越界；“顺手优化”、统一风格、
更现代、以后可能有用或开发者声称必要，都不能代替必要性证据。

未经用户允许擅自修改其他功能，且不属于已授权需求的必要配套，必须判为 P1 并返回 FAIL；
造成需求无法成立、核心验收无可用路径或交付被阻塞时判 P0。不得因原功能仍能运行、
改动看似有益或可撤回而降为 P2/P3。逐项给出需求/授权依据、具体 diff 位置、被改变的功能
及必要性核实结果；需要扩大范围时交由 engine 进入既有用户处置流程，不在本门补写授权。
完成范围检查后，继续以下复杂度判断。

1. 需求之外的内容 —— 不在确认范围内。
2. 仓库已有可复用的归属者 —— 应复用或改造既有者，不新建。
3. 标准库或运行环境自带能力已可表达 —— 应使用，不自造。
4. 已安装依赖已可表达 —— 应使用，不新增。
5. 存在更清晰且复杂度较低的等价实现 —— 可提出具体简化建议，不以行数最少为目标。
   审查者须给出具体替代写法，核实其在已确认范围内的行为、副作用、错误处理与必要验证
   均等价。仅删换行、压缩排版或省略必要行为不算简化。不要为寻找更短写法单独扩大检查；
   完成范围内实质复杂度核对后结束，纯等价收缩只作 P3。

逐一排除后才承认其必要；发现可用替代方案时报告具体依据，不因开发者未写排除说明
就推定存在缺陷。过度设计发现按共享契约的实际影响定级：纯等价表达收缩为 P3 建议，
有范围内实质后果时按证据定级；仅 P0/P1 导致 FAIL。被削减的验证、错误处理或安全行为
是需求覆盖问题，不归本门。

实现复杂度的判据是：代码量和改动文件数是否与需求相称、新概念与公开/配置面是
否必要、既有代码能否复用或删除，以及是否残留重复、过期、未使用或可收缩的逻
辑。为不存在的场景、假设性风险或过度防御而预留的代码、参数与配置，以及本可用更简单、更清晰的方式表达却写得更复杂的改动，均属本门范围内的问题。当重构或清理确实移除了真实的重复或复杂度时，更大的 diff 是合理的。

本门不接收也不得索取 QA 用例正文或逐用例执行证据。对看似无调用者的公开接口，建议删除
或形成 finding 前先核对附近的 `acceptance-surface` REQ/AC 引用及其已确认验收职责；注释
只是职责线索，不自动证明接口必要，也不要求普通内部接口增加模板注释。

方案层面的结论优先于实现细节：不要在"被否决的方案本应存在"这一假设上继续审
查实现细节。把更简单且足够的替代方案，与该多余设计带来的全部范围内后果，合
并成一个方案层面的发现项报告。
