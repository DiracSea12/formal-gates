CASE-001
mode: blackbox
description: REQ-001／AC-001、AC-002，REQ-008／AC-016：共同说明只保留一份，逐例审查识别错误 oracle，修改仅撤销实际受影响的审批；黑盒设计与审查的公开输入和实际工作区均保持基线隔离。
procedure: 在不可变候选的隔离安装中，按候选发布的操作文档创建最小 Git run，保存原生基线 B，并通过 qa-worktree 入口登记隔离工作区。通过 prepare-action 分别准备并实际派发 blackbox qa-design 和 qa-review，按正常顺序完成设计登记与审查。设计包含两条引用同一准备说明的用例、另一条使用不同说明的独立用例和完整覆盖映射；其中一个 oracle 明确违反样例已确认需求。两类派发均保存完整公开输入、声明的 worktree 路径及代理实际工作区身份：在实际工作区执行原生 Git 根路径、HEAD、工作树差异和未跟踪文件清单检查，与 B 对照；结合公开输入清单核验当前需求注入及开发材料隔离，不读取生产实现。保存共同说明记录和逐例审查结论。修正错误 oracle 后再次审查；随后分别修改单条用例、修改共享准备说明，每步检查待审集合并完成受影响部分审查。此用例是同一 run 中的有序场景，不能把后一步作为独立初始状态。
oracle: 共同说明存在唯一内容及稳定引用；错误 oracle 被定位到具体用例，其余用例有明确审查或合法继承结论。单条修改使该条及实际受影响部分失效，共同说明修改使所有引用者失效，不相关审批保留；完整双向覆盖映射始终可核对。黑盒设计和审查的实际工作区均对应已登记隔离路径，原生 HEAD 等于 B，生产树保持基线；两类派发输入均包含当前确认需求，输入及工作区均不含本次生产代码、白盒测试或开发者解释。不得仅凭提示词声明工作区或仅核对审查派发通过隔离验收。任一错误用例获批、受影响用例漏审、无依据扩大重审集合或任一派发隔离不成立均为失败。
review status: PASS

CASE-002
mode: blackbox
description: REQ-002／AC-003、AC-004：同一派发内批量实际执行复用候选准备，隔离独立用例状态，并在失败后仅停止依赖步骤。
procedure: 使用候选公开的批量执行或 fixture 入口，对固定用例组执行一次批次：一个正常独立用例、一个会改变工作状态的独立用例、一个从相同初始状态读取结果的独立用例，以及一个先决操作必然以文档规定方式失败的有序依赖组。每个独立用例从干净副本起步。记录构建、共同准备及副本创建次数，并逐例保存真实命令、标准输出、标准错误、退出状态和执行顺序。将失败组置于独立读取用例之前，以验证继续执行。
oracle: 同一候选只构建一次，可复用准备没有逐例重做；状态修改不污染其他独立用例。真实失败有失败输出，其依赖操作未执行且状态如实保留，后续独立用例仍有真实结果。批次没有新增逐例代理、TaskKey 或逻辑任务额度。构建、安装或宿主派发若本身列为本例验收目标，必须另有本轮实际执行证据，不能以缓存准备记录代替。
review status: PASS

CASE-003
mode: blackbox
description: REQ-003／AC-005、AC-006：高成本前置状态可以构造，但目标入口必须实跑；最小执行脚本能发现已知错误且未变版本可以复用。
procedure: 选用交付中一项文档化的高成本前置 fixture，通过支持的工具构造前置条件，保存构造命令、内容清单以及目标操作尚未完成的可观察状态。用新增或修改的短执行脚本真实调用被测公开入口、采集输出并断言。再从干净副本给脚本提供一项与其关键 oracle 对应的已知错误样例，真实运行并观察失败；若交付包含缺陷回归脚本，用能呈现原错误的固定样例核验。最后用相同脚本版本执行第二个适用副本，检查审批复用记录。
oracle: 证据清晰区分前置构造和目标调用，目标结果来自本轮真实命令；没有预置成功结果并当作实跑。已知错误样例使脚本报告失败且不会被结果登记吞掉；适用的回归脚本可发现原错误。脚本版本未变时无需重新完成整轮设计审批，结果仍保留逐次实际调用证据。
review status: PASS

CASE-004
mode: blackbox
description: REQ-004／AC-007：同次执行中断后保存完整 PASS／FAIL，半途条目保持未完成，续跑只补缺项并保留原 FAIL。
procedure: 在干净 run 中通过文档化逐例执行与结果登记入口依次完成一个真实 PASS、一个真实 FAIL，启动第三条后在其输出或判据尚未完整时正常中断，第四条不启动。保存中断时的公开状态、证据和执行计数。保持候选、用例、工具和环境绑定不变，使用同一派发的支持续跑入口继续；按入口给出的未完成集合执行第三、第四条并登记。不得手改正式 state 或把半途输出补写成已完成证据。
oracle: 中断状态显示原因及未完成集合；前两条真实结果及证据均保存，第三、第四条不能继承为 PASS，整轮不能提前 PASS。续跑只补未完成条目，不重做完整且绑定有效的前两条；原 FAIL 仍保留，最终不会因续跑而被抹去。
review status: PASS

CASE-005
mode: blackbox

procedure: 从同一已完成部分条目的干净 fixture 建立四个独立场景，分别通过支持的正常操作改变候选提交、单条用例版本、执行工具版本、文档明确参与绑定的相关环境。每个场景保留一个适用的不受影响对照条目；若候选或工具变化按公开契约影响全部条目，则如实按全体影响测试。调用公开续跑入口，保存变更前后绑定、复用或失效原因、待执行集合及实际重跑命令。不得直接修改状态文件制造版本变化。
oracle: 每个变化维度均被识别；受影响旧结果不能直接作为新绑定下的通过证据，必须重跑。公开契约允许且绑定有效的不受影响结果能够复用，失效和继承原因可核对；不存在仅凭内容相似就无条件继承或没有依据的全量重跑。
review status: PASS

oracle: A 的有效测试被显式绑定并由 QA 本轮独立运行，无测试改动时不强制新增文件或推进快照。B 的错误断言与缺失分支被识别并修正或补测，不能仅因已有测试全绿而放行；变更测试已提交并进入最终快照，用例引用与实际运行测试对应。

CASE-009
mode: blackbox
description: REQ-006／AC-012：缺少验收覆盖、步骤不可执行和错误 oracle 分别阻止相应批准或冻结，建议处置不能绕过；采纳导致行为变化时必须重审受影响用例。
procedure: 从相同固定已确认需求建立三个独立干净 QA 场景，三者必须分别执行：A 有一个明确验收点没有对应的实际验证用例；B 覆盖声明完整，但一条用例遗漏必需前置操作，导致按其步骤无法完成目标；C 覆盖和步骤完整，但一条 oracle 明确违反需求。每个场景仅保留对应缺陷，其余用例有效。分别通过公开入口登记用例、进行真实独立 qa-review，并在缺陷仍存在时通过公开的可选建议处置路径尝试推进批准或冻结；保存每种缺陷、逐例及集合审查结论、建议处置响应、批准／冻结响应和最终状态，不能任选其中一种代替另两种。B 使用稳定的步骤缺陷，不使用临时环境故障或基线尚无新增入口作为不可执行依据。另从已批准用例集出发采纳一条会修改共同操作路径或验收含义的建议，使用正常编辑入口落实，再查看实际待审集合并重审。复用候选公开的门审及产品／技术审正常场景，核对相同建议处置入口是否仍遵守各自原有规则；只在这些层引入的不同使用行为上执行，不重复纯字段校验。
oracle: A 的缺漏验收点被明确识别，集合不能获得完整覆盖通过或冻结；B 的不可执行用例不能获批，集合不能冻结；C 的错误 oracle 用例不能获批，集合不能冻结。三个拒绝条件分别有本轮实际证据，任何可选建议处置均不能解除仍存在的缺陷；定级遵守项目范围和严重度规则，不因条目 FAIL 自动升级 P1。采纳造成路径或验收含义变化后，全部实际受影响用例重新审查，不相关有效审批保留。门审 P2 必修、门审 P3 建议以及产品／技术审用户处置规则未被 QA 专用变更替换。
review status: PASS

CASE-010
mode: blackbox
description: REQ-007／AC-013、AC-014：最终提交整理先于最后必需验证，Seal 固化同一候选；验证后候选变化不能直接继承完整通过。
procedure: 在独立 Git fixture 中通过正常开发及白盒补测产生多条提交和测试变更，使用候选已文档化的最终候选准备入口完成必要整理，再完成路线和 requirement guarantee 要求的最后必需验证，记录 candidate identity。调用 Seal 并比较前后身份、验证绑定及既有产物路径。另从未 Seal 的已完成最后验证副本正常提交一个影响验收的修改，调用公开推进入口，观察 AFFECTED 判定、所需重验和最终 FULL 约束，完成规定重验后再 Seal。各分支均使用真实 Git 操作和产品入口，不手改 state。
oracle: 多提交整理及白盒测试纳入候选均发生在最后必需验证之前；该验证与 Seal 指向同一 identity，Seal 不再 squash 或因自身改变候选追加全量执行。验证后改变候选不能直接承认旧证据为新候选完整通过；AFFECTED 与最终 FULL 按既有规则执行。黑盒用例等 Seal 产物正常生成，已验证候选身份保持不变。

CASE-013
mode: blackbox
description: REQ-009／AC-017、AC-018：优化前后使用同一 Codex 模型实际完成设计、审查和执行，必需模型耗时与 token 有真实来源，重复工作减少且缺陷发现能力和覆盖不减少。
procedure: 在同一 Codex 模型及配置、固定任务和验收点、可比环境下，分别对已标明源码身份的优化前版本和最终候选实际运行设计、审查、执行三个阶段。复用既有共同说明审查、批量准备、中断续跑及已知缺陷场景，保持正常场景、常见错误和缺陷清单一致；旧版缺少新增入口时，使用其已支持的等价完整流程，并记录对应关系。两个版本的三个阶段均实际调用 Codex 宿主，保存调用身份、阶段及派发绑定、命令、结果、起止时间和原始用量来源，通过交付的现有 cost 路径取得输入、缓存输入、非缓存输入、输出 token。逐阶段对账，记录墙钟计时边界及是否包含工具等待，另记录派发、构建、准备和中断后重复执行次数。来源或必需指标缺失时保留未完成状态，修复采集或补跑后再完成对比，不以模拟 lifecycle 或 CLI 写入耗时替代模型任务数据。
oracle: 两版的设计、审查、执行共六个阶段均有真实 Codex 调用及可对账的模型任务墙钟耗时和四类 token；输入缓存分类遵守实际计数口径，零值只有在原始计数确为零时有效。必需指标没有 unavailable、估算或冒充缺失的零值，报告数字能追溯到现有 cost 投影及宿主来源。可核对的重复审查、重复准备和可避免重跑减少，不要求固定倍率；相同已知缺陷仍被发现，用例与验收覆盖不减少，未完成执行不能 PASS。
