# 任务拆分与保留总任务实例

是否拆分由主代理建议、用户确认。拆分建议对所有正式 run 必填呈现并留痕；仅高置信
要拆时需用户确认拆分方案，其余情形（高置信不拆或不确定）记录"建议不拆（原因）"即
可、不要求确认。双速：高置信不拆走快速路径（黑盒 QA 设计可与 start-readiness 并
行开始），拆分可能串行（先确认方案再设置分片）。拆分建议含：拆分理由、如何拆、哪
些子任务可并行、以及改拆后果说明。确认前可调整（改切片边界、并行范围、各切片路
线），确认后即为二元、不重切；确需调整走既有需求变更流程。

## 拆分判据

同时避免两个方向的错误：

- **过细**：子任务小至不值得单独执行一遍完整流程。
- **过粗**：一个子任务包含多个本可独立实现、独立验收的逻辑单元，或工作量超出单次
  完整流程可验证的范围。

介于两者之间，按独立验证、依赖顺序、拆分收益三点判断切分边界：各逻辑单元是否能独
立实现与验收、子任务间的依赖顺序是否清晰、拆分带来的并行与隔离收益是否大于额外流
程开销。大而连贯的请求保持单一 run 是正常做法。

## 流程

在任何子任务开发之前，用 `workflow start` 传入 `--retained-overall`，在完整请求的
原始基线上启动并保留一个总任务实例，带上完整需求和完整需求方案。Part 2（start-
readiness）完成后记录拆分决定（`workflow slicing`）；拆分决定为 split（分片 >= 2）
时，保留总任务实例自动附加合并门与合并 QA 作为其合并后验证，只跑这两者，不涉常规
路线选择。

每个子任务各自启动一个子任务实例，并使用单独的原生 VCS 工作树。子任务实例继承主
任务 run 的拆分决定记录，开发 worker 门经继承满足，不再单独确认拆分。路线在拆分决
定后逐切片确认：主代理给出统一默认路线推荐，用户只对需要差异化的切片单独调整。容
量允许时并发运行相互独立的子任务（并行确认是提示词/流程层保证，CLI 只记录并行建
议），并在依赖边上等待。

合并已 Seal 的子任务分支并解决冲突之后，用 `workflow snapshot` 把合并后的标识记录
为保留总任务实例中已完成的开发。合并 QA 的跨切片交互用例在各分片开发期间并行设计/
审，合并后执行于合并快照；合并门审查合并引入的变更（冲突解决、集成修复、跨切片接
缝）、组合产生的跨切片架构回归，以及合并整体相对完整需求的比例/复杂度。审查者有权
查看各分片 worktree 的变更与主线总变更（base→merged）。分片 worktree 在合并门审
查完成前保留。切片与合并验证覆盖 Git/SVN/P4——隔离映射为对应 VCS 的工作副本/客户
端工作区，合并映射为对应 VCS 的合并/集成。

不要创建第二个总任务实例、不要替换它的基线、不要为总任务准备或派发开发子代理，也
不要在合并之后重复澄清或路线选择。集成阶段的发现项回到各自所属的子任务实例。那些
子任务修复被 Seal 并合并之后，在保留总任务实例中，直接用 `workflow snapshot` 记录
新的合并标识。
