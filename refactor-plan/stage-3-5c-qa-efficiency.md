## 1. 要解决什么

保留独立 QA，把时间主要花在判断功能和测试是否正确，减少重复读材料、搭环境和逐条操作。
黑盒优先处理，白盒在同一计划内优化。

本地 `review-convergence-3-5b` 的已关联派发记录显示：黑盒执行累计约 7 小时 29 分，
黑盒设计约 3 小时 57 分，黑盒设计审查约 1 小时 55 分；白盒设计、审查、执行合计约
1 小时 32 分。黑盒两次长执行分别完成 22/63、59/63 条，最终都未完整结束。

这些是代理轮次耗时相加，包含工具和等待，不是整个流程的经过时间；该 run 最终存在
用户授权跳过，不能当作全量 QA 通过样本。“完整执行”也不等于 PASS。
数据用于确定先改哪里，不用于承诺提速倍数。

审计来源：项目 `.gates/results/review-convergence-3-5b.json` 与关联宿主会话；
详细计算留在本机
`/private/tmp/formal-gates-qa-cost-audit-20260906/最近封板流程耗时与Token分析.md`。
临时分析文件不是新的权威账本。

## 2. 黑盒审查：每条都判断，共同步骤只查一次

例如，20 条用例都要先创建项目、启动流程，最后传入的参数不同。创建项目和启动流程的
共同做法统一审一次；20 条用例各自的特殊前提、关键操作和预期结果仍然逐条判断。

具体改法：

- 用例可以引用同一份共同准备步骤和操作说明，不必在每条中复制全文；特殊条件写在该条用例里。
- 审查者先检查共同部分，再检查每条用例的差异、可执行性和验收标准，仍交付逐条结论。
- 已有的未变用例审批继承继续保留。返修后审改动及受影响部分；共同步骤变化时，相关用例必须重新检查。
- source、验收点、用例的覆盖映射继续完整对账。不能用“这一组大概没问题”替代逐条判断，不能靠抽样宣告整组通过。
- 黑盒设计与审查继续在基线隔离环境进行，不读取本次生产代码、白盒测试或开发者解释。
  开发前新增入口按已确认的公开契约审查，不因旧基线没有该入口就判不可行。

本项改变的是重复阅读和路径核查方式，不减少应覆盖的需求。设计和审查也要共用这份
共同说明，避免为了减少审查开销，反而增加设计文档的维护量。

## 3. 黑盒执行：批量实跑，减少重复准备

同一待测版本构建一次，共同环境准备一次，各用例从干净副本开始，批量运行真实命令，
分别保留输出和结果。AI 负责组织执行、分析失败及处理需要判断的情况。

- 优先复用现有候选构建、安装和 `scripts/phase3-qa-fixture.sh`，不另建通用测试平台。
- 只复用不属于当前验收目标的准备工作。用例若测试构建、安装、启动或真实宿主派发本身，相关步骤必须在本轮实际执行。
- 各用例不能共用会互相污染的可变状态；需要同一会话连续推进的场景，明确作为有顺序依赖的一组。
- 某条失败只阻止依赖它的后续操作，其他可独立执行的用例继续。最终结果仍按每条用例登记。
- 批量执行是同一 QA 派发内部的组织方式，不为每条用例新增代理、逻辑任务或派发额度。

**高成本前置状态允许手动构造的规则继续保留。** 用例写清构造了什么，随后真实调用
被测入口并观察结果；不能构造一个“已经成功”的结果替代待测操作。若真实 host 交互就是
验收目标，必须真实交互。沿用现有项目边界，不增加固定成本阈值或逐条申请许可。

### 测试脚本怎么处理

不要求每轮先交付一整套新测试工程。一次性简单检查可以直接执行；经常重复的步骤才
整理为短小脚本或现有测试工具可运行的用例。

脚本只承担明确的准备、调用、取证和断言职责。新增或修改时检查这些内容是否对应已确认
用例、是否会漏报失败；未变脚本按相同版本复用，不重新启动完整设计审批。
修复缺陷的回归测试要证明能发现原来的错误，关键成功/失败判断应有已知错误样例校验。
不强制为全部测试再写一套“测试的测试”，也不新增递归 QA 流程。

## 4. 黑盒中断：保存已完成结果，补跑剩余部分

例如，63 条已执行完 59 条，剩下 4 条卡住，应保留前 59 条各自的真实结果，后续补跑
缺失部分。前 59 条可以有 PASS 或 FAIL，不能因为执行过就全部当作通过。

- 在现有 run 状态及证据机制中保存本次执行已完整完成的条目；中断原因和未完成项同时可见。
- 续跑前核对待测版本、用例版本、执行工具和相关环境。未改变且证据完整的部分可以复用；变化影响到的部分重新执行。
- 半途停止、没有可核对输出或状态不清楚的用例，仍是未完成，不继承为 PASS。
- 整体尚未执行完整时保留 `PENDING` / `RUNTIME_ERROR` 等相应未完成状态；不能提前登记整轮通过。
  最终按批准的预期集合汇总，缺失、重复、未知用例及授权跳过继续分别识别。
- 已有跨轮次结果继承和 `AFFECTED` 范围继续使用；本项新增的是同次未完成执行的进度保留与受控续跑。
- 续跑遵守现有派发生命周期、重试上限和 3.5b 的额度规则，不用新任务编号绕过上限。

## 5. 白盒：先独立判断覆盖，再复用测试、补缺口

QA 先根据需求与实现列出应该验证的行为和关键分支，再检查已有测试。已有测试的输入、
断言和覆盖有效，就明确绑定并独立运行；缺少或不可靠的部分才新增、修正。

- 取消“不能读取或复用已有测试、每条都必须由本轮 QA 新写”的要求。
- 保留独立设计判断、测试位置与用例的对应关系、独立执行和真实输出；开发者说已通过不能代替 QA 运行。
- 普通逻辑优先用单元测试，跨模块行为用集成测试，真实公开路径由黑盒承担；按需求保留必要交叉验证，避免无理由重复验证同一事实。
- QA 审查既有测试时必须看真实断言，不能只核对测试名或覆盖率。有问题的断言要修，不能仅凭现有测试全绿认定需求满足。
- 白盒新增或修改测试时，提交并形成最终含测试快照；没有测试改动时，不为凑出一份新测试交付物推进快照。

本项有意把保证从“测试必须重新编写”改为“QA 必须独立检查覆盖和断言并运行”。
黑盒隔离规则保持不变。

## 6. 少为建议返工，最后只测确定的交付版本

### QA Review 的可选建议

真实的需求漏测、操作不可执行、预期错误，按项目范围与严重度规则处理，仍会阻止用例
获批。仅凭条目 FAIL 不能自动升级成 P1。

确属可选的 P2/P3 建议保留稳定 ID，允许采纳、延期或不采纳并记录理由；不再要求
为了关闭建议一定新增、修改或删除用例。完成处置且覆盖校验通过即可冻结。
采纳建议如果改变共同路径或某条用例的验收含义，按第 2 节重新检查受影响部分。

这明确替代当前“QA Review P2/P3 必须通过改用例吸收后才能冻结”的规则。
只调整 QA Review，不改变门审 P2 必须修、门审 P3 留作建议及产品审/技术审的处置规则。

### 最终版本与 Seal

把最终提交整理（含需要的 squash）移到最后一轮必需验证之前；验证绑定最终要交付的
不可变候选，Seal 只固化这些结果，不再先制造一个新候选再触发整套重跑。

中间返修仍使用已有 `AFFECTED` 范围。路线及 requirement guarantee 要求的最终 `FULL`
继续执行；后续若交付版本发生变化，相关证据重新判定，不凭“内容看起来一样”直接继承。
阶段 7 的主线集成、最终验证、Seal、安装切换顺序继续遵守总计划。

## 7. 参考了哪些具体实现

以下是已核验组件中可借鉴的机制，不是声称这些仓库都拥有与本项目相同的独立黑盒审批流程。
采用哪些办法以及如何保留本项目的保证，由上面的计划明确规定。

| 参考实现 | 实际做法 | 本项目采用的部分 |
| --- | --- | --- |
| [Archon review](https://github.com/coleam00/Archon/blob/main/.archon/workflows/sdlc/review/archon-review.yaml) | 首轮多角度审查，返修后由一个 continuation reviewer 对照旧问题与修复改动检查 | 减少重复复审；不照搬其上下文开放方式，黑盒隔离保留 |
| [Compound Engineering](https://github.com/EveryInc/compound-engineering-plugin/blob/main/skills/ce-code-review/references/finish-review.md) | 问题去重后集中验证；符合其条件的测试建议与残余风险另列，真实缺陷保留 | 集中处理共同事实、区分可选建议与阻塞问题；不把所有 P2/P3 一概忽略 |
| [Playwright Pro](https://github.com/alirezarezvani/claude-skills/blob/main/engineering-team/playwright-pro/skills/generate/SKILL.md) | 沿用已有测试设施生成测试，再交给 runner 实际执行 | 重复操作交给程序；命令行项目使用已有脚本和工具，不强制采用 Playwright |
| [阿里 Open Code Review](https://github.com/alibaba/open-code-review/blob/main/internal/agent/agent.go) | 审查引擎保存进度、支持恢复并区分部分完成 | 把进度保存和恢复机制用于 QA；这是本项目的适配，不是该仓库已有黑盒续跑 |
| [Addy Osmani test-engineer](https://github.com/addyosmani/agent-skills/blob/main/agents/test-engineer.md) | 写测前了解已有测试，分析覆盖缺口，选择合适测试层级 | 白盒先判断覆盖再补测，复用经独立检查的有效测试 |

## 8. 落地顺序与改动位置

先处理黑盒审查与建议往返，再处理批量执行和中断续跑，随后完成白盒复用与最终版本
顺序；测试随对应实现推进，最后做同一候选上的综合验证。这是工作顺序，不按编号自动
增加正式 Batch 或子代理。

| 工作 | 主要改动位置 |
| --- | --- |
| 共同步骤、逐条判断、增量复审 | `prompts/actions/qa-design.md`、`prompts/actions/qa-review.md`，现有用例及覆盖校验 |
| 批量执行、独立副本、最小脚本 | `prompts/actions/qa-execution.md`、`scripts/phase3-qa-fixture.sh` 及现有候选准备工具 |
| 本次执行进度与续跑 | `internal/validate/workflow_qa.go`、现有结果持久化与派发生命周期 |
| 白盒复用、建议处置与冻结 | QA 三份提示词、`internal/validate/review_convergence.go` 及相关校验 |
| 最终候选先确定再验证 | `internal/validate/workflow_carry_seal.go`、快照与 review-wave 衔接 |
| 操作规则与阶段 4 接入 | `SKILL.md`、`references/formal-flow.md`、README，以及对应 engine QA 合同与 fixtures |

3.5c 的交付目标是隔离候选里可实际使用的 QA 改进，不能仅交一个预览器或纯计算函数
就宣称运行流程已经提速。阶段 4 接入 engine 时沿用同一语义，不另建第二套 QA 状态机、
账本或测试平台。修改候选不会自动更新固定稳定 driver；驱动版本和全局安装继续遵守
总计划的隔离、冻结与切换边界。

不在本阶段迁移旧 run、追改旧 Seal、扩张项目支持范围，或增加实时成本面板。
3.5a 的覆盖完整性、3.5b 的成本口径与有限重试继续保留。

## 9. 怎么验收

| 场景 | 应看到的结果 |
| --- | --- |
| 多条用例共用准备步骤，其中一条预期有误 | 共同部分审一次，错误用例仍被单独发现；全部用例都有明确结论 |
| 只改一条用例，或改共同步骤 | 前者只重新检查该条及实际受影响部分，后者重新检查所有依赖该步骤的用例 |
| 多条独立用例批量执行 | 每条可追溯到真实命令、输出和结果；状态不串用；构建、准备次数可核对 |
| 执行中途停止，再恢复 | 已完整完成且绑定未变的结果保留，缺失部分补跑；版本或相关条件变化会使受影响结果失效；未齐不能整体 PASS |
| 高成本前置状态手动构造 | 构造内容有记录，被测操作仍真实执行；测宿主派发或安装本身时有本轮真实证据 |
| 已有白盒测试有效，以及已有测试断言有误 | 前者复用并独立运行，后者被识别并修正；不因测试已经存在或已经全绿就放行 |
| QA Review 只有可选建议，以及存在真实验收缺口 | 前者完成理由登记后可冻结，后者继续阻塞；不扩大到门审或产品审规则 |
| 最后一轮必需验证通过后 Seal | 结果与最终交付候选一致，Seal 不再改候选并触发重复全量验证 |

用固定的一组正常场景、常见错误和已知缺陷比较优化前后：分别记录设计、审查、执行
耗时，输入/缓存输入/输出 token，派发次数，构建与准备次数，中断后的重复执行量。
复用现有 cost 投影，补最小的步骤耗时记录；缺失计量不能当作零。按本阶段追加并已确认的
Codex 交付要求，两版使用相同 Codex 模型和配置，真实完成设计/审查/执行；输入、缓存命中、
未命中、输出与原生请求 usage 对账，模型任务计时包含工具等待且与 CLI 命令耗时分开。
必需指标采集不全时对比仍未完成，须修复或补跑；该计量修复不扩展到其他 provider。

正确性要求是既定覆盖不遗漏、已知缺陷仍能发现、未完成不能通过；效率要求是上述重复
审查、重复准备和可避免的重跑实际减少，并在相同条件下给出前后数据，不预设固定提速倍数。

本文保留此前 3.5a/3.5b 及审查收敛需求作为历史依据。3.5c 实施时，仅按本文明确改变的
QA 审查方式、白盒复用、QA 建议处置、执行续跑和最终候选顺序同步当前规则与阶段 4 接入；
其余已确认约束继续有效。
