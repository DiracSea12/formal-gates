# ADR-002：开发分批与验证档位

> 状态：已由用户确认（2026-08-22），作为通用流程规则冻结。
> 范围：任何 run 的开发组织与验证节奏；引擎按总需求 §8.5"开发分批与组间验证"机械承载。补充 ADR-001 未覆盖的开发过程组织层。
> 决策依据：2026-08-22 对业界系统（Claude Code、OpenAI Codex、MetaGPT、LangGraph、CrewAI、Google Jules、OpenHands、SWE-agent、Aider、Agentless）公开资料的调研。

## 背景

大体量 run 若一次性交付，开发质量与审查覆盖同时衰减；若每个子单元都跑全套验证流程，成本不可接受。需要一个通用的分批与验证档位规则，使成本与质量由方法保证而非原则希望。

## 业界调研结论

1. **验证绑定任务/里程碑边界是共识**：OpenAI Codex 官方模式为里程碑小到单个 agent 循环内可完成，每个里程碑配验收标准与验证命令，每完成即跑 tests/lint/typecheck，失败就地修复后才继续（stop-and-fix rule）；CrewAI guardrail 的定义即"进入下一任务前校验本任务输出"。
2. **轻量护栏每步、全量测试批边界是隐性共识**：SWE-agent 与 Aider 每次编辑后跑本机 lint（免费毫秒级，SWE-agent 消融实验证明价值约 3 个百分点）；没有任何被调研系统默认每步跑全套测试（Aider 的每步 auto-test 存在但默认关闭）。
3. **大 diff 两种先例**：Claude Code `/batch` 把大迁移拆为 5–30 个子代理、各自独立 worktree 与 PR（对应本项目的 split 档）；Aider 每次编辑一个 commit（天然小步可回滚）。
4. **"分批验证 vs 一次性验证"的量化成本权衡业界空白**：无任何被调研系统正面回答过该问题。最接近的三条边角料：Claude Code 的档位哲学（"Each step trades setup for attention"）、MetaGPT 限制验证-修复循环次数防失控（重试 ≤3）、Agentless 用 LLM 筛选回归测试避免全量执行（$0.70/issue 成本卖点）。本 ADR 的档位判据因此只能建立在结构性信号上，不能引用业界量化先例。
5. **OpenHands 实证教训**：提示词式任务管理被实测证伪——agent 会一次性重写任务清单、报告执行而未真正执行（官方 issue #9970），随后转向显式工具维护 plan 文件。这直接支持本决策"引擎机械承载、不依赖代理自觉"的立场。
6. **业界无系统以代码行数作为任务粒度判据**：Claude Code 用语义判据（一句话能说清 diff 边界），Codex 用"一个循环内可完成"，OpenHands 的 <100 LOC 属交互式小任务指引、与本 ADR 的批不同层。行数受测试占比、语言、样板密度、重构增删影响，衡量不了"是否单一关注点"。

## 决策

1. **批次计划义务**：受理阶段只确认需求与方案，不冻结批次计划；显式批次计划在拆分决定与路线确认时一并产生、经同一次用户决定确认并留痕，于开发开始前登记。允许"单批 + 理由"退化形态。划分依据依赖链、体量与风险：依赖链（消费链）必须串行；零耦合支线可并行；共享文件、接口或语义的工作面不并行；接口冻结点优先作为批边界。
2. **批粒度**：批是任务单元，单批一个内聚关注点——语义判据为"能用一句话说清本批 diff 即一批"；批内提交保持原子、可独立构建。
3. **验证节奏分层**：批内每次编辑后执行项目声明的低成本确定性检查；批边界执行该开发计划指定的回归命令；每批终态可判——树可构建、声明的回归通过、自测留痕、任务清单逐批勾选。检查与命令由各项目按自身构建/测试成本声明，不预设"毫秒级"或具体工具。
4. **探路优先**：含不确定性边界的探路工作必须作为首批 spike：结论留痕，代码不进入交付。
5. **验证档位**（随批次计划一并选定并留痕）：批内自测为固定底座（永远启用）；默认为开发完成后单次全量门禁；确有需要时增设组间快照 + 增量审查 checkpoint（冻结中间 DevelopmentSnapshot，复用 ReviewScopeMode 与 carry 继承判定：未受影响 PASS 直接沿用，只对增量 diff 审查/执行；组间轮不计 repair wave）。档位依据结构性信号：预期生产逻辑是否多模块扩散、独立验收单元数；不依据总行数或批数。split 属 run 拆分机制（child/merge/独立 Seal 生命周期），不是验证档位，不在此选择。
6. **不变量**：批次不改变 run 边界、公共入口、Seal 语义或强制并行不变量；不产生额外受理、双审或 Seal 轮次。
7. **引擎义务**：batch 是现有 TaskKey 上的分组与依赖信息，批次完成状态从成员 task 与验证结果派生，不新增 batch 状态机、receipt 或独立生命周期。组间快照与增量 diff、carry/AFFECTED 判定复用既有机制。批次登记与边界执行由引擎机械承载；批怎么切、档位选哪个等语义判断由主代理/Operator 建议、用户确认，引擎不实现语义分类器。

## 量级经验参考（非规范）

本项目初期实测批次约在数百至两千行区间（含测试），单次全量档适用于生产逻辑集中且测试占比高的 run。此句仅为经验参考，不构成规范；各 run 受理时按第 5 条结构性信号自行评估。

## 已拒绝的替代方案

- 每子单元全套验证流程（成本不可接受；业界无此做法）；
- 一次性大 diff 交付（开发与审查质量同时衰减，无缓解机制时业界无先例）；
- 提示词自觉遵守分批纪律（OpenHands 实证证伪）；
- 以代码行数作为批粒度或档位判据（业界无先例且信号最弱，见调研结论 6）；
- 把 split 当作验证档位在受理时选择（split 是 run 拆分机制且其绑定时点在拆分决定，受理时选择与之矛盾）；
- 为 batch 新增独立状态机/receipt 生命周期（batch 是 TaskKey 的分组与派生信息，见决策 7）。
