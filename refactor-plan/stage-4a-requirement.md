## 需求点

### REQ-001：沿现有入口连续执行批准批次
#### 要求
从批准用例、shared-step、依赖、允许范围和 pending 派生可执行清单；facade 连续消费获准的 prepare、target、collect，保存逐操作绑定与回执，正常步骤间无需模型重新编排。机械判据由经审查脚本实际断言；文字 oracle 不自动转成可执行判据，退出零不等于语义 PASS。需要语义判断时交回证据，原生交互目标仍实跑。所有层级代理受同一入口约束，不扩大名单、重开 TaskKey、调换开发代理或重跑保留 PASS。
#### 验收条件
- AC-001：小型多批用例实际连续完成合法步骤，逐条结果可核对，模型往返减少；名单外、倒序、重复及已完成操作仍拒绝，语义问题未被机械通过替代。
#### 来源
计划 §2.1、§4.1；阶段 3.5c QA 复用和阶段 4 任务操作契约。

### REQ-002：共用准备并保留状态隔离
#### 要求
接通现有候选导出、构建及 `scripts/phase3-qa-fixture.sh`，不恢复旧 workflow 调用。相同有效构建内容、参数和工具链只准备一次；返修未提交修改属于输入，变化时重建受影响产物。并行相同准备复用现有绑定与互斥；普通用例共用依赖、工具缓存，仅分配独立输入、可变工作与输出，不逐例复制完整 HOME、插件、源码及依赖。安装、构建、缓存隔离或原生交互为目标时保留独立真实操作；不能复制活动 run 或带路径绑定安装制造合法新实例。昂贵调用前检查已明确且可本地验证的前提；失败说明差异，不放宽判据。通用函数参数化，未变脚本不重新完整审批。
#### 验收条件
- AC-002：并发、续跑与换执行者不重复有效准备；同基线下未提交返修不会复用旧产物；用例状态互不污染，明确前提错误提前发现，必要独立准备仍实际发生。
#### 来源
计划 §4.2；3.5c REQ-002、REQ-003、REQ-008。

### REQ-003：独立工作持续推进
#### 要求
复用现有依赖、资源归属、任务领取与修订校验；原生调用等待时推进独立可运行项，同流程依赖有序，实际共享可变资源按资源串行。失败只阻塞依赖项；全受阻时列明关系。并发上限表示排队，不是 FAIL；有限重试沿既有契约。进度等待能及时处理纠偏，不以查询周期充当任务预算或取消任务。

engine 签发动作后，由持续运行的程序执行器自动领取并通过当前宿主适配器完成启动或续用、身份绑定、等待、结果采集和再次推进；主代理不逐项转交，也不能选择遗漏合法动作。执行器只消费 engine 已签发动作，不自行决定任务、顺序、重试、恢复或结果接纳。动作和宿主调用使用持久化状态、幂等标识及可恢复租约，进程重启后继续合法未完成项，不重复已观察副作用。只有用户确认、无法自动恢复的明确阻塞或终态交还主代理。

所有声明完整支持的宿主必须提供可编程的启动、续用、等待、采集、取消、身份和用量能力。安装或启动前完成能力探测；缺少强制闭环所需能力时明确拒绝该宿主的完整流程，不得退回依赖主代理手工转交的路径，也不得让动作长期停留在已签发未运行状态。
#### 验收条件
- AC-003：小型混合场景证明主代理不执行任何逐项转交时，已签发动作仍由程序自动进入宿主启动、续用、等待、采集和后续推进；等待和单支失败期间独立项继续，依赖与共享资源顺序正确；上限下排队可恢复，进程重启不重复已观察副作用，阻塞原因具体。对每个声明完整支持的宿主核对能力探测与同一闭环；能力不足时在启动前明确拒绝，不留悬空动作。
#### 来源
计划 §4.3、§8。

### REQ-004：逐例留证、批量交回与增量续跑
#### 要求
用既有结果字段记录实际命令、退出码、输出位置与判据比较，沿 checkpoint/submit 批量处理；既有事件足够时不另创协议。程序检查完整性、重复、冲突及文件存在，独立判断处理语义矛盾。只交回新增结果和合法剩余项，由现有 writer 原样保留有效旧条目及身份、来源绑定。缺证据、暂停、自然语言结论均不能代替实际 PASS 或退出证据。
QA 设计、审查和返修恢复阶段 4 前的职责与增量模式，由当前引擎自动推进：
- 黑盒、白盒设计者交付可执行用例及共享准备的草稿增量，不自行给整套 QA 覆盖下 PASS/FAIL 结论。真正的工具或运行错误仍按既有错误恢复处理；尚未做完不作为一份覆盖判定结束设计。确有公开契约或前态阻塞时，说明已核实的具体障碍，沿原有缺口、审查和用户处置流程解决，其余可完成部分继续交付。
- 程序合并新增、修改和删除：新用例由程序分配稳定 ID；修改、删除引用已有 ID；未提及的用例、共享准备及有效审查/执行记录原样保留。整体替换必须显式提出，不把一次局部提交当成全量替换；真实修改仅使受影响的审批和执行记录失效。
- 设计冻结完整可照做的步骤、前置构造方法、取证方式和判据，不强制提前编写驱动脚本或 command。未声明命令的批准用例由执行者在既有 qa.target 提交实际命令；引擎绑定候选、用例、工作目录和操作回执，保存实际 stdout/stderr/退出码，仍拒绝名单外、倒序和重复操作。已声明命令不得被替换；执行者不得改变批准步骤或判据。批量消费将需要执行者填写命令的用例明确列为待输入，继续其他合法独立项，不冒充失败或 PASS。
- 独立 QA 审查负责用例可执行性、需求与验收点映射及集合层面的完整覆盖。设计提交被接纳仅表示草稿已登记，不表示覆盖通过；完整覆盖与必要审查未通过，不冻结、不进入最终验收。
- 审查要求返修后，设计者取得当前完整用例集、相关审查意见和已认可结果，只提交必要增量。程序拒绝没有实质新增、修改或删除的重复返修，不能只重列未覆盖项或重复原结果冒充修复；有效且未受影响的成果不重做。
- 领取、派发、等待、采集、合并、独立审查、返修及后续推进由现有引擎与执行器负责，保留原流程必要的主代理核实和用户确认节点。开发与基线黑盒设计仍并行；模式和次数不由主代理临时编排。复用现有状态、结果、稳定标识与宿主适配器，不恢复旧 CLI、旧 writer 或兼容路线，不新增另一套任务或材料系统。
#### 验收条件
- AC-004：多批及中断恢复结果覆盖精确集合，旧 PASS/FAIL 不被重抄改写；缺失、重复、冲突仍拒绝，语义失败保留真实证据，仅恢复合法剩余项。 复用小型夹具验证设计增量闭环：初次草稿进入独立审查，缺失覆盖被检出；返修新增缺失用例且保留原 ID 和有效结论；无实质修改的重交被拒绝；修改只重审受影响项，显式删除/整体替换才移除旧项；重启和重放不重复合并、不丢已有成果。黑盒与白盒沿同一通用机制验证，不增加平台实机全量重跑。 验证无设计期 command 的用例能获独立批准，并经同一引擎在执行期完成实际命令、双流和退出码取证；恢复保留实际操作，原批准命令不可替换，越界或重复执行被拒绝。
#### 来源
计划 §4.4、§8–9；现有 checkpoint/result 契约。 阶段 4 前 QA 增量设计、独立审查和实质返修合同（ee990ba）。

### REQ-005：减少上下文和状态搬运
#### 要求
启动消息给角色、当前动作、准确候选、必要绑定与范围，以及当前动作所需文档、代码、脚本和证据的可读取路径；代理通过已有文件读取、搜索和查看差异能力按需读取，保留原代理身份。产品审、技术审、开发与续做、黑白盒设计及复审、QA 执行、门审、返修均遵守同一交接原则。引擎决定材料范围、绑定和交接，主代理不筛选、拼装或逐项转交。

主代理在需求案编写及产品审、技术审阶段可以编写、修改需求和方案，按既有流程确认。一旦进入开发阶段，正式派发提示词完全由引擎依据已确认需求、方案、任务及其绑定材料生成；主代理不得自行撰写、改写或追加其中任何文字，也不得通过 Batch 的任务、子任务、DoD、材料说明或其他自由文本字段重新定义开发范围。正式开发派发入口仅允许引用已确认对象及提交明确用户决定；自行替换、缩写或加料的任务定义和发送内容须被拒收，不能只靠代理自觉。需要改变需求、方案或已确认任务时，先通过现有正式变更流程返回相应编写、审查和确认阶段，再进入开发；不新增另一套规划器或材料系统。该限制按当前正式阶段生效，不扩成全程禁止主代理编写需求案。临时对话消息暂不禁止，本次不增加聊天拦截。

不把源码全文、完整代码差异、整轮结果、全部 QA 状态或全部历史交接直接塞入提示词；不以迁移到 prompt.txt、总索引或其他强制中间文档代替删除无关材料，也不新增专用分段检索协议。文件路径绑定当前动作所用版本，在实际工作区可读取；有现成版本文件时直接引用，确需固定的结构化任务材料只保存当前动作所需部分，不另复制整仓材料。

按当前动作筛选相关材料，无关内容不进入启动消息、路径清单或该动作材料副本。开发只交当前批次、必要依赖和实际续做信息；增量设计只补受影响部分；QA 执行只交当前用例及其必需共享步骤、依赖和续跑证据；返修只交当前修复范围关联的问题与必要证据。门审以绑定的基线、候选和审查范围按需查看差异。必要的完整需求与待审设计仍可定位和读取，不能为减小体量丢弃验收范围或原始证据。

状态投影只交回新增完成、剩余计数与具体异常，不反复输出整份 state、提示词及全部 PASS。主代理按异常定位原始证据，不逐条重写通过结论。实际派发与追加消息对用户可见，摘要不能替代权威材料。新版本接入并验证可继续当前 run 后立即移除旧驱动兼容分支和本次临时过渡代码，保留历史结果、证据、身份、次数及其正常读取能力，不等 Seal 再清理。
开发提示词禁止未经用户允许擅自新增、修改或删除需求外的功能或代码。必要配套须有与当前需求的直接关系及不修改会失败的具体依据，不以文件名单限制正常跨文件实现。复杂度门检查完整实现 diff 中的需求外改动并核实必要性；未经授权且不属于必要配套的其他功能修改至少 P1/FAIL，达到交付阻塞等 P0 后果时定 P0。以需求/授权与实际 diff 对照证明，不以必须另有运行故障为阻塞前提，也不因改动有益或可撤回而降级。
所有阶段实际交给模型的固定规则、动态输入、结果 schema 和工具说明均须逐项检查并精简，包括需求澄清、产品审、技术审、开发与续做、黑白盒设计与复审、白盒前置覆盖判断、QA 执行与续跑、各门审及返修。固定规则去重，按当前角色和动作选择必需章节；黑盒不收到白盒专用规则，其他角色亦不得混入不适用规则。无关或失效内容直接删除，不进入任何必读文件或路径清单。渐进式披露使用已有文件读取能力和当前绑定的准确路径：初始消息只提供当前职责、必需约束、最小绑定与需要读取的材料入口；按需读取相关细节，不把整份规则或材料正文换到另一个文件继续强制全文读取。宿主环境、完整 PATH、内部调度摘要等不供角色决策或结果绑定使用的字段不进入模型输入。保留实际职责、合法输入、验收边界和结果契约，不以缩短文本为由丢弃要求；不新增索引层或披露框架。结果 schema 只描述当前动作合法结果，使用实际接口支持的结构；引擎继续校验重复路径等语义约束。

**技术方案：本轮 B4 的剩余交付**
B4-S1 对应上述全部阶段的实际消息、结果 schema 和工具说明优化；不是只检查旧的材料路径功能或过滤环境字段。复用当前共用装配入口和已有 Markdown 章节选择，逐角色删除重复与无关说明；按动作提供需要的规则及可读取材料入口，不增加平台分支、提示词文件或披露框架。

当前已核实的缺口包括：QA 审查整份加载白盒专用规则；所有角色收到包含不可用操作的整段工具说明；白盒 testFiles schema 的 uniqueItems 被实际接口拒绝。修复这些实例后仍须检查所有其余阶段，不能把实例清单当成缩小范围的依据。源码、diff 和不相关的历史材料继续遵守路径交接与不灌入约束。
