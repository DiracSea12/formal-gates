# 阶段 3.5c：QA 提效正式需求与技术方案

## 目标与范围

落实 `refactor-plan/stage-3-5c-qa-efficiency.md`，在保留独立 QA 和覆盖完整性的前提下，减少重复审查、重复准备和可避免的重跑。黑盒优先，兼顾白盒；交付隔离候选中可实际使用的流程改进。

本次修订同时纳入用户追加的两项交付：修复已复现的历史 checkpoint 测试失败，并用真实模型调用补齐优化前后对比的模型耗时与 token；该对比不得以 unavailable 作为完成结果。

token 和用时修复明确限定为 Codex 模块：其真实宿主调用、来源绑定、用量解析、计时和现有 cost 投影的交付验证。其他 provider 不在本次修复范围内；共用投影仅承载 Codex 修复所需的数据，保持其他 provider 的既有行为。

本 checkpoint 接在 3.5a、3.5b 之后、阶段 4 之前，不新增正式阶段或 RunPhase。此前黑盒长执行未完成的记录仅用于确定优化重点，不作为全量 PASS 或提速承诺。

正常使用和常见误操作的范围、严重度与证据边界沿用 `prompts/reviewer-base.md`。3.5a 覆盖契约、3.5b 单一 cost 投影和有限重试继续有效；只有本文明确列出的 QA 行为和最终候选顺序发生改变。

## 技术方案

1. 在既有用例模型中保存可复用的共同准备/操作说明及稳定引用，设计与审查消费同一份内容。每条用例保留特殊前提、操作差异、oracle 和覆盖映射。共同说明变化时，按引用关系撤销相关审批；未变且不受影响的审批继承。
2. 在现有 QA 提示词、`scripts/phase3-qa-fixture.sh` 和候选准备工具中落实批量执行。按不可变候选复用构建和非验收目标的准备步骤，为独立用例创建干净副本；有序场景显式声明依赖。短脚本只负责准备、真实调用、证据采集和断言。
3. 扩展 `internal/validate/workflow_qa.go`、现有结果持久化和派发续跑入口，在同一 run 的现有状态中分次登记完整逐例结果。进度绑定候选、用例版本、执行工具及相关环境，保留中断原因、未完成集合和复用/失效依据；最终仍由原 expected-set 和覆盖校验汇总。
4. 扩展 QA 建议处置和 `internal/validate/review_convergence.go` 的冻结条件：稳定 suggestion ID 可登记采纳、延期或不采纳及理由。采纳并改变共同路径、可执行性或验收含义时，重审受影响部分；仅可选建议不再强制修改用例。
5. 修改 QA 三份提示词和白盒引用校验，让 QA 先独立列出应验证的行为、分支与 oracle，再读取已有测试的输入和真实断言，绑定有效测试并独立运行，补齐缺口。有测试变动才形成含测试的新快照。
6. 将现有 Git 提交整理/squash 从 `workflow_carry_seal.go` 的 Seal 尾部前移到最后一轮必需验证之前，衔接快照与 review-wave。最终验证绑定整理完成的不可变候选；Seal 检查同一 identity、固化结果并物化既有流程产物，不再改变候选身份。后续代码、测试或候选变化仍按既有影响判定处理。
7. 同步 `SKILL.md`、`references/formal-flow.md`、QA 提示词、README/README_EN、相关 engine QA 合同、fixtures、阶段计划和命令路由矩阵；只同步本文改变的语义。阶段 4 沿用同一契约，不在此阶段提前完成 regular engine 全流程接管。
8. 修正历史 checkpoint 检查的比较对象，使路径和文档都来自该测试声明的同一 base/delivered 快照对。保持真实历史内容及检查义务，不通过跳过用例或修改旧记录取得通过。
9. 使用 Codex，在同模型、同固定场景和同环境条件下实际执行优化前后的设计、审查和执行阶段，保存真实宿主调用及用量来源。沿用 `internal/cost` 和现有 cost 投影，接通必要的 Codex 来源绑定，解析当前 Codex 的实际 usage 记录，并消除同一请求的重复计数。记录各阶段起止时间与墙钟耗时，明确计时边界；输入、缓存输入、非缓存输入和输出 token 与 Codex 宿主原始计数对账。采集失败表示对比未完成，修复采集或补跑后再交付。该修复不扩展到其他 provider。

新增参数及结果字段沿用既有 CLI 约定，由实现和技术审确定；必须提供已文档化、可在隔离安装中真实调用的操作路径，不能仅交预览器、纯函数或依赖手改正式 state 的演示。候选中沿用当前仍提供 QA 能力的 runtime/writer 路径，既有 engine envelope 不得回落给 legacy writer。

## 需求点

### REQ-001：共同说明复用与逐条增量审查

#### 要求

设计与审查共用可引用的准备步骤和操作说明，共同部分检查一次，每条用例仍判断特殊前提、差异操作、可执行性、真实取证方法和验收标准。未变且不受影响的审批继续继承；修改用例或共同说明时，重新检查实际受影响的全部用例。source、验收点、case 双向映射完整对账，不抽样或按组背书。黑盒设计/审查留在基线隔离环境，不读取本次生产代码、白盒测试或开发者解释；新增入口按已确认公开契约判断，不因基线尚无入口而否决。

#### 验收条件

- AC-001：多条用例引用同一准备说明，其中一条 oracle 有误时，共同部分只有一份设计/审查记录，错误用例被单独识别，每条用例均有明确审查或合法继承结论，覆盖映射无遗漏。
- AC-002：只修改一条用例时，仅该条及实际受影响部分失效；修改共同说明时，所有引用它的用例重新检查；黑盒输入中没有本次实现、白盒测试或开发者解释。

#### 来源

3.5c 计划第 2、8、9 节；3.5a 的覆盖完整性与黑盒隔离约束。

### REQ-002：批量真实执行与状态隔离

#### 要求

同一候选构建一次，复用不属于验收目标的准备工作，独立用例从干净副本起步；需要同一会话连续推进的场景明确为有序依赖组。逐条记录实际命令、输出、结果，一条失败只阻止依赖操作，其余独立用例继续。若构建、安装、启动或真实宿主派发本身是验收目标，本轮必须真实执行对应步骤。批量仅是同一 QA 派发内部组织，不新增逐例代理、TaskKey 或额度。

#### 验收条件

- AC-003：固定独立用例组批量执行时，构建和共同准备次数可核对、重复次数减少，每条有独立真实输出；加入会改状态的用例后，其他用例仍从干净状态开始。
- AC-004：注入一条真实失败后，依赖步骤停止、独立用例继续，各自结果正确；以安装或真实宿主交互为验收目标的用例具备本轮真实证据，不能用复用准备替代。

#### 来源

3.5c 计划第 3、9 节。

### REQ-003：构造前置状态与最小执行脚本

#### 要求

继续允许构造高成本前置状态，记录构造内容，随后真实调用被测入口并观察结果，不构造已成功的目标结果。一次性简单检查直接执行，重复步骤才整理为短脚本或既有测试工具用例。新增/修改脚本核对准备、调用、取证、断言与已确认用例是否一致、是否漏报失败；同版本未变脚本可复用。缺陷回归测试须能发现原错误，关键成功/失败判断使用已知错误样例校验，不为全部测试递归编写测试。

#### 验收条件

- AC-005：构造前置状态的用例明确记录构造与真实操作边界，真实调用和观测可追溯；没有将目标成功结果预置后当作实跑证据。
- AC-006：新增/修改执行脚本遇到已知错误样例时报告失败，缺陷回归用例可识别原错误；相同脚本版本复用不触发新一轮完整设计审批。

#### 来源

3.5c 计划第 3 节“高成本前置状态”和“测试脚本怎么处理”、第 9 节。

### REQ-004：同次未完成执行的进度保存与受控续跑

#### 要求

在现有 run 状态及证据机制中保存已完整完成条目的真实 PASS/FAIL，同时显示中断原因和未完成项。续跑核对候选、用例版本、执行工具和相关环境；绑定未变且证据完整的结果可复用，变化影响到的部分重新执行。半途停止、输出不可核对或状态不清楚的条目保持未完成，整体未齐保留 PENDING/RUNTIME_ERROR 等状态。最终 expected-set 校验继续区分缺失、重复、未知条目和授权跳过；授权跳过不是 PASS。沿用跨轮 AFFECTED 继承和同 TaskKey 生命周期、重试上限及 3.5b 额度，不用新编号绕过限制。

#### 验收条件

- AC-007：一组含 PASS 和 FAIL 的执行中途停止后，完整条目及证据保存，续跑只补未完成项且保留原 FAIL；半途条目不继承为 PASS，结果未齐时整轮不能 PASS。
- AC-008：分别改变候选、用例、工具或相关环境，受影响进度失效并重新执行；未受影响且绑定有效部分可复用，原因可核对；缺失、重复、未知和授权跳过被正确识别，续跑不增加逻辑任务额度。

#### 来源

3.5c 计划第 4、9 节；3.5a 执行完整性与 3.5b 有限重试约束。

### REQ-005：白盒独立覆盖判断与已有测试复用

#### 要求

QA 先独立列出需验证的行为、关键分支和 oracle，再检查已有测试的输入、真实断言和对应覆盖。有效测试显式绑定并独立执行；缺少或错误部分才新增、修正。普通逻辑优先单测，跨模块用集成测试，公开路径以黑盒承担，保留有依据的交叉验证。取消不得读取/复用已有测试、每条必须新写的限制，保留用例与测试位置对应、独立运行和真实输出。有测试改动须提交并形成最终含测试快照；无改动不为新增交付物而推进快照。

#### 验收条件

- AC-009：有效已有测试经 QA 独立检查覆盖、输入和断言后绑定复用，并有本轮真实执行输出；没有测试改动时无需新增测试文件或推进快照。
- AC-010：已有测试全绿但断言错误/覆盖缺失的样例被识别并修正或补测，相关测试提交进入最终快照；不能仅凭测试名、覆盖率或开发者声明放行。

#### 来源

3.5c 计划第 5、9 节。

### REQ-006：QA 可选建议按理由处置后冻结

#### 要求

真实需求漏测、步骤不可执行或预期错误仍阻止相应用例获批，按项目范围和严重度判断，不因条目 FAIL 自动升级 P1。确属可选的 P2/P3 保持稳定 suggestion ID，允许采纳、延期、不采纳并记录理由，不强制改用例；全部处置且覆盖校验通过后可冻结。采纳若改变共同路径、可执行性或用例验收含义，重审受影响部分。本变更只适用于 QA Review；门审 P2 必须修、门审 P3 作建议、产品审/技术审用户处置规则继续有效。

#### 验收条件

- AC-011：仅有可选 P2/P3 的用例集，逐 ID 登记采纳/延期/不采纳和理由后可通过覆盖校验并冻结；未知 ID、缺理由或未处置项不能被当成已完成处置。
- AC-012：真实验收缺口即使被附上可选建议处置也不能绕过用例批准/覆盖校验；采纳导致路径或验收含义变化时受影响部分重审，门审和产品/技术审规则未被替换。

#### 来源

3.5c 计划第 6 节“QA Review 的可选建议”、第 9 节；明确替代旧 QA P2/P3 必须改用例吸收规则。

### REQ-007：最终候选先确定、最后验证、Seal 固化

#### 要求

将最终提交整理（含必要 squash）放在最后一轮必需验证之前。QA 与门结果绑定最终要交付的不可变候选，Seal 不再生成新候选而触发重跑。普通返修沿用 AFFECTED，路线及 requirement guarantee 要求的最终 FULL 仍需完成；候选后续变化重新判定相关证据，不凭内容相似直接继承。黑盒用例等既有 Seal 产物仍正常落盘，阶段 7 主线集成、最终验证、Seal、安装切换顺序继续遵守总计划。

#### 验收条件

- AC-013：含多条提交及白盒测试变更的场景，在最终验证前完成整理，最后必需验证与 Seal 指向同一 candidate identity；Seal 不再 squash 或要求因自身改候选而新增一轮全量执行。
- AC-014：最后验证后改动候选时，旧证据不能直接作为新候选完整通过；AFFECTED 与最终 FULL 的既有要求仍成立，Seal 产物正常落盘且不改变已验证候选身份。

#### 来源

3.5c 计划第 6 节“最终版本与 Seal”、第 9 节；增量封板计划阶段 7 顺序。

### REQ-008：隔离交付与阶段 4 同义接入

#### 要求

开发在独立 worktree，正式 run 使用现有冻结稳定 driver；候选从已提交快照构建并安装到独立 namespace，真实运行新增 QA 能力。运行输入不软链到开发工作区，候选 host/config/state/registry 与稳定环境隔离。同步当前文档、提示词、校验、engine QA 合同和阶段 4 接入计划，保持同一语义与 writer 归属。本阶段不迁移旧 run、不追改旧 Seal、不切全局安装、不增支持平台、不建第二套 QA 状态机/账本/测试平台、不增加实时成本面板。

#### 验收条件

- AC-015：从不可变提交构建的实际隔离安装具备可调用的共同说明、建议处置、进度续跑和最终候选操作路径；证据标明源码与安装身份、各隔离路径，候选不驱动本正式 run 或写稳定状态。
- AC-016：QA 提示词、操作文档、CLI 行为、engine 合同/fixtures 和阶段 4 计划对本文变更一致；3.5a 覆盖、3.5b cost/额度及黑盒隔离保留，未提前接管 engine regular 全流程或添加第二 writer。

#### 来源

3.5c 计划第 8、9 节；增量封板计划第 1、2 节的固定驱动与隔离交付规则。

### REQ-009：正确性与实际重复成本对比

#### 要求

本项追加的 token 和用时修复仅针对 Codex 模块，优化前后的真实模型对比均使用 Codex。

在相同条件下，用固定正常场景、常见错误和已知缺陷比较优化前后。设计、审查、执行阶段必须包含实际模型调用，并分别记录可对账的阶段起止时间、墙钟耗时、输入/缓存输入/非缓存输入/输出 token、派发次数、构建/准备次数和中断后的重复执行量。明确模型任务墙钟时间是否包含工具等待，不把 CLI 写入耗时冒充模型耗时。复用现有 cost 投影，仅补最小计时和来源接入；本次交付对比中的必需模型耗时及 token 不得为 unavailable，也不得以零值、估算或模拟 lifecycle 替代真实用量。来源暂未就绪或无法对账时，该项保持未完成，修复采集或补跑至取得真实数据。正确性要求覆盖不漏、已知缺陷仍发现、未完成不能通过；效率要求重复审查、重复准备和可避免重跑实际减少，不承诺固定提速倍数。

#### 验收条件

- AC-017：交付固定场景、优化前后源码/模型/环境、真实宿主调用、命令与结果的对比记录，能核对重复审查、构建/准备和中断重跑的减少；两版设计、审查、执行的模型任务耗时与各类 token 均有真实来源，必需指标没有 unavailable 或冒充缺失值的零数。

## 实施顺序与完成定义

初始顺序为：共同步骤与审查/建议处置 → 批量执行与中断续跑 → 白盒复用与最终候选顺序 → 同一候选综合验证、对比记录和隔离交付。现有实现保留；本次追加先修正历史检查并补齐真实模型计量，再完成对比及最终候选验证。测试随对应修改推进，不按条目数新增 Batch 或代理，补充开发沿用技术审复核后的粒度决定。

复用现有测试设施，不引入新依赖；对比证据保存为本阶段验证记录并引用现有 cost 投影，不另建权威账本。每项实际交付路径纳入 VCS，正式独立审查与封板按已确认路线和固定 driver 执行。

完成需满足 REQ-001 至 REQ-010 的全部适用验收条件、所选正式验证与 Seal，并保留阶段候选/主线集成身份的既有关联记录。历史检查失败和对比中必需模型指标 unavailable 不再作为本次交付可保留的未完成项。授权跳过必须如实保留，不称为执行 PASS。

## 考虑过但不采用

- 不照搬外部参考仓库架构或引入通用测试平台：计划只借鉴减少重复操作的具体机制。

- 不让可选建议为了关闭状态而强制改用例，不为未变测试或脚本重复完整设计审批。
- 不用新代理/新 TaskKey 绕过中断重试上限，不预造目标成功结果，也不为测试再建递归 QA。
