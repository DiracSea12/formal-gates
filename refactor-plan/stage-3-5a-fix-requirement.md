# 需求案：3.5a-fix

## 背景与目标

当前 formal-gates 的需求确认流程已经要求 AI 与用户先对齐需求，再生成需求/方案文档，随后交给产品审和技术审。本次改动让这份需求案同时承担三种职责：

1. 给人阅读的完整需求与方案说明；
2. 给产品审、技术审使用的确认事实来源；
3. 给 QA 覆盖流程引用的结构化需求点来源。

需求案仍由 AI 根据用户原始输入和对齐结果直接编写，不增加一份独立的“任务清单”或草稿文件。程序只检查文档是否符合约定的机械结构；需求是否合理、是否完整以及业务含义是否正确，仍由用户、产品审和技术审判断。

凡是必须实现、会改变产品或流程行为、或者需要进入 QA 验收保证的内容，都必须写入 `## 需求点` 下的 `REQ/AC`。需求点之外的自然语言正文只用于背景、解释和方案说明；其中可以记录由技术审或开发后代码审查/实现质量门验证的技术方案约束，但不得独立新增一条未进入 `REQ/AC` 的产品或流程要求。仅约束实现位置、代码边界或未来迁移归属且不改变产品/流程行为的内容不得伪装成 `AC`，否则会与“所有 AC 必须进入 QA 闭环”自相矛盾。

本次改动的核心完成条件是：对于绑定本需求案且启用 QA 的 run，凡是已经写入并由用户确认的 `REQ` 和 `AC`，都必须进入后续 QA 覆盖与执行闭环；任何未被 QA 用例覆盖、未执行或未通过的确认项，都不能被流程判定为完成。lightweight 不写这类需求案，保持原有记录路线；custom 允许不选择 QA，但该 run 明确不提供需求覆盖保证。

## 范围与非目标

范围：

- 复用现有 `requirements-clarification` 与 `workflow requirement --confirmed` 用户确认机制。
- 允许 AI 在 run 内直接编写和修订当前正式需求案；用户确认前，该文件处于未确认状态。
- 在用户确认前，对需求案执行确定性的 Markdown 结构预检；预检失败时不允许确认通过。
- 保留背景、目标、范围、方案、约束、风险等自然语言正文；只对“需求点”章节规定机器可读结构。
- 所有必须实现的产品/流程行为和验收条件都必须进入“需求点”章节；其他正文不能成为绕过 `REQ/AC` 覆盖投影的独立需求来源。
- 产品审、技术审和 QA 继续使用用户确认后的同一份需求案。
- 从用户确认后的需求案自动生成 QA 必须覆盖的有限集合；不得再人工抄写或手工筛选另一份覆盖清单。该规则只适用于启用 QA 的 run。
- 对启用 QA 的 run 中每个确认后的验收条件建立“需求点 → 验收条件 → QA 用例 → 本次执行结果”闭环，缺少任一环节时阻断通过。
- full route 固定选择 QA，因此在只绑定一个正式需求案文件时进入需求覆盖保证；custom route 选择至少一个 QA 类型时同样进入保证，覆盖按所选类型并集计算。custom 不选择 QA 时允许继续，但 run 必须明确标记为“不提供需求覆盖保证”，不得声称所有 `REQ/AC` 已完成 QA 闭环。
- lightweight route 不写入本需求案，不受本 change 的 `REQ/AC` 覆盖保证约束，保持原有记录路线行为。
- 本 change 的强制 QA 覆盖保证同时适用于 `split=no` 和 `split=yes`。分片时由保留总任务实例持有完整需求投影，各切片和合并范围逐项认领 `AC` 责任，合并后再对最终完整候选执行全量 QA 并由保留总任务实例汇总结论；串行或并行执行切片不改变保证标准。
- 启用本 change 覆盖保证的 run 不允许额外登记 `--requirement-artifact`；full 或 custom+QA 在发现额外 artifact 时必须拒绝进入 QA 设计。覆盖保证状态必须由当前 run 的持久化启用状态明确表达，不能根据 artifact 数量、route 或文件格式临时猜测。
- 产品审和技术审各自最多自动完成三轮；超出后不得继续自动派发，只能由用户逐轮明确授权。
- 产品审和技术审的原始审查结果、逐项裁决与当前有效流程状态必须分离；有效状态写错后可通过受控、可审计的正式操作纠正，不能手改 `state.json`，也不能靠空跑一轮审查洗掉错误状态。
- 不修改 `internal/engine` 的自动化编排、状态协议或 3.5a 覆盖引擎。

非目标：

- 不要求用户的原始输入采用 OpenSpec、PRD 或其他固定格式。
- 不为每一种外部需求格式编写适配器。
- 不让程序替代用户判断业务含义、优先级、合理性或“是否还有遗漏”。
- 不新增独立的需求清单、独立的人工确认阶段或第二套需求事实来源。
- 不允许直接覆盖或删除原始审查证据；“状态可纠正”只改变带完整来源的裁决和有效流程投影，不提供手工编辑状态文件或抹除历史的后门。
- 不改变现有分片判据、切片开发隔离方式、合并顺序或并行调度策略；本 change 只补充需求点责任分配、最终候选全量 QA 和保留总任务汇总门控。

## 需求点

### REQ-001：需求案与结构化需求点合一

#### 要求

最终需求案必须同时保留自然语言正文和结构化需求点。结构化需求点直接写在同一份需求案中，不另建任务清单或 QA 清单作为需求事实来源。

需求点章节是必须实现的产品/流程行为及其验收条件的唯一声明位置。其他正文可以解释这些需求或记录技术方案约束，但不能独立增加需要实现或需要 QA 保证的产品/流程要求；发现此类内容时，必须先将其改写进对应 `REQ/AC`，再允许确认。

每个 `REQ` 的“要求”字段中，凡是能够独立漏做、会改变产品或流程行为、或者需要进入 QA 保证的强制义务，都必须由同一 `REQ` 下至少一个 `AC` 明确承接。产品审必须逐条核对这种“要求义务 → AC”关系；不能仅凭其他 AC 大致相关就推定已经覆盖。只描述原因、背景或不改变产品/流程行为的技术说明不要求机械拆成 AC；但一旦该说明本身成为必须满足的交付约束，就必须进入 AC。

#### 验收条件

- AC-001：对于同时包含自然语言正文和多个有效 `REQ/AC` 区块的需求案，预检通过，并能从同一文件提取出完整且一致的 `REQ/AC` 集合供后续产品审、技术审和 QA 覆盖流程使用。
- AC-002：需求案之外不再要求维护第二份承载同一需求的清单。
- AC-027：产品审发现需求点之外存在独立的、必须实现的产品/流程行为或验收条件时，需求案不能通过；该内容必须先进入对应 `REQ/AC`，不能在结构化覆盖集合之外被确认并获得完整覆盖保证。
- AC-042：产品审必须逐个 `REQ` 核对其“要求”字段中的每项独立强制义务是否由同一 `REQ` 下至少一个具体 `AC` 承接；发现仅写在要求正文、可能独立漏做却没有对应 AC 的义务时必须 FAIL 并一次列全，补齐前不能确认该需求案具备完整覆盖保证。

#### 来源

用户已确认“清单与需求案合二为一”。

### REQ-002：需求案正文保留自然语言，需求点采用固定 Markdown 结构

#### 要求

需求案采用 UTF-8 Markdown。除 `## 需求点` 章节及其需求点区块外，文档可以使用自然语言和普通 Markdown 组织背景、目标、范围、方案、约束和风险。

整份文档必须且只能有一个 `## 需求点` 章节；该章节至少包含一个、数量不限的需求点。章节下的每个直接三级标题必须是一个需求点，格式为：

```markdown
### REQ-001：非空的需求点标题

#### 要求

一段或多段非空的自然语言要求。

#### 验收条件

- AC-001：一条可观察、可判定的验收条件。
- AC-002：另一条验收条件。

#### 来源

一段或多段非空的来源说明。
```

字段的规范如下：

- 需求点标题必须匹配 `### REQ-[0-9]{3,}：标题`；`REQ` 编号至少三位数字，标题不能为空。需求点数量没有上限。
- `REQ` 编号在整份文档中必须唯一，不要求连续，也不因插入新需求点而重编号。
- 每个需求点必须按“要求 → 验收条件 → 来源”的顺序，且各有且只有一个对应的直接 `####` 字段；需求点区块不得再包含其他直接 `####` 字段。
- “要求”字段必须有非空内容，可以是一段或多段自然语言。
- “验收条件”字段至少包含一条直接列表项；每条必须匹配 `- AC-[0-9]{3,}：非空验收条件`。
- `AC` 编号在整份文档中必须唯一，不要求连续；修改已有验收条件时保留原编号，新增条件使用未占用编号。
- “来源”字段必须有非空内容，可以写用户原始输入、对齐结论或已确认的外部规格来源。
- 需求点区块在下一个同级 `###` 需求点或 `##` 章节开始处结束。
- 需求点章节外出现 `### REQ-...` 标题、规范“验收条件”字段之外出现形如 `- AC-...` 的直接列表项，或者需求点区块中出现缺少规范字段的需求点，均视为结构错误，而不是被静默忽略。
- 按 CommonMark 语义识别围栏代码块；代码围栏中的标题和列表项示例不参与解析。

#### 验收条件

- AC-003：缺少 `## 需求点`、出现多个 `## 需求点`、章节内没有需求点、需求点没有标题或需求点 ID 不符合格式时，预检失败。
- AC-004：重复 `REQ` ID 或重复 `AC` ID 时，预检失败，并报告重复 ID 和所在行。
- AC-005：缺少“要求”“验收条件”或“来源”字段、字段顺序错误或字段内容为空时，预检失败；错误输出必须包含需求案文件路径、错误行号、具体违反的结构规则，并在能够识别所属需求点时包含对应 `REQ` ID。
- AC-006：验收条件中存在不符合 `AC` 格式的直接列表项，或没有任何验收条件时，预检失败。
- AC-007：背景、目标、方案、约束和风险等非需求点正文可以继续使用自然语言，不因没有结构化字段而失败。
- AC-017：需求案不是可按 UTF-8 解码的 Markdown，`## 需求点` 下存在不是规范 `REQ` 标题的直接三级标题，或者 `REQ/AC` 标题或正文为空时，预检失败。
- AC-028：每个需求点的“要求”“验收条件”“来源”必须是直接 `####` 字段、各有且只有一个并保持规定顺序；存在其他直接 `####` 字段、字段重复或字段跨越下一个同级 `###` 或 `##` 边界时，预检失败。
- AC-029：合法的 `REQ/AC` 编号可以不连续；插入新需求点或验收条件时，已有条目保持原编号，新增条目使用未占用编号，不得因要求连续编号而失败或自动重编号。
- AC-030：需求点区块在下一个同级 `###` 需求点或 `##` 章节处结束；`## 需求点` 之外的 `### REQ-...`、规范“验收条件”字段之外形如 `- AC-...` 的直接列表项、区块边界内缺少规范字段的需求点均按结构错误报告；CommonMark 围栏代码块中的 `REQ/AC` 示例完全不进入解析、重复检查或覆盖投影。
- AC-043：恰好包含一个结构合法 `REQ` 且该 `REQ` 至少包含一个合法 `AC` 的需求案必须能够通过结构预检；解析器不得设置需求点数量上限，并且包含任意有限数量结构合法、ID 唯一的 `REQ/AC` 区块时不得仅因数量较多而失败。

#### 来源

用户要求先把结构标准规定完整，再查看成品；本格式是在不强制统一外部需求输入格式的前提下，为 formal-gates 内部正式需求案规定的最小统一结构。

### REQ-003：AI 生成、程序预检、用户确认

#### 要求

流程接收用户原始输入后，由 AI 将对齐结果直接写入当前 run 绑定的正式需求案。程序对当前文件执行上述结构预检；AI 可以根据预检错误继续修订同一文件。预检通过后，将当前文件原样呈现给用户，由用户确认这一版内容。

#### 验收条件

- AC-008：预检失败时，`workflow requirement --confirmed` 被拒绝，需求状态保持未确认。
- AC-009：预检通过后仍必须取得用户明确确认，程序不能把预检通过自动当作用户确认。
- AC-010：用户确认绑定的是当前需求案 revision；产品审、技术审、开发和 QA 不得消费未确认 revision。
- AC-011：预检只报告结构性错误，不对业务语义作出替代用户的最终判断。
- AC-044：AI 从用户原始输入和对齐结论生成当前 run 的正式需求案，并在预检失败或用户要求修改时直接修订同一个已绑定文件；流程不得要求先生成草稿文件，也不得另建第二份清单后再复制回正式文件。
- AC-045：结构预检通过后，呈现给用户确认的必须是当前 run 已绑定的完整正式需求案及其当前 revision，而不是摘要、另一份文档或旧 revision；用户确认后记录的 revision 必须与所呈现文件一致。

#### 来源

用户已确认“直接写正式需求文件，然后校验，再给用户确认”，不增加草稿步骤。

### REQ-004：预检接入现有确认机制，不增加用户环节

#### 要求

预检作为现有需求确认链路的前置校验，接入现有 `requirements-clarification` 和 `workflow requirement --confirmed` 机制。预检通过且用户确认后，继续使用现有 revision/hash 绑定和后续审查流程。

#### 验收条件

- AC-012：不新增独立的用户确认阶段；用户只确认当前这份正式需求案。
- AC-013：用户确认后修改需求案会被现有 revision 漂移/需求修订机制识别，不能静默继续使用旧确认。
- AC-014：产品审、技术审和 QA 只能消费用户确认后的需求案 revision。
- AC-046：结构预检必须作为现有 `requirements-clarification` 与 `workflow requirement --confirmed` 链路的前置门控；预检通过和用户确认仍通过这条既有链路记录，不得旁路、替换或新增另一条确认入口。

#### 来源

用户已确认“修改现有确认机制适配新机制，复用已有确认环节”。

### REQ-005：复用公开流程与既有覆盖协议

#### 要求

本次改动在现有需求确认、workflow/run-state、QA 和 Seal 公开流程上增量启用，不要求调用方改用第二套入口，也不改变现有 3.5a coverage contract 的输入/输出协议。适配层必须把确认后的需求案和现有 QA 记录转换成 3.5a 已有的 source、point、case、edge、review、whitelist 与 execution 输入，不能另造第二套覆盖判定核心。

`internal/engine` 不得修改，以及 legacy 与阶段 4 的实现归属，是本次方案的技术代码边界，放在“方案与技术约束”中由实际 diff、静态检查和实现质量门验证；它不是普通 QA acceptance point。开发前技术审只判断这个宏观边界能否落地，不提前做逐文件代码审查。

#### 验收条件

- AC-015：不启用 QA 覆盖保证的正常路线继续使用同一套自动化流程和对外协议，不新增第二套调用入口。
- AC-016：启用保证能力时，适配层把 `REQ`、`AC` 和 QA case 分别投影为现有 3.5a coverage contract 的 required source、acceptance point 和 acceptance case，并生成唯一的 coverage edge；QA review 必须显式提交逐 source、逐 point、逐 case 的完整决定后才能调用既有 whitelist 投影，不能只凭 case PASS 自动推导或伪造 source/point PASS，现有 coverage 协议及判定结果保持不变。

#### 来源

用户已确认“不改自动化引擎”。

### REQ-006：每个已确认需求点必须完成 QA 覆盖与执行闭环

#### 要求

用户确认需求案后，程序必须从当前确认 revision 中自动提取全部 `REQ` 和 `AC`，生成本 run 的权威 QA 覆盖输入。每个 `AC` 必须映射到至少一个经 QA 审查批准的用例，并且所有映射用例都必须在当前候选上得到执行通过结果。该覆盖输入只能由确认后的需求案派生，不允许人工另抄一份可独立增删的清单。

保证能力必须以 run state 中持久化的 `RequirementGuaranteeActivation`（字段名可等价）显式表达。full 或 custom+QA 只有在结构预检、用户确认并冻结需求投影后才能进入 `active`；custom 无 QA 与 lightweight 分别保持本需求定义的非保证状态。不得根据 artifact 数量、当前 route 或文件看起来像新格式而临时猜测激活。

本条只适用于本 change 定义的 QA-enabled guarantee：formal flow 中使用 full route，或 custom route 选择至少一个 QA 类型，并且只绑定一个正式需求案文件。一个 `REQ` 只有在它包含的全部 `AC` 都完成“已批准用例覆盖 + 最终当前候选执行通过”后，才能视为完成。任何确认后的 `REQ` 或 `AC` 没有进入覆盖输入、没有 QA 用例、用例未获批准、用例未执行或执行未通过，均必须阻断 QA PASS、相关完成门和正常 Seal。custom route 不选择 QA 时不触发上述阻断，但必须保留“不提供需求覆盖保证”的明确状态；lightweight 不进入本条链路。存在额外 requirement artifact 时，不能进入本保证模式，必须在 QA 设计前拒绝该模式，而不是产生部分覆盖结果。用户若通过既有显式 Seal 跳过授权强行封板，可以继续获得带审计记录的非正常 Seal，但覆盖保证必须永久标记为 `waived/not-guaranteed`，逐项列出未闭环内容，且不得生成完整闭环 PASS。

`split=no` 时，当前 run 直接对完整需求投影和当前候选负责。`split=yes` 时，保留总任务实例持有完整且权威的需求投影；每个 `AC` 必须且只能分配给一个主责任范围，主责任范围可以是某个切片或保留总任务的合并范围。切片可串行或并行执行，均使用同一份已确认需求案 revision，并只能为分配给自己的 `AC` 建立责任映射；用例可以同时覆盖多个 `AC`，但不能因此改变或隐藏主责任分配。全部切片合并后，保留总任务实例必须把各切片和合并范围已批准的 QA 用例去重汇总，并在合并后的最终完整候选上以 `FULL` 范围重新执行全部用例。切片候选上的执行结果只能作为中间结果，不能替代最终合并候选上的执行。跨切片交互仍由合并 QA 覆盖，但合并 QA 不能代替对全部已批准用例的最终全量执行。

分片整体要获得覆盖保证，每个承担 `AC` 主责任的切片都必须选择 full，或选择至少一个 QA 类型的 custom；任何责任切片选择不含 QA 的 custom 时，切片可以按既有授权继续，但保留总任务实例必须标记整体“不提供需求覆盖保证”，不得产生全部闭环 PASS。切片 Seal 只表示该切片在自身候选上的阶段性完成，不得声称整个需求案已完成；只有保留总任务实例在最终合并候选上汇总通过后，才能给出整体保证并最终 Seal。

#### 验收条件

- AC-018：确认需求案后，覆盖输入中的 `REQ` 集合与需求案中的 `REQ` 集合完全一致，不允许缺少、额外或手工筛选。
- AC-019：覆盖输入中的 `AC` 集合与需求案中的 `AC` 集合完全一致，每个 `AC` 必须归属其文档中的 `REQ`。
- AC-020：每个 `AC` 至少映射一个经 QA 审查批准的用例；一个用例可以覆盖一个或多个 `AC`。选择多个 QA 类型时，以所有已选择类型的合并覆盖结果为准，不要求同一 `AC` 在每个类型中重复覆盖；没有映射、只有未批准用例或映射到未知 ID 时，QA 不能 PASS。QA review 必须对完整 `REQ/source`、`AC/point`、`case` 集合分别逐项给出决定，任一层缺失、重复、未知、非 PASS 或仅有集合级/case 级 PASS 时不能生成 approved whitelist。
- AC-021：保证模式每次执行都必须使用 `FULL` 范围覆盖当前候选；每个已批准用例必须在当前候选上执行。缺少结果、未执行、失败、待定、使用 `AFFECTED`/继承结果，或结果绑定到旧 revision/旧候选时，QA 和正常 Seal 不能 PASS；显式跳过授权只能得到逐项留痕的 `waived/not-guaranteed` Seal，不能得到覆盖保证。
- AC-022：需求案 revision 发生变化时，本 change 对 QA-enabled guarantee run 保守地使该 run 的全部覆盖绑定、QA 审查结论和 QA 执行结果失效；分片时同时使责任分配、全部切片和合并范围的覆盖绑定、审查及执行结果失效。旧结果可以作为历史记录保留，但不得被 meaning-preserved 重新绑定或冒充当前 revision，新的 revision 必须重新确认并完成完整覆盖闭环。
- AC-023：`workflow show` 必须输出当前覆盖保证状态、绑定的需求 revision、方案 revision 和 manifest digest、`REQ/AC` 总数，并逐项输出每个 `REQ/AC` 对应的 QA 用例、审查状态和当前候选执行状态，使“已确认但未实现或未测试”的条目不能被集合级 PASS 隐藏。
- AC-024：对已经持有当前版本有效 guarantee activation 的 run，full route 固定进入 QA 保证；custom route 选择至少一个 QA 类型时进入同一保证并按所选类型的覆盖并集判断；custom 不选择 QA 时流程可以继续，但相应 run 的可见结果明确写出“不提供需求覆盖保证”，且不得生成“全部 `REQ/AC` 已完成 QA 闭环”的 PASS 结论。分片整体中任一承担 `AC` 主责任的切片不选择 QA 时，保留总任务实例同样不得生成整体保证结论。
- AC-025：lightweight route 不要求写入本需求案，保持现有记录路线，不因本 change 新增 QA 阻断。
- AC-026：QA-enabled guarantee 必须只绑定一个正式需求案文件；额外 requirement artifact 在 QA 设计前被拒绝进入保证模式。`split=no` 和 `split=yes` 都可进入保证，串行或并行分片采用相同标准，均不得产生部分覆盖冒充完整覆盖的结论。
- AC-031：`split=yes` 时，保留总任务实例从同一确认 revision 建立完整权威 `REQ/AC` 投影，并在任何切片 QA 设计前记录“每个 `AC` 恰有一个主责任范围”的完整分配；遗漏、重复主责任、未知 `AC`、未知切片或切片与主任务 revision 不一致时阻断继续。
- AC-032：切片 QA 用例只能把该切片主责的 `AC` 作为责任覆盖输入；用例附带覆盖其他 `AC` 时可作为重复证据保留但不能改变主责任归属。切片 `workflow show` 和 Seal 必须明确它只完成自身责任范围，不能输出整个需求案已完成的结论。
- AC-033：每个切片 Seal 必须为保留总任务实例留下不可变的已批准 QA 用例清单及其需求 revision、QA 类型、case ID 和 `AC` 绑定；用例全局身份按“切片或 master 范围 + QA 类型 + case ID”确定。所有切片合并后，保留总任务实例必须按该身份汇总并去重各切片及合并范围全部已批准 QA 用例，在最终合并候选上按 `FULL` 范围重新执行；任何用例只在切片候选执行、被继承、使用 `AFFECTED`、缺少结果或未通过时，整体 QA 和正常 Seal 被阻断。
- AC-034：合并 QA 必须覆盖跨切片交互和集成接缝，但不能作为全部最终执行的替代品；保留总任务的完整闭环只有在每个 `AC` 都能追溯到主责任范围、已批准用例和最终合并候选 PASS 结果时成立。
- AC-035：保留总任务的 `workflow show` 和 Seal 必须逐项汇总完整 `REQ/AC` 的责任切片或合并范围、QA 用例、审查状态及最终合并候选执行状态；任一责任切片为 custom 无 QA 时整体显示 `not-guaranteed`；已进入保证但存在缺失、旧 revision、旧候选或未通过状态时显示未完成并阻断正常 Seal；显式跳过时显示 `waived/not-guaranteed`。三种情况均不得显示完整闭环 PASS。
- AC-048：一个 `REQ` 只有在该 `REQ` 的全部 AC 都已经映射到经 QA 审查批准的用例，并且全部相关用例都在最终当前候选上执行 PASS 后才可显示完成；产品审按 AC-042 发现要求正文仍有未 AC 化的强制义务时，该 `REQ` 不得进入已确认的完整覆盖集合。
- AC-057：run state 必须持久化 guarantee activation、来源和绑定的需求投影；只有确认链路完成结构预检、用户确认和投影冻结后才能写入 `active`。activation、投影冻结和 revision/CAS 提交必须原子；字段缺失、损坏或部分写入时安全拒绝产生保证 PASS，不得根据其他状态猜测或补造完整闭环。

#### 来源

用户明确要求：凡是已经写进并确认的需求案内容，流程必须防止实现漏做和 QA 漏覆盖。

### REQ-007：产品审和技术审各自具有三轮自动上限

#### 要求

产品审 `product-review` 与技术审 `start-readiness` 必须各自维护独立、持久化的完成轮次计数。每个动作默认最多自动完成三轮；达到三轮后，编排层不得继续自动准备第 4 轮。用户可以在看到剩余问题和风险后逐轮明确授权额外一轮，但授权不能预先累积，也不能同时扩大另一个审查动作的额度。

轮次上限属于语义审查循环，不是代理运行失败重试。只有成功记录的 `PASS` 或 `FAIL` 才计一轮；`RUNTIME_ERROR`、被判无效的审查、未完成或中断派发不计轮，也不得消耗额外授权。需求 revision 改变、meaning-preserved/meaning-changed 重绑或普通结果失效不能自动清零，以防通过反复改 revision 绕过上限；只有用户显式执行 workflow reset、结束当前 run 或启动新 run 才建立新的自动额度。

当前 regular formal flow 的权威编排仍在 legacy workflow 状态机，因此本 change 先按现有开发后审查波次的模式，在 `internal/validate` 的 run state、派发前门控和结果记录中提供同语义过渡实现，不修改本 checkpoint 尚未承载 regular 的 `internal/engine` 代码。同时直接更新 engine 权威重构方案：阶段 4 迁移 regular 时，Controller 必须按 master run + action kind 接管两条持久化 `PreDevelopmentReviewSeries`，前三轮按需生成 workflow-policy 预授权的 fresh-review `TaskKey`，超限转 action-specific typed Ask 并逐轮只增加一个 TaskKey；legacy 字段随后退役，不保留双权威。该语义轮次不能与单个任务的瞬时 `RetryPolicy.MaxAttempts` 混同。

审查轮次能力必须在 run 创建时初始化两条持久化 series，并从成功记录的完整语义审查结果机械投影 completed 轮次。不得从 `dispatch.attempt`、当前单值 `ActionResult` 或 transcript 猜测、补造或重建轮次，也不得在普通 revision 变化或结果失效时静默清零。

#### 验收条件

- AC-036：`product-review` 和 `start-readiness` 分别公开持久化 `completed`、默认上限 `3` 与用户额外授权轮数；一个动作的计数或授权不影响另一个动作。
- AC-037：每次成功记录 `product-review` 或 `start-readiness` 的 `PASS`/`FAIL` 后，对应完成轮数恰好增加一；如果该轮使用了一次用户额外授权，则同时只消费这一轮授权。`RUNTIME_ERROR`、无效结果、未完成或中断派发既不增加轮数，也不消费额外授权；同一已授权语义轮次可以在运行故障后重派，无需用户重复授权。
- AC-038：某动作已完成三轮且没有未消费的额外授权时，准备下一轮必须被 CLI 硬拒绝；用户通过 `--user-requested` 并提供非空理由后，只放行该动作的一轮额外审查并留痕，不能一次授权多轮或授权另一个动作。
- AC-039：需求 revision 变化、meaning-preserved/meaning-changed 和普通审查结果失效保留两个动作的已完成轮数及额外授权记录；显式 workflow reset、新 run 或终态结束按各自既有生命周期建立新额度。
- AC-040：`workflow show` 输出两个动作各自的完成轮数、当前有效上限、剩余自动轮数和额外授权来源；到达上限时，下一步明确要求用户决定，而不是继续自动派发或把超限伪装成 `RUNTIME_ERROR`。
- AC-041：三轮上限只约束产品审和技术审的语义轮次，不改变开发后 QA/门审已有的共享三轮波次，也不改变 agent task 因瞬时运行错误使用的 retry attempt 语义。
- AC-058：run 创建时必须原子初始化 `product-review` 与 `start-readiness` 两条 pre-development review series 及其 activation 来源；后续记录只能由绑定当前 action、revision 和有效完整审查结果的正式入口更新。字段缺失、记录不一致、损坏或部分写入时拒绝准备或记录下一轮，不得从 attempt、单值结果或 transcript 猜测轮次，也不得静默清零后声称三轮保证。

#### 来源

用户指出产品审和技术审可能无限复审，并明确决定：两个阶段都改成三轮自动硬上限，超出后由用户逐轮决定。

### REQ-008：审查状态可通过正式裁决纠正

#### 要求

产品审 `product-review` 与技术审 `start-readiness` 必须把三类事实分开持有：审查代理返回的原始候选结果、Operator/用户对 finding 的核实与裁决记录、由前两者确定性计算出的当前有效流程状态。审查代理的 `PASS`/`FAIL` 只是不可变的原始证据，不能被主代理直接抄成最终权威状态；Operator 必须先核实需求前提、正常入口、证据、范围和严重度，再把有效 finding 交给用户逐项确认或驳回。

即使候选结果已经被错误接纳，ACTIVE、非终态 run 也必须提供受支持的审查纠正操作。纠正可以把某个 finding 判为无效、修正严重度或修正错误裁决，并据此重新计算有效状态；语义纠正必须由用户明确确认，纯机械的 binding、完整性或 stale 校验失败可以由程序直接拒绝接纳。纠正必须精确绑定 run、action kind、dispatch/result digest、需求 revision 和被替代记录，写明原因、来源、旧值与新值；原始结果不得删除，只能被新的裁决记录 supersede。不得通过手改 `state.json`、伪造一轮 PASS 或额外空跑一次审查来纠错。

有效状态按固定规则投影：确认的 P0/P1 使对应动作保持阻塞并要求在修订后 fresh review；P2/P3 只形成建议；被驳回或纠正为无效的 finding 不再阻塞。如果一轮完整有效审查的全部 P0/P1 都已被驳回，且没有其他未处置或已确认的 P0/P1，则该轮的有效结果直接变为 PASS，可进入下一阶段，不得再派一轮只为改写聚合状态。finding 的确认、驳回、严重度修正或有效状态从 FAIL 改为 PASS，不新增也不删除一次已经完整有效的语义审查轮；只有整轮结果被判定为 invalid、incomplete、stale 或错误绑定时，该轮才不计数，并从权威计数投影中移除。

纠正导致有效状态由 PASS 变为阻塞时，必须使依赖该结果的后续产品/技术审、拆分、路线、开发、QA、门和 Seal 证据按依赖关系失效或等待重新建立；纠正只是清除错误阻塞时，则直接重新计算可用下一步，不制造新 review。阶段 4 引擎继续使用单一 `state.json` 权威投影和 CAS，不引入事件溯源；原始结果、裁决和纠正回执作为有界 typed records 保存在同一投影中。

#### 验收条件

- AC-049：run state 分别持久化原始 review candidate、稳定 finding ID/digest 及逐项 adjudication/correction、`EffectiveReviewStatus`；`workflow show`/engine `show/status/next` 同时显示原始结论、被 supersede 的裁决、当前有效结论和来源，三者不得共用一个可被直接覆盖的状态字段冒充彼此。
- AC-050：审查代理结果必须先经 Operator 核实需求前提、正常入口、证据、范围、严重度和完整性；无效、范围外、错误绑定、不完整或 stale 的候选不得写成有效 finding 或权威 PASS/FAIL。Operator 只能提出语义裁决候选，不能代替用户确认会改变有效产品/技术判断的纠正。
- AC-051：ACTIVE、非终态 run 提供正式的审查纠正 CLI 操作；阶段 4 提供等价的 typed correction event/Ask。每次纠正必须绑定精确 run、action、dispatch/result digest、需求 revision、目标 finding/adjudication，携带非空原因和授权来源，并以 CAS/freshness 拒绝过期或重复冲突纠正；原始审查结果保留，只追加可追溯的 superseding correction receipt。
- AC-052：有效状态确定性重算：存在未处置或已确认的 P0/P1 时保持阻塞；仅有 P2/P3 时为 PASS 加 advisory；所有 P0/P1 均被驳回或纠正为无效且不存在其他阻塞项时直接变为 PASS。该重算不得依赖新的审查代理输出。
- AC-053：一轮完整有效审查的唯一 P0/P1 或全部 P0/P1 被用户驳回后，下一阶段立即可用，不要求额外 fresh review、不消耗额外审查授权，也不得准备一轮没有待验证修订、只用于把 `FAIL` 改写为 `PASS` 的审查。
- AC-054：完整有效审查无论其 finding 后续如何确认、驳回、改严重度或使有效结论在 PASS/FAIL 间变化，都只计一个 completed semantic round；纠正判定整轮 invalid、incomplete、stale 或错误绑定时，该轮从有效计数中排除。任何纠正都不得重复计轮、重置其他动作的 series 或改变单个 TaskKey 的 retry attempt 额度。
- AC-055：纠正使有效状态由 PASS 变为阻塞时，所有依赖该状态形成的下游结果按依赖关系变为 stale/blocked，并在 `show/status/next` 列出影响；纠正只清除错误阻塞时，Controller/legacy workflow 重新计算并开放合法下一步，不清除无关证据、不额外派 review。

#### 来源

用户在本 run 中发现主代理把未经正确校准的候选 P1 写成正式 FAIL，随后即使用户驳回唯一 finding，现有状态仍要求空跑一轮才能进入技术审。用户明确要求审查状态可正式纠正，并询问引擎重构后是否仍会发生同类错误。

## 方案与技术约束

- 需求点结构只在本文件的 `## 需求点` 章节内生效；外部输入可以是任意自然语言、OpenSpec、PRD 或其他格式，由 AI 负责转写为本文件格式。
- 必须实现的产品/流程行为和验收条件只能由 `REQ/AC` 声明，且所有 `AC` 都必须进入 QA case 闭环。需求点外的正文只能作背景、解释或技术方案说明；仅约束实现位置、代码边界或未来迁移归属、且不改变产品/流程行为的技术约束不建立 `AC`，分别由 start-readiness、实际 diff、开发后代码审查/实现质量门验证。技术约束若同时改变产品行为或验收，必须把行为部分另写进相应 `REQ/AC` 并接受 QA。
- 预检实现为确定性 Markdown 解析/校验，不依赖模型判断；错误必须指出文件、行号、需求 ID（如可识别）和具体规则。
- 预检只保证结构、唯一性和字段完整性，不声称证明需求语义正确、验收条件合理或绝对没有需求遗漏。
- 结构预检通过后，对于 QA-enabled guarantee run，系统必须从同一确认 revision 自动派生并冻结一份保存在 run state 中的需求投影；投影至少包含完整的 `REQ/AC` 集合、需求 revision 和内容 digest。它是需求案的不可变投影，不是第二份可独立编辑的清单；具体存储结构由实现决定。
- QA adapter 必须复用现有 3.5a coverage contract：`REQ` 投影为 `RequiredSource(PRODUCT_REQUIREMENT, QA)`，`AC` 投影为 `AcceptancePoint`，现有 QA case 投影为 `AcceptanceCase`，三者关系只由 `CoverageEdge` 表达。映射必须校验 ID 存在、归属正确并去重；选择多个 QA 类型时，覆盖完整性按各类型合并后的并集判断，不把同一需求点强制要求在每个类型中重复声明。不得另建覆盖核心或修改 `internal/engine/coverage` 协议。
- QA review 的记录入口必须显式承载 3.5a `ReviewResult` 要求的完整 `SourceDecisions`、`PointDecisions`、`CaseDecisions` 及 unbound 集合；只有三层都逐项 PASS 才允许调用 `ProjectWhitelist`。现有仅按 case 的 review 状态可以作为 case 决定来源，但不得自动推导、补写或伪造 source/point PASS。QA execution 仍可按 case 提交，但每个需求点都必须能核验当前候选标识、候选 digest、需求 revision 和内容 digest。任一关联项缺 review、缺 execution、非 PASS 或绑定不匹配，都阻断 QA PASS 和 Seal。
- `workflow show` 必须公开输出覆盖保证状态、绑定 revision/digest、REQ/AC 总数和逐项覆盖状态；非分片 run 只有所有需求点完整通过时才能显示保证成立，分片由保留总任务实例输出完整聚合状态，切片只输出自己的责任范围。custom 无 QA 显示 `not-guaranteed`，不得显示完整闭环 PASS。
- 需求案同时承载需求和方案，因此覆盖契约的 `SolutionRevision` 与当前需求案的 `RequirementRevision` 使用同一个 revision；不新增第二份方案文件。
- QA case 必须记录一个或多个所覆盖的 `AC` ID；QA design 提交、QA review、QA execution 和 Seal 都通过这份绑定校验。custom 不选择 QA 时不创建这条强制闭环，并显式记录无覆盖保证；lightweight 不进入本 change。
- QA-enabled guarantee 在 route/QA design 前必须校验正式需求案文件数量为一；不满足时拒绝进入本保证模式，不尝试猜测 artifact 之间的合并关系。
- guarantee activation、来源、结构预检结果与冻结投影必须在用户确认和 revision/CAS 提交的同一原子状态变更中写入；不能靠 artifact 数量、route、文件结构或其他历史状态猜测或补造。
- `split=yes` 时，保留总任务实例冻结完整需求投影和 `AC → 主责任范围` 映射；责任范围为切片 run ID 或 master merge。每个 `AC` 恰有一个主责任范围，未知、遗漏或重复主责任均拒绝。切片继承 master 的需求/方案 revision 与 manifest digest，不独立改写或重解释完整需求投影。
- 切片的 QA manifest 只承载其主责 `AC`，并绑定 master run ID、slice run ID 和共同需求 revision；case 可额外覆盖其他 `AC`，聚合时按 case 与 `AC` 身份去重，但额外覆盖不能满足被遗漏的主责任分配，也不能让同一切片结果重复计数冒充多份独立证据。
- 所有切片合并后，保留总任务实例将各切片和 merge QA 的已批准 case 投影为最终执行白名单；该白名单必须绑定最终 merged candidate，并固定 `FULL` 执行。切片执行结果只作阶段性证据，不进入最终 PASS 继承；merge QA 负责新增跨切片用例，但不替代对切片既有已批准 case 的最终重跑。
- 分片聚合只扩展现有 workflow/run-state/QA/Seal 适配层与控制层，不改变 `internal/engine`。若现有 coverage contract 不能直接表达跨 run 聚合，由适配层为最终 master 校验组装单一完整 contract，再调用既有 engine 接口。
- QA-enabled guarantee run 的覆盖执行范围固定为 `FULL`；既有 `AFFECTED`/继承路径可以继续服务非保证路线，但不能为本保证模式提供满足条件的结果。
- 本 change 可以修改需求确认、预检、CLI、run state、QA 和 Seal 的现有适配层或控制层，但不得修改 `internal/engine` 的自动化编排、覆盖逻辑或既有协议；该代码边界由实际 diff、静态检查和开发后实现质量审查验证，不建立普通 QA acceptance point。
- 当前 checkpoint 的产品审/技术审轮次状态由 `internal/validate` 分动作持有，派发前检查有效上限，`record-action` 成功记录 `PASS`/`FAIL` 后计数，超限时复用 `prepare-action --user-requested --reason` 的用户来源留痕并只增加一轮。阶段 4 由 engine Controller 将同一状态迁为 master run + action kind 的 `PreDevelopmentReviewSeries` 和 action-specific typed Ask，随后删除 legacy 权威；该计数与开发后 `CompletedReviewWaves`/`ExtraReviewWaves`、pre-wave review series、engine task retry 四者彼此独立。
- legacy 过渡实现必须在审查状态中分开保存 raw candidate、finding 裁决/纠正和 effective status；settle/correction 后由程序重算 transition，不直接改写原始结果。阶段 4 用同一 `state.json` 投影中的 typed records、单调 revision/CAS 和纯投影接管，不引入事件溯源。对当前 run 这类“唯一 P0/P1 已驳回”的情况，纠正后的有效产品审状态直接为 PASS，不要求第 4 轮。
- pre-development review series 必须在 run 创建时与 activation 来源原子初始化，之后只从正式、完整、有效的语义审查记录投影；不从 attempt、单值结果或 transcript 猜测历史，也不因普通 revision 变化或结果失效重置。阶段 4 engine 接管后删除 legacy 权威计数，不形成双权威。
- start-readiness 必须评估开发粒度，至少分别判断 `REQ-001`～`REQ-006` 的“结构化需求案与 QA 覆盖保证”和 `REQ-007`～`REQ-008` 的“审查轮次与状态治理”是否应作为两个独立 Batch。该评估只决定同一 formal run 内的开发批次，不预设必须拆成多个正式 run；最终按技术审结论和用户确认的 slicing/route 执行。
- `RequirementConfirmed=false` 时，AI 可以在本 run 内修订需求案；该文件不能作为产品审、技术审、开发或 QA 的最终输入。
- 用户确认时绑定当前需求案 revision，并冻结对应 manifest；确认后的 revision 漂移继续走既有需求修订分类，但对本 change 的 QA-enabled guarantee run 一律让已有覆盖 binding、review 和 execution 变为 stale，必须针对新 revision 全量重新闭环。
- 现有工作区中与本需求无关的未提交改动不纳入本次范围。

## 确认状态与权威来源

本文件不保存可变的确认状态。是否已确认以及可消费的 revision，由 run state 中的 `RequirementConfirmed` 和 `RequirementRevision` 决定；产品审、技术审、开发和 QA 必须读取 run state 绑定的当前需求案，不得根据本文件中的静态文字推断确认状态。
