---

formal-gates 是一套完整的 AI 辅助开发工作流。它把一次开发从开始到结束都管起来：先讲清需求、确认怎么做，开发前让独立的"评审"先把关，开发时写、审、测三方互相隔离，开发后逐项检查，发现问题打回重改，最后把整轮结论固定存档。每一步都有标准做法，每一步都留记录，任何结论都能回溯。

**用它，你不需要先读懂下面的术语。** 装好之后，对你的 AI 说一句"帮我用 formal-gates 处理这次改动"，它会一步步引导你走完整个流程：问清你的需求、把方案讲给你确认、执行、最后给你一份结果报告。你只需要回答它的问题、在关键处确认。下面的内容是讲它内部怎么工作，给想了解的人看。

```text
用户
  │
  ▼
主代理（你的 AI，负责编排）──► 记录（.gates/）
  │
  ├─► 开发代理   独立会话 · 只拿需求 + 改动
  ├─► 审查关卡   独立会话 · 只看完整改动
  └─► 测试代理   独立会话 · 真实执行已批准用例
```

一句话：把"写的人""审的人""测的人"互相隔开，谁都看不到对方的思考过程；每一步的结论都存档，最后压成一份不依赖任何对话记忆的总结。

## 为什么需要它

同一个 AI 既写代码、又检查、又测试自己写的东西，会有两个毛病：

- **自己审不出自己的错。** 检查的人和写的人共享同一份记忆，AI 可以用"我写的时候就是这么想的"来搪塞，而不是只看改动本身——该发现的错就这样漏掉了。
- **不留记录。** 没有独立的检查，也没有可查的记录。一次对话结束，当初为什么这么做、检查结果如何、为什么通过，全都丢了。

formal-gates 用一套覆盖全过程的流程回应这两个问题：

- **动手之前**：先讲清需求、确认方案，让独立的评审先过一遍，把"什么算对"定下来。
- **开发之中**：写代码的人与检查的人完全隔离，只按已确认的需求做，每一步都有版本库记录。
- **开发之后**：真实测试、逐项审查，最后把结论固定成一份不依赖任何对话记忆的存档。

检查环节在互相看不到的独立会话里进行：审查者只拿到需求原文和改动的 diff（零上下文），看不到写代码时聊了什么，只能就事论事。CLI 是唯一记录，封板（把整轮结论固定成存档）时不依赖任何人的记忆。

## 特性

- **覆盖完整流程** —— 需求确认、拆分与路线、开发前评审、测试设计、开发、快照、独立审查、返修、封板，一步不缺、每步留记录。
- **先讲清需求再动手** —— 开发前主代理会一个决策一个决策地问清楚，把整合后的完整方案给你确认，你确认了才继续。
- **默认提醒一次** —— 主代理收到内容修改请求时默认提醒一次：若需走 formal-gates 流程，可直接提出。大/复杂需求在默认提醒之外额外强调一次（检测到复杂需求，建议走 formal-gates 流程）。主代理不会自行触发，也不会反复提及。你明确要求时才进入正式流程，在正式流程内再决定完整程度：full、custom 或 lightweight。
- **先定"什么算对"再写码** —— 开发前先把要验证的行为写成用例（真实执行的），独立评审通过才动代码；之后没变的结论直接保留，不必重测。
- **写、审、测互相隔离** —— 三个角色在互相看不到的独立会话里工作，审查者只看需求和改动本身，无法被写码时的记忆影响。
- **快照钉住进度** —— 实现完成后在版本库里钉一个不可变标记，后续所有审查只针对这个标记，不随临时改动漂移。
- **审查关卡即文件** —— 每一道独立审查关卡（本项目里叫"门"）就是一个 Markdown 文件，文件名就是门的名字。想加就加、想删就删，想改审查逻辑就改文件。
- **返修与继承** —— 发现问题打回重改；没受影响的通过结论直接继承，需要重跑的关卡每次都看**完整改动**，测试执行会把已批准用例在新快照上重新跑一遍。
- **CLI 是唯一记录** —— 运行期间只有一份临时状态，结束只留一份不可变存档；不复制项目文件，版本库本身就是全部真相。
- **原生版本库** —— Git / SVN / P4 直接驱动快照与对比；没有版本库的项目不进正式流程。

## 正式流程：从需求澄清到封板

你的改动请求会先走**受理**，然后进入正式流程。**正式流程共九个阶段**（1–9），受理在正式流程之前。

> **整套流程仅在你主动要求时启用。** 主代理不会自行触发：收到内容修改请求时默认提醒一次（若需走 formal-gates 流程，可直接提出），大/复杂需求额外强调一次（检测到复杂需求，建议走 formal-gates 流程）；你明确要求时才进入正式流程。九个阶段的正式流程较为繁重，原因在于每一步都设有门禁与记录；只想留记录的轻量任务可走轻量路线（start → 需求登记 → Seal，不验证只留记录），无需九个阶段。

每个阶段都有标准做法、明确的执行者、和留存的记录。下文里"主代理"指你的 AI 编排者。

### 受理：讲清需求、确认方案（正式流程之前）

**做什么**：只有在你明确要求走正式流程时，受理才开始。主代理先检视现状，然后一个决策一个决策地问清楚需求细节（一次一个，用大白话讲清每个选择的后果），再把整合后的完整方案讲给你听，等你明确确认。确认后评估工作量，由你决定是否进入正式流程（是 / 否）；路线 full / custom 在正式流程内、拆分决定之后确认，lightweight 不经拆分决定与路线选择。平时收到内容修改请求，主代理默认提醒一次（若需走 formal-gates 流程，可直接提出）；大/复杂需求在默认提醒之外额外强调一次（检测到复杂需求，建议走 formal-gates 流程）。
**谁来做**：主代理直接做，不需要独立代理。
**留什么**：已确认的需求，作为后面一切判断的依据。
**一句话**：所有请求默认提醒一次、你可直接提出走正式流程；大/复杂需求额外强调一次；你明确要求时才走正式流程，并在流程内用 full / custom / lightweight 决定完整程度（见阶段 3）。

### 1. 启动

**做什么**：选定仓库用的版本库类型（Git / SVN / P4），固定它的基线，登记本次需求与相关文档。没有版本库的项目不进正式流程。
**谁来做**：主代理通过 CLI 启动一次正式 run。
**留什么**：这次 run 的临时状态文件，以及固定的基线。

### 2. 登记需求

**做什么**：把受理阶段已确认的需求正式登记进流程，作为后续一切判断的依据；需求有修改时，相应调整测试用例（没受影响的不动）。
**谁来做**：主代理通过 CLI 登记。
**留什么**：已确认的需求与配套文件绑定进流程状态。

### 3. 决定要不要拆分、流程跑多完整

**做什么**：先决定工作是否**拆分**（把大任务拆成几个独立部分、各自开发后合并审查——只有很大的任务才需要，通常不必拆）。然后决定流程的完整程度：**full**（完整测试 + 全部审查关卡，最为全面、也最为繁重）或 **custom**（自行选择——例如仅选择测试、或仅选择部分关卡；至少选择一项，且不能全选，全选即为 full）。若 full 过于繁重，可用 custom 自行缩减范围。**lightweight**（只留记录、不验证）不走拆分决定与路线选择：它在 start 时声明（`workflow start --route lightweight`），start → 需求登记 → Seal 三步直达，封板标注「本 run 未经任何验证」。
**谁来做**：主代理给出建议，你拍板。
**留什么**：拆分决定与选择写进流程状态，之后沿用。
**一句话**：先决定怎么切，再决定审多严。

### 4. 开发前：独立评审 + 定"什么算对"

**做什么**：开发前先过两轮独立评审。第一轮看"需求合不合理"，第二轮看"方案够不够简单、能不能开发"；发现的问题按严重程度分级，交给你逐项拍板。开发前还要把要验证的行为写成测试用例（真实执行的），独立评审通过后，"什么算对"在写码前就定死了；结构层面的检查留到开发后，由独立代理读代码设计。
**谁来做**：每轮一个全新的独立评审员；主代理把发现项转达给你拍板。
**留什么**：已拍板的发现项，和已批准的测试用例。
**一句话**：写码之前先审"该不该做、够不够简、什么算对"。

### 5. 开发

**做什么**：开发代理在独立会话里按已确认的范围实现，与所有评审员完全隔离；新增或改动的交付路径先加入版本库，返回前核对从基线到当前的全部改动，交付前自己先测一遍。
**谁来做**：独立的开发代理会话，与评审员互不可见。
**留什么**：实现本身进入版本库，成为后续快照与对比的内容。

### 6. 固定快照

**做什么**：实现完成后，在版本库里钉一个不可变标记（git 里就是一个 commit），记录这一步对应的版本。
**谁来做**：主代理通过 CLI 记录。
**留什么**：不可变快照。后续所有审查只针对这个快照，不用工作区的临时状态，保证结论可复现。

### 7. 开发后审查

**做什么**：测试与各道审查关卡并行。测试只跑已批准的用例；每道关卡（`gates/` 目录下的文件，一个文件一道门）各自用全新的独立会话看完整改动，互不干扰。结果经主代理核对后记录为 PASS / FAIL。
**谁来做**：独立的测试执行 + 每道关卡一个全新的独立评审员。
**留什么**：关卡结论与测试结果，经主代理核对后记录。
**一句话**：每一道关卡都用全新会话面对同一份完整改动，谁也不能靠记忆混过去。

### 8. 返修

**做什么**：出现测试失败或 P0/P1 问题（必须修复的严重问题）时，整轮退回修复（同一轮的 P2/P3 小建议一并处理）。只有 P2/P3 小建议时同样要修，不是不用管：三轮预算内直接修、不问你也不重新审查，预算用尽后才把建议摆出来由你决定（开发前的产品/技术审里，P2/P3 建议始终逐条由你拍板）。没受这次修复影响的通过结论会直接继承；需要重新运行的关卡，每次看的都是**完整改动**（从开始到当前的全部），不是只看出问题的那一小段；测试执行会把已批准用例在新快照上重新跑一遍。最多三轮自动审查，用尽后每次修复需要你明确授权。
**谁来做**：主代理固定修复前的标记、派开发代理修复，然后重新快照并重审。
**留什么**：修复改动与新的快照；修复前的版本留作继承判断的依据。
**一句话**：小修不重测没变的东西，大改走独立判断。

### 9. 封板

**做什么**：所有必需结果通过后，把整轮结论固定成一份不可变存档，清掉临时状态。有还没完成的结果会卡住封板；运行出错的需要你手动跳过或重试；测试失败或 P0/P1 必须先修复，除非你明确授权跳过。
**谁来做**：主代理汇总并确认当前版本库标记。
**留什么**：一份 `.gates/results/<run-id>.json` 不可变存档——哪几道关卡通过、每个发现项的位置与严重级别、测试结果。之后任何人打开仓库都能看到这一轮发生了什么。
**一句话**：封板之后，这一轮的结论不依赖任何人的记忆。

### 进阶：任务拆分与总任务

默认一个请求按一次 run 处理。过大的工作可以按依赖、职责和风险拆成几个独立部分，各自在自己的工作区开发；一个"总任务"保留原始基线、完整需求和选择，负责对合并后的结果做整体审查。拆成两个及以上时，会自动附加合并关卡与合并测试。要不要拆、怎么拆，在阶段 3 由你决定。

### 一个端到端的例子

假设你想让 AI 给项目加一个"登录失败自动重试"功能：

- **受理**：主代理先问你几个问题（重试几次、隔多久、要不要记日志），把方案讲给你听；你确认后选择走正式流程。
1. **启动**：在仓库里启动一次正式 run。
2. **登记**：登记这条需求。
3. **拆分与路线**：主代理建议这条需求不用拆（理由存档），你确认走 full。
4. **开发前**：独立评审员看需求和方案，发现项交给你拍板；测试用例先写好"重试三次仍失败要报错"这类并获批。
5. **开发**：开发代理实现，改动进入版本库。
6. **快照**：钉一个不可变提交，后续审查只看它。
7. **审查**：测试跑已批准用例，各道关卡用全新会话看完整改动。
8. **返修**：如有测试失败或严重问题，打回修复、重新快照再审。
9. **封板**：全部通过，压成一份存档，这一轮完成。

## 示例产物

**一道审查关卡（门）** 是 `gates/` 下的一个 Markdown 文件，文件名就是门 ID。加一道门 = 写一个文件、重新安装：

```markdown
# 命名门（示例）

审查改动中的命名与可读性，只报告含义模糊或误导的标识符。每个发现项给出
仓库内相对位置。P0/P1 阻断通过，P2/P3 仅作建议不阻塞。
```

发现项按严重程度分级：P0/P1 是会阻断通过的严重问题，P2/P3 是仅建议、不阻塞的问题。

本仓库默认预置两道门（均位于 `gates/` 目录，一个文件对应一道门）：

- **复杂度门** —— 判断实现是否"足够且最简"：新增的抽象、文件、类型、状态或配置均须能归于现有能力，若无归属可寻则属过度设计。
- **实现质量门** —— 从四个并列维度审查实现质量：需求是否被完整覆盖、实现是否偏离应有设计语义、架构与耦合（模块边界、职责归属、依赖方向、解耦与可维护性，与其他维度同权重）、正确性与可维护性（含测试质量、死代码、可观察的性能退化）。

此外，**合并门**在拆分（分片 ≥ 2）场景下自动附加，审查合并引入的变更（冲突解决、跨切片接缝）与跨切片架构。

**封板后**，这一轮的结论固定成一份不可变存档 `.gates/results/<run-id>.json`：哪几道门通过、每个发现项的位置与严重级别、测试结果。要查的时候打开看就行，不需要记任何字段名。

## 安装与卸载

### 从 release 安装（推荐）

不需要 Go 工具链。下载最新 release 的源码包，解压后在包内运行安装脚本（macOS/Linux 用 `install.command`，Windows 用 `install.bat`）。脚本会下载匹配当前平台的正式二进制、canary 与 SHA256 校验和，校验后组装本地包并调用同一个原生安装器：

```bash
./install.command --host claude --scope global
# Windows: install.bat
```

### 从源码构建（只读验证）

源码构建产物是候选 binary，只用于包验证和隔离 canary，不能执行安装、bootstrap、
卸载或 workflow 写入。正式安装统一使用上面的 release 引导脚本，由脚本把校验后的
binary 放到固定 stable launcher 后再进入唯一原生事务：

```bash
go build -o bin/formal-gates ./cmd/formal-gates
bin/formal-gates package validate --root .
bin/formal-gates canary portable --root . --format json
```

Windows 使用 `bin\formal-gates.exe`。`bin\formal-gates.exe` 是 Windows 资产：在
macOS/Linux 上不要试图运行它（会报 `exec format error`），请使用各自平台的
`bin/formal-gates`。

安装会把本包自带的宿主 hook 合并进对应配置：Claude Code 写 `~/.claude/settings.json`，Codex 写 `~/.codex/hooks.json`，Cursor 写 `~/.cursor/hooks.json`（项目级安装写所选项目下的对应文件）；DeepSeek Harness 全局安装写 `$DSH_HOME/cordis.patch.yml` 并挂载包内最小 Cordis 插件，项目级安装只装 skill 与 `AGENTS.md` 指令（DSH 只自动加载 home 级补丁）；ZCode 全局安装写 `~/.zcode/cli/config.json`，项目级安装只装 skill 与 `AGENTS.md` 指令（当前 ZCode 忽略项目级 hook 配置）。已有的非 formal-gates hook/插件行不会被覆盖；多个宿主共享项目 `AGENTS.md` 时，只有最后一个仍在使用该文件的宿主卸载才会清理 managed marker。

安装还会维护受理规则：Claude Code 使用全局 `~/.claude/CLAUDE.md` 或项目
`CLAUDE.md`，Codex 使用全局 `~/.codex/AGENTS.md` 或项目 `AGENTS.md`，Cursor 项目
使用 `.cursor/rules/formal-gates.mdc`，DeepSeek Harness 使用 `$DSH_HOME/AGENTS.md`
或项目 `AGENTS.md`，ZCode 使用全局 `~/.zcode/AGENTS.md` 或项目 `AGENTS.md`。Cursor 全局不创建规则文件，只保留现有运行时和
hook 集成。当前规则写在宿主指令区块 `<formal-gates:host-instructions:start>` 与
`<formal-gates:host-instructions:end>` 之间；重复安装会替换区块内容并把重复区块收敛为一个。
从旧版（包括旧 target/bin hook 或旧 marker）升级时，直接用 release 引导脚本加
`--force` 安装；唯一事务会把安装器拥有的旧 hook 迁移到固定 launcher，并收敛规则区块。

### 原生卸载

卸载使用相同的 host、scope 和 project 参数，并清理 formal-gates 运行时、安装器拥有
的 hook 条目和完整 marker 规则区块，同时保留区块外文档内容与其他 hook：

```bash
$HOME/.local/bin/formal-gates uninstall --host claude --scope global
$HOME/.local/bin/formal-gates uninstall --host cursor --scope project --project <project>
$HOME/.local/bin/formal-gates uninstall --host dsh --scope global
$HOME/.local/bin/formal-gates uninstall --host dsh --scope project --project <project>
$HOME/.local/bin/formal-gates uninstall --host zcode --scope global
$HOME/.local/bin/formal-gates uninstall --host zcode --scope project --project <project>
# Windows: %LOCALAPPDATA%\formal-gates\bin\formal-gates.exe uninstall ...
```

规则区块按 marker 删除，即使运行时目录已经不存在也不需要规则源码。

### 参数语义

- `--force`：目标已存在时替换它。
- `--skip-hooks`：只安装包，不改宿主 hook 配置（只有当 hook 配置必须逐字节不变时才用）。

## 使用方式

作为使用者，你只需要做三件事：

1. **安装** —— 按上一节把它装到你的 AI 宿主平台（claude / codex / cursor / dsh / zcode）。给对应 AI 宿主平台说一句"帮我安装 formal-gates"即可。
2. **让 AI 引导你走完整个流程** —— 装好后，对你的 AI 说"帮我用 formal-gates 处理这次改动"，它会引导你走完：问清你的需求、把方案讲给你确认、执行、汇报结果。你不需要记任何命令，也不需要先读懂本文里的术语。
3. **审阅结果** —— 每轮结果由主代理汇总给你：哪些关卡通过、哪些发现项需要处理、封板存档长什么样。你随时可以打开 `.gates/results/<run-id>.json` 查看这一轮的完整结论。

`formal-gates workflow ...` 命令由流程驱动者（你的 AI 代理）执行。

## 常见问题

**我需要先读懂这些术语才能用吗？**
不需要。安装后对你的 AI 说"帮我用 formal-gates 处理这次改动"，它会一步步引导你走完整个流程，你只需要回答它的确认问题。本文的术语是给想了解内部机制的人看的。

**formal-gates 是不是只是一个开发后审查/质检工具？**
不是。开发后审查只是正式流程九个阶段的第七步。完整流程还包括受理阶段的需求澄清与确认，开发前的拆分与路线、独立评审、测试设计，开发中的开发与快照，以及贯穿其后的返修与封板。本 README 对全流程各阶段等量介绍，审查只是其中一个环节。

**我开一个新窗口去审查不就行了，为什么要用 formal-gates？**
开新窗口解决"独立审查"这一点。formal-gates 提供的是完整流程：需求确认、独立评审、测试设计、开发、快照、独立审查、返修、封板，每次必走、每步留记录；返修时没变的部分继承，需要重跑的关卡仍看完整改动。

**和"AI 写完再让 AI 审"的 review bot 有什么区别？**
review bot 通常运行在生成代码的同一个上下文里，AI 可以用写代码时的记忆填补审查盲区。formal-gates 把实现、测试和审查放进互相看不到的独立会话，审查者只拿需求 + 改动，没有实现记忆可用，只能基于改动本身判断；同时留下一份 CLI 记录。

**formal-gates 什么时候会被触发？**
主代理不会自行触发：收到内容修改请求时默认提醒一次，若需走 formal-gates 流程，可直接提出；大/复杂需求在默认提醒之外额外强调一次（检测到复杂需求，建议走 formal-gates 流程）。你明确要求时才进入正式流程，受理阶段只决定是否进入正式流程（是 / 否）；跑多完整（full / custom）不是受理阶段选的，而是在正式流程内、拆分决定之后才确认；lightweight 不经拆分决定与路线选择，在 start 时声明。

**正式流程是不是很重？**
是。正式流程会派出多名独立评审员、真实执行测试，比普通开发消耗更多时间与 token。若 full 过于繁重，可在正式流程内选择 **custom** 自行缩减（不选择测试、或不选择部分关卡）；只想留记录的轻量任务可走 **lightweight** 路线（`workflow start --route lightweight` → 需求登记 → Seal，不验证只留记录，封板标注「本 run 未经任何验证」）；规模特别大的工作可采用**拆分**模式，拆分为若干独立部分并行开发、合并后整体审查。此外，审查关卡（门）可自由增删与定制——若某道门不合适，可删除或修改其审查逻辑，这同样会影响整体轻重。

**需要什么前置条件？**
从源码构建需要 Go 1.22+，并选一个宿主（claude / codex / cursor / dsh / zcode）。正式流程需要一个 Git、SVN 或 P4 仓库；无版本库的项目不进入正式流程。

**如何增加或删除一道审查关卡？**
新建或删除 `gates/<id>.md` 并重新安装即可。文件名就是门 ID，不需要改任何配置表。删除文件即移除关卡，数量不限。若要修改审查逻辑，修改门文件即可。

**审查结果一定是最终结论吗？**
不是。每个独立代理的结果只是候选输入：主代理在记录或展示前必须核对需求匹配、正常使用边界与结果格式；对失败或阻塞项还会独立复现其文档化路径再作判断。核对不通过就丢弃该结果。

**封板后留下什么？**
该 run 的整个临时目录被删除，只保留一份存档 `.gates/results/<run-id>.json`。它不保留提示词副本、证据图或详细状态树。
