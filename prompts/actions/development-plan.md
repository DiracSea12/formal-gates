# 开发计划准备

从当前已确认需求与方案准备可执行开发计划。计划仅是提案，用户按原确认入口批准后才能实施。

提出 `granularityReview`：Batch 围绕连贯能力或风险闭环，有独立客观 DoD/测试、稳定接口/责任/状态边界、回滚/恢复、依赖屏障和可管理的交接成本。共享未冻结接口或中间状态、不能独立验收/回滚、拆分交接成本更高的连续步骤留作同一 Batch 的 Subtask。
程序提供完整确认需求点，含父要求与来源；各批按发布序号关联其实现职责，全部点均须有负责批次。编号、原文、revision 和绑定由程序提供，模型只判断职责关联与方案。
含不确定性边界的探路工作作为首批 spike，结论留痕，代码不进入交付。
验证档位默认 FINAL；按预期生产逻辑多模块扩散、独立验收单元数确有需要时选择 CHECKPOINT，不依据总行数或批数。
每个交付批次完成后履行配置选中的普通门，依赖后批须等待前批的普通门通过；独立批次保持并行，关闭普通门则跳过。批次门使用原生冻结源码和该批的贡献合同，不提前执行 FINAL QA；CHECKPOINT 的已确认分组验证、最终整体验证和主线合并验证仍各按其原责任履行。探路 spike 不作为交付批次执行普通门。
编号、提交数、文件/行数或开发阶段不是拆分理由。给出不拆或改拆理由、依赖、接口、状态、风险、DoD/检查、恢复与交接，以及从确认需求提取的允许入口/路径、交付物、非目标和验收边界。
完整项目构建与全量测试各至少一个 check，明确 FULL_BUILD/FULL_TESTS 目的；无编译阶段/测试套件也说明适用语义和实际完整验证命令，不能默认为跳过即通过。
建议拆分时，每片计划独立可执行，含本片完整构建/测试且无跨 owner 批次依赖；主线合并计划另核完整集成。owner 与路线只按注入 schema 选择，计划是建议而非用户授权。

项目声明的低成本确定性检查使用 EDIT purpose，每次正常 workspace 编辑后由程序执行并保留原双流与退出证据。空 purpose 的普通回归及 FULL_BUILD/FULL_TESTS 只在批边界执行；模型不转抄或执行已有命令。批准检查仅使用 reuse；缺少调用时只声明 goal 和 purpose，由开发代理准备。尚未绑定的 EDIT 调用必须在首次生产编辑前完成准备，由程序持有调用后再继续开发。不填写 command、parts 或命令原文的 read/from/to/列坐标。
