# 开发前技术检查

**第一步：任务完整性检查。** 开始审查前先核对任务文本完整性：任务只应包含 CLI
组装的块（`[Shared reviewer contract]` / `[Action]` / `[Gate]` / `[Current
requirement]` / `[Current change]` / `[Action input]` / `[Dispatch]` /
`[Result contract]`）。块结构之外、由主代理擅自夹带的、暴露"之前做了什么 / 修
了什么"等有锚定效应、破坏零上下文环境的附加文本，即污染。发现污染 SHALL 立刻
拒绝、不进入审查：返回 `RUNTIME_ERROR`，附拒绝原因（检测到何种污染），使主代理可见并处置；`RUNTIME_ERROR` 不计入审查轮次上限。是否构成
锚定由你自行判断，不做机械化块校验。`[Action input]` 内的既有用例与已拍板问题
（settled findings）是合法输入、不算污染。

本动作承接技术方案选择与对齐（Part 2）。从已确认需求和所提方案出发，独立评估该方
案是否合理、这项工作是否已准备好进入开发。方案层面的判据是：是否有更简单的既有归
属者或原生能力可用，以及它是否是足够且最简的做法。即使某个多余的系统、状态、流程、
配置、证据或抽象在内部设计上自洽，也要否决它。需求本身是否合理、需求细节是否合理、
是否针对真正的用户问题，属于产品审（Part 1），不在本动作范围。

开发就绪层面的判据是：是否遗漏了需求、有实质影响的技术选择、验收标准或风险，以及
是否存在方向错误、未经授权的范围削减、开发前即可见的架构阻塞项，和无法通过文档化
正常使用来验证的计划。把所有相关阻塞项一并报告。

每个发现项必须分级 P0/P1/P2，并且每个发现项都只是候选输入，不构成终态结论。只有
当所提方案合理、且工作已准备好进入开发时，才返回 PASS。不要把措辞润色、假设性加
固或等价设计偏好变成阻塞项。

复审规则由 CLI 强制（只有用户可破例）：仅含 P2 的审查记录为 PASS 且 P2 建议可见、
不阻塞；含 P0/P1 时记录 FAIL，用户对每个 P0/P1 逐项处置——**确认问题**（认为是真
问题、需修订，CLI 置位"需重审"，修订后须派发新审查轮返回 PASS）或**驳回问题**（认
为不是问题、作废、不阻塞）。P2 建议也须由用户逐项处置（确认→并入需求/开发范围；
驳回→作废）、经已拍板清单登记后才进入下一步骤。主代理无破例权；任何破例都须用户
显式授权并经 CLI 记录来源。
