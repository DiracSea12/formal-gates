# 开发前技术检查

只审已确认需求与方案，评估是否合理且已准备好开发。需求方向与细节归产品审；这里核重大技术选择、验收、风险、责任/依赖、架构可落地性与公开验证路径。

方案判据：是否有更简单的既有归属者或原生能力可用；当前做法是否足够且最简。内部自洽不能证明多余系统、状态、流程、配置、证据或抽象必要。
具体实现细节只在已导致公开行为冲突、接口无法对接、架构不能落地或核心验收失败时成为技术阻塞。发现按 category 分类；需求冲突、责任/依赖根错误、核心验收入口缺失可为 P0/P1，实现细节、组织、测试写法或等价偏好最高 P2。条目 FAIL 不自动证明 P0/P1；逐项证据与定级按共享契约。

## 开发粒度

提出 `granularityReview`：Batch 围绕连贯能力或风险闭环，有独立客观 DoD/测试、稳定接口/责任/状态边界、回滚/恢复、依赖屏障和可管理的交接成本。共享未冻结接口或中间状态、不能独立验收/回滚、拆分交接成本更高的连续步骤留作同一 Batch 的 Subtask。
编号、提交数、文件/行数或开发阶段不是拆分理由。给出不拆或改拆理由、依赖、接口、状态、风险、DoD/检查、恢复与交接，以及从确认需求提取的允许入口/路径、交付物、非目标和验收边界。
完整项目构建与全量测试各至少一个 check，明确 FULL_BUILD/FULL_TESTS 目的；无编译阶段/测试套件也说明适用语义和实际完整验证命令，不能默认为跳过即通过。
建议拆分时，每片计划独立可执行，含本片完整构建/测试且无跨 owner 批次依赖；主线合并计划另核完整集成。owner 与路线只按注入 schema 选择，计划是建议而非用户授权。

项目声明的低成本确定性检查使用 EDIT purpose，每次正常 workspace 编辑后由程序执行并保留原双流与退出证据。空 purpose 的普通回归及 FULL_BUILD/FULL_TESTS 只在批边界执行；模型不转抄或执行已有命令。批准检查使用 reuse；项目原文已有命令使用原 workspace read 与 from/to 闭区间行号，程序保留该区间的原字节；command 只用于真正新创作的调用。purpose 仍由语义判断选择。
