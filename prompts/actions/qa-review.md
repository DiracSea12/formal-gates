# QA 审查

机械明确的准备和动作必须已经写入待审 case/shared-step 的有序 operations，或由精确
`<路径>_test.go::TestName` 引用完整指定。逐条核这些实际载荷与步骤、前提、oracle 的
对应性；缺执行动作、仅自然语言描述或不透明引用没有 operations 时，具体指出 case
缺口并判 FAIL，交原设计补齐和重新审查。执行者只能比较程序的真实收据，不能猜命令
或临时补动作。完整协议见 `references/qa-operations.md`。

对照已确认需求，以及 CLI 提供的已接受覆盖上下文，独立审查处于待定状态的候选 QA
用例。集合层面的发现项可以指出覆盖缺失或重复，而不必让一个本身有效的用例判为不通过。
结果契约由 CLI 以 [Result contract] 块注入，本提示词不重复其语义。

审查模式随用例 mode 而定：白盒用例的批准阶段读取实现——结构测试充分性依赖实现，
判断结构测试是否充分；黑盒用例保持零上下文——不检视生产实现、实现 diff、测试、开
发者解释、开发后结果或另一位审查者的结论。黑盒审查在 QA 隔离工作区中进行（从基线
创建、不含本次开发代码），以注入的当前需求文档为准。

测试准备按 `prompts/actions/qa-design.md` 的“测试准备可构造”规则核验：确认构造方法可照做，
不要求前置有公开生成入口或真实跑完前序流程，也不因手工构造正常可达前置否定用例。

检查这些用例是否定义了可观察的预期判据、黑盒被测操作是否使用文档化的公开步骤、是否停留在文档
化的正常使用和常见操作失误范围内，以及是否在直接拥有该行为的最低层验证每个行为。

**按流程时点核验入口。** 测试环境、fixture 和正常可达前置可按“测试准备可构造”规则
准备，不要求真实重跑前序流程。既有工具、构造方法和执行所需宿主能力须当前可用。
本次需求新增或修改的产品入口，在开发前依据已确认接口契约核对命令、参数、行为和
判据；不能仅因基线帮助或产物尚未包含该入口而判 FAIL。契约缺少执行所需的实质细节
仍是用例缺口。快照后的 QA 执行必须对真实产品验证入口并实际运行被测逻辑，不能用
构造的预期输出代替。若用例测试的正是宿主真实集成或派发，该能力仍须真实核验。

**每条用例固定核验六项。** 对每个尚未批准的 case，分别核验并在逐 CASE 判定依据中
体现：①被测入口及参数按上述流程时点核验（黑盒使用公开入口）；② setup/前置条件完整且操作顺序可达；③当前指定执行
环境确实具备用例要求的能力；④ procedure 能真实执行并留下逐用例证据；⑤ oracle 逐项
对应已确认需求，既不遗漏要求，也不加入需求未承诺的结果；⑥检查范围与声称相称——
步骤与判据实际验证的范围不得窄于用例声称覆盖的行为或验收点，只验证观察到的样例、
只挑字面输入或顺带绕开判据所含边界而宣称更广覆盖的用例，其通过不能代表声称范围成
立，属用例缺陷；修正方式是把步骤/判据扩到声称范围，或把声称范围收窄到实际验证的
范围并交由集合级覆盖判定补齐其余。任何一项不成立，该 case
不得 PASS。不能用其他 case、现有测试、开发者说明或“执行时再处理”补足。

若被测目标就是真正创建全新的 Codex task、使用特定已登录宿主能力或调用其他外部执行者，
必须先确认本次 QA 执行环境实际提供该能力，并能保存任务身份与交互证据；只有当前对话、
shell 或普通子进程不等于新 Codex task。能力不存在时判定用例不可执行，不得给通用 PASS。
若验证的就是 fresh reviewer 的真实派发或身份捕获，必须实际派发并取得相应结果与证据；
若审查结果仅作其他被测逻辑的前置数据，可按设计规则构造，不能冒充真实派发的观测。

oracle 还必须核对流程时点和授权前置。例如只有在轮次上限耗尽后才允许的额外授权，不能
被写成提前授权也应成功。对被测场景要求 Operator 故意提交虚假声明、伪造证据或谎报已核验的
对抗性场景，按项目边界判为范围外/不可作为正常范围阻塞项；不得要求程序实现自然语言
测谎或语义证明器，也不得把这种 case 批准为正常黑盒保证证据。

**先查真实阻塞，再查表达细节。** 审查的第一优先级是确认用例能从给定前置条件出发，
通过文档化的公开入口实际执行，并能用外部可观察结果判定成败。对每个待审黑盒用例，
按上述流程时点，逐一核对既有被测命令与参数的公开文档/帮助，或新增入口的已确认接口
契约，并核对
fixture/场景与隔离环境前置能否按写明的构造方法建立；若既有入口不存在、新增入口契约
不完整或前置无法按步骤建立，
这是用例可执行性阻塞，必须直接判 FAIL 并指出缺失的入口或前置，不得把问题留给执行代理
“到时再看”。白盒用例同样先确认其绑定的已有或新增结构测试确实能建立并运行。

集合层面的覆盖充足性按此判定：某验收点只有正向路径用例、没有任何失败/误用/边界类
具体用例（且无既有强判据用例覆盖该层面），是覆盖缺失，构成阻塞级发现，不是 P3 建
议。审查时间按以下顺序投入：①不可执行、需求核心无法验证、公开入口与 oracle 矛盾；②真实
的范围内行为缺陷和关键验收点遗漏；③才是边界覆盖和重复性。措辞、命名、排版、字段
顺序偏好、可等价表达的判据、已被其他用例直接覆盖的重复比对，只能作 P3 建议，不得
阻塞 PASS，也不得因此开启新的审查-修复轮。发现同一根因影响多个用例时合并说明根因
和受影响条目，完成根因核对后停止继续雕琢同类变体；不要为了证明“更完整”而增加新
用例或要求无关的额外机制。

**不得把文字闭合作为通过条件。** 用例的描述、步骤和 oracle 即使彼此写得完整，也
不能替代对真实入口、公开参数、fixture、harness 前置和用户可观察结果的核验。先把
实际阻塞和行为缺陷说清楚；发现这些问题后直接判定并给出影响，不得继续围绕同一问题
补词、改名、补字段或追求形式上的文本闭合来拖延或掩盖结论。

**必须逐条检查步骤的可通性。** 对每一条黑盒用例，按其原文步骤逐项核对：公开入口、
命令或调用、参数、输入、fixture/harness 前置、操作顺序和证据留存方式是否按上述时点有据、
能够建立并能走到预期判据；任一关键步骤无法照做或无法观察结果，都必须直接判 FAIL，
写明卡在哪一步以及缺少什么。不得因为描述和判据在文字上互相闭合，就跳过步骤可通性
检查或把问题推给黑盒执行阶段。

白盒审查同时独立判断每条 case/shared-step 关联的 `files` 与明确测试引用是否属于测试
材料，是否改变了生产代码、运行配置、生产依赖或构建输入。读取签发的 `reviewBase`、
`reviewArtifact` 原始差异以及实际候选代码/配置；PASS 的逐项 reason 须给出该判断的实际依据。
声明为测试不是归属证明；无法确定或实际属于生产输入时，该原条目判 FAIL 并给出具体理由。
隔离 artifact 只是待审材料，尚未通过这次独立审查时，不表示 test-only、生产等价、可排除质量门或可提升。

**白盒独立审查覆盖与真实断言。** 先独立列出应验证的行为、分支与 oracle，再检查绑定测试
的输入、实际断言和对应覆盖。可批准有效已有测试；错误断言或缺口仍须修正或补测，不能
凭测试名、全绿、覆盖率或开发者声明批准。黑盒不得以运行已有套件替代公开入口实跑。

共同说明只核验一次，按原未继承共享说明顺序返回 status 和 reason，身份由程序回填；每条 case 的特殊前提、差异
操作、证据、oracle 与覆盖仍独立判断。未变且不受影响的审批继承；共同说明变化时重新
检查全部引用者，不抽样、不按组背书。脚本新增或修改时核对准备、真实调用、取证和断言，
关键失败判据用已知错误样例确认可报错；同版本未改脚本不重新完整审批。

**覆盖充分性判定（逐验收点，不是逐需求点）。** 先把每条需求拆成它承诺的每个可观察
行为与验收点：正向生效、失败路径或不得误报、边界/中间态、以及「本次改动可能破坏的
既有文档化正常使用行为是否仍被覆盖」的回归面——凡对应到不同的可观察行为、或需要不
同公开步骤才能验证的角度，都是独立验收点，不得合并。再逐点核对是否有用例直接覆盖。
若同一需求承诺多个可独立观察的行为，却被一条用例顺带捆绑、只在步骤或预期判据里一笔
带过，或缺少某个角度的独立验收点，即构成覆盖遗漏，判 P1 阻塞、必须补用例。只有同
一确定性规则、同一公开入口、同一可观察判据在不同输入上的重复，才属于不必要的重复
覆盖、不要求补。当直接自动化覆盖已经验证同一条确定性规则、且更高层没有引入不同的
正常使用行为时，缺少更高层的重复覆盖不构成阻塞项。

**深浅判定。** 用例的预期判据若空泛到无法区分对错（如只有「正确/符合预期」而无
具体可观察物），或步骤含糊到无法照做（类别名引用、未指明入口与操作），判该用例
FAIL、要求改写为具体判据——浅覆盖等同未覆盖。同一验收点的典型/边界/错误三个层
面，已有强判据覆盖的层面不要求重复。

判定前先做一次“能不能跑、跑了能不能判”的快速核验；只有这两项成立后，才检查是否
需要补充细节。不要因为用例没有写出所有可想象的字段、变体或重复的机械比对，就把一个
已经能验证核心验收点的用例判为 FAIL。

不要在本动作中设计替代用例。逐用例的 FAIL 决策直接使该轮 FAIL。

**逐条审查义务（未批准条目）。** 对候选集内**尚未获得批准**的用例（本轮新增或
修改的条目），必须逐条独立审查：逐条完整读取该用例的描述、步骤与预期判据原文，
逐条给出判定；禁止以抽样、模式扫描、批量判读或“保持既有状态”式的合并背书替代。
已批准且未受影响的用例和共同说明由程序沿原签发可继承事实保留，不要求模型重列。返回 caseDecisions/sharedStepDecisions 数组仅覆盖签发集合中未继承项，按原列表过滤后的顺序逐项填写 status 和 reason；不填写 CASE 标识、ID 键或继承占位。来源与验收点仍必须各自独立审查，不能因用例继承自动背书覆盖完整性。实际缺陷保留真实 FAIL 与原证据，不因为继承内容而忽略。

集合层 finding 的 CLI 严重度取值为 P1/P2/P3；若定为 P1，必须为该 finding 单独给出非占位定级理由、需求、正常
执行路径、延期影响、可定位证据，以及范围/严重度/因果/复现核验；CASE 的 FAIL 或整批
FAIL 不能自动推出 finding 为 P1。缺少这些字段的候选只产生无效结果回执，不进入 QA
review 的权威投影。

集合级可选 P2/P3 是结构化、非阻塞建议，不把总体 PASS 改为 FAIL。每条建议明确对象和
建议，供 CLI 分配稳定 suggestion ID。建议判断按签发顺序登记采纳、延期或不采纳及理由，程序装配实际 ID，且覆盖
校验通过后可冻结；不强制改用例。采纳改变共同路径、可执行性或验收含义时重审受影响
部分。真实漏测、不可执行或预期错误仍阻止用例获批，不能用可选建议处置绕过。门审及
产品/技术审的发现项规则保持不变。
