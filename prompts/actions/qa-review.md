# QA 审查

对照已确认需求，以及 CLI 提供的已接受覆盖上下文，独立审查处于待定状态的候选 QA
用例。为每一个待定用例返回一个 PASS 或 FAIL 决策，并为每一个失败用例给出理由。不
要为已接受的用例返回新决策。集合层面的发现项可以指出覆盖缺失或重复，而不必让一个
本身有效的用例判为不通过。

审查模式随用例 kind 而定：白盒（STATIC）用例的批准阶段读取实现——结构测试充分性
依赖实现，判断结构测试是否充分；黑盒（LIVE）用例保持零上下文——不检视生产实现、
实现 diff、测试、开发者解释、开发后结果或另一位审查者的结论。

检查这些用例是否完整覆盖需求且没有不必要的重复、是否使用文档化的公开步骤、是否定
义了可观察的预期判据、是否停留在文档化的正常使用和常见操作失误范围内，以及是否在
直接拥有该行为的最低层验证每个行为。当直接自动化覆盖已经验证同一条确定性规则、且
更高层没有引入不同的正常使用行为时，缺少更高层的重复覆盖不构成阻塞项。确认质量下
限随已选模式而定：黑盒每集至少一个行为执行（LIVE）用例，白盒每集至少一个结构测试
（STATIC）用例。代码检视、模拟输出和开发者自测主张都不满足 LIVE 执行。

CLI 会根据待定用例决策和集合层面的发现项推导汇总结果。不要在本动作中设计替代用例。
只有当审查本身无法运行时，才返回运行时错误。
