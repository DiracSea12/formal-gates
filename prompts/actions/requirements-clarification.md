# 需求澄清

本动作由主代理以交互方式完成正式受理登记：把受理阶段已对齐的完整需求与技术方案直
接写入本 run 当前绑定的唯一正式需求文件，在最终确认前完成结构预检、计算精确 revision，
再向用户呈现该文件全文与精确 revision 并单独请求最终确认；用户要求修订时继续更新同
一文件、重新预检并重新呈现全文与 revision。不得只在聊天中给草稿、摘要或条目清单，也
不得另建未绑定的草稿文件。取得用户最终确认后才返回 PASS。本动作不再承担深度澄清内
容——需求细节澄清并入产品审（Part 1），技术方案选择与对齐并入 start-readiness
（Part 2）；主代理对明显缺口仍提问（快速澄清兜底），深度需求审由产品审在确认后以发
现项逐项完成。

先检视仓库事实与已确认记录，不让用户重复提供可直接查明的事实。沿用仍适用的用户
决定；只有未决事项会实质改变范围、公开行为、验收标准或主要架构时才提问。逐维核对
目标、场景、范围、默认值、失败路径、验收、约束与取舍，不把维度清单变成必问清单。
一次只问一个有实质影响的决策，用日常语言讲清背景与选项。范围内的次要实现细节自行
决定，不为假设性场景新增问题；无剩余实质缺口时记录“无剩余缺口”，结束澄清。

只把用户简述、明确决策、已批准的需求记录和当前唯一事实来源的规格说明当作需求证据。
既有实现、测试、任务勾选框、旧流程输出和长期记忆只用于确立仓库事实与既有约束，不能
授权改变范围。记录实际问答及“考虑过但放过”项的依据，不把自主实现选择记成“已对齐”。
用户确认过范围或路线，不等于确认了其他实质决定；推荐或默认选择不替代本动作规定的
正式需求全文与精确 revision 确认。PASS 记录只写用户实际确认的内容。

保持只读：不要准备开发、不要派发工作者；除更新本 run 已绑定的唯一正式需求文件外，
不修改任何项目内容。所有问题解决之后，先把完整需求与决策写入该文件并运行结构预检；
预检失败时必须留在本动作内修正，不能请求确认。预检通过后呈现该文件全文和精确
revision，并等待用户明确确认。该文件是本 run 的验收输入与事实来源，也是后续产品审
（Part 1）的输入对象。最终确认前用不带 `--confirmed` 的 `workflow requirement` 校验并
绑定待确认 revision；若用户修改已绑定内容，按现有修订规则同时声明 `--meaning changed`
后再预检。用户确认所呈现的同一 revision 后，本动作返回 PASS；编排层必须先用
`record-action` 记录该 PASS，再对同一 revision 执行
`workflow requirement --confirmed`；单一结构化正式需求会在该确认中原子冻结保证
envelope（`--activate-guarantee` 作为兼容写法仍可接受）。不得在 PASS 记录前执行确认命令，
因为正式确认入口以本动作 PASS 为前置。返回契约由 CLI 以 [Result contract] 块注入，本提
示词不重复其语义。

**登记集（RQ-011，进入开发后对主代理的写豁免范围）。** 随本 change 登记承载需求与
方案的文档：逐文件按"改该文件是否改变该 change 的需求/方案"判定，是 → 登记，否
（任务/进度/执行/跟踪类文档）→ 不登记。格式无关，不按文件名/后缀/位置识别。登记
清单须提出给用户确认后生效；登记集 = RQ-011 主代理豁免集 = 需求修订作用域，三者同
一。审查通过、进入开发后，已登记文档被修改即走需求更改流程（CLI 硬阻断、回需求澄
清重新登记）。

## 项目边界

项目边界同 `prompts/reviewer-base.md`：只保证文档化正常使用与常见操作失误。除非
用户明确要求加固，对抗性输入、恶意编辑、手工改写状态、权限或不可变文件失败、不
受支持的平台，以及其他人为构造的攻击或违规，不引入对应澄清项或机制，也不引出新
需求。
