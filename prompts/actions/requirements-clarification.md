# 需求澄清

主代理按 SKILL.md 的受理规则完成需求澄清、唯一需求文件预检、全文与精确 revision 展示及用户确认。
这是交互受理，不是原生子代理动作，不生成工作者 PASS、模型结果 schema 或工具调用记录。
需求与重大技术选择先澄清；后续产品审、技术审各自独立检查并返回发现项。

先检视仓库事实与已确认记录，不让用户重复提供可直接查明的事实。沿用仍适用的用户
决定；只有未决事项会实质改变范围、公开行为、验收标准或主要架构时才提问。逐维核对
目标、场景、范围、默认值、失败路径、验收、约束与取舍，不把维度清单变成必问清单。
一次只问一个有实质影响的决策，用日常语言讲清背景与选项。范围内的次要实现细节自行
决定，不为假设性场景新增问题；无剩余实质缺口时记录“无剩余缺口”，结束澄清。

只把用户简述、明确决策、已批准的需求记录和当前唯一事实来源的规格说明当作需求证据。
既有实现、测试、任务勾选框、旧流程输出和长期记忆只用于确立仓库事实与既有约束，不能
授权改变范围。记录实际问答及“考虑过但放过”项的依据，不把自主实现选择记成“已对齐”。
用户确认过范围或路线，不等于确认了其他实质决定；推荐或默认选择不替代本动作规定的
正式需求全文与精确 revision 确认。确认记录只写用户实际确认的内容。

除更新本 run 已绑定的唯一正式需求文件外，不修改项目内容，不准备开发或派发工作者。
通过 `workflow start --requirement <path>` 和首次 `workflow drive` 绑定并预检文件；
预检失败先修正。预检成功后，以 `workflow submit` 的 `REQUEST` 提出 `confirm-requirement`；
完成上述全文与 revision 展示，等待用户明确确认；取得确认后，用该 Ask 的 requestId、token、digest
提交 `DECIDE`。不得在用户确认前提交确认决定。执行参数和事件字段以 `references/engine-regular.md` 为准。
进入开发后的需求或方案修改走现有正式变更流程，不以需求登记授权修改其他项目内容。

## 项目边界

项目边界：只保证文档化正常使用与常见操作失误。除非
用户明确要求加固，对抗性输入、恶意编辑、手工改写状态、权限或不可变文件失败、不
受支持的平台，以及其他人为构造的攻击或违规，不引入对应澄清项或机制，也不引出新
需求。
