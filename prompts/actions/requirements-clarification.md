# 需求澄清

本动作在受理阶段、正式流程启动之前由主代理以交互方式进行，收窄为纯受理登记：把受
理阶段已对齐的完整需求与技术方案写入需求文件，取得用户最终确认后返回 PASS。本动
作不再承担深度澄清内容——需求细节澄清并入产品审（Part 1），技术方案选择与对齐并
入 start-readiness（Part 2）；受理阶段主代理对明显缺口仍提问（快速澄清兜底），深
度需求审由产品审在确认后以发现项逐项完成。

对明显缺口仍提问：拷问并对齐所有有实质影响的细节，不留任何需要猜测或假设的余地。
不区分产品问题还是技术问题：目标动机、用户场景、范围边界/非目标、细节与默认值、
异常与失败路径、验收标准、约束与取舍、风险——只要实质且含糊，就逐维追问到明确。
拷问不是连珠炮：仍然一次只问一个有实质影响的决策，用日常语言讲清背景与选项。

自己检视仓库事实，而不是让用户来提供。只把用户的简述、明确决策、已批准的需求记录
和当前作为唯一事实来源的规格说明，当作需求证据。既有实现、测试、任务勾选框、旧的
流程输出和长期记忆都不足以授权改变范围；它们只能用于确立仓库事实和既有约束。

记录拷问轨迹：问了什么、用户答了什么。记录"考虑过但放过"的项——放过须有理由，且
不构成实质猜测。返回 PASS 之前自检"是否还有任何有实质影响的细节是我不得不猜的"；
有就不返回 PASS。次要实现细节自行决定，除非它们变得有实质影响。

不得跳过澄清：除非确无会实质改变范围、验收、公开行为或架构的决策需要澄清（此时记
录"无剩余缺口"），否则返回 PASS 之前必须已经与用户完成过澄清问答，并将对齐结论总
结呈现给用户让用户最终确认。PASS 记录只写用户实际确认的内容。用户确认过范围或路
线，不等于确认了其他决定；任何会改变用户看到的行为、验收标准或架构方向的决定，都
必须先问用户，不得自己定了再记成"已对齐"。

保持只读：不要准备开发、不要派发工作者；除写入需求文件外，不修改任何项目内容。所
有问题解决之后，呈现完整整合后的需求与技术方案，并等待用户明确确认——"确认"指呈
现完整整合需求与技术方案并取得用户最终确认。取得确认后，把整合后的完整需求与决策
写入需求文件（受理阶段、正式流程启动之前，作为本 run 的验收输入与事实来源），该
文档也是后续产品审（Part 1）的输入对象。只有在取得用户最终确认之后才返回 PASS；
返回契约由 CLI 以 [Result contract] 块注入，本提示词不重复其语义。

**登记集（RQ-011，进入开发后对主代理的写豁免范围）。** 随本 change 登记承载需求与
方案的文档：逐文件按"改该文件是否改变该 change 的需求/方案"判定，是 → 登记，否
（任务/进度/执行/跟踪类文档）→ 不登记。格式无关，不按文件名/后缀/位置识别。登记
清单须提出给用户确认后生效；登记集 = RQ-011 主代理豁免集 = 需求修订作用域，三者同
一。审查通过、进入开发后，已登记文档被修改即走需求更改流程（CLI 硬阻断、回需求澄
清重新登记）。

## 项目边界

项目边界同 `prompts/reviewer-base.md`：只保证文档化正常使用与常见操作失误。除非
用户明确要求加固，对抗性输入、恶意编辑、手工改写状态、权限或不可变文件失败、不
受支持的平台，以及其他人为构造的攻击或违规，不引入对应澄清项或机制，也不引出新
需求。
