# 需求澄清

本动作在受理阶段、正式流程启动之前由主代理以交互方式进行。既要对齐用户想要的
结果，也要对齐每一个会实质改变公开行为、验收或架构的技术选择。一次只问一个有
实质影响的决策，并根据用户的回答和实际请求调整下一个问题；不要使用固定问卷。
本动作只做澄清、确认并把整合后的完整需求写入需求文件，不执行任何后续流程步骤
的登记或内容核对。

自己检视仓库事实，而不是让用户来提供。只把用户的简述、明确决策、已批准的需求
记录和当前作为唯一事实来源的规格说明，当作需求证据。既有实现、测试、任务勾选
框、旧的流程输出和长期记忆都不足以授权改变范围；它们只能用于确立仓库事实和既
有约束。

只问那些答案会改变范围、验收、公开行为或必需架构边界的问题。用日常语言解释每
个问题：说明真实的用户问题、用户可见的后果、可选项、推荐答案，以及它为什么重
要。如果你做不到这一点，只能依赖内部术语或未加解释的抽象，那你还不具备提出这
个问题的资格。不要把实现提案藏在澄清问题里。

不得跳过澄清：除非确无会实质改变公开行为、验收或架构的决策需要澄清（此时记录
"无剩余缺口"），否则返回 PASS 之前必须已经与用户完成过澄清问答，并将对齐结论
总结呈现给用户让用户最终确认。PASS 记录只写用户实际确认的内容。用户确认过范围
或路线，不等于确认了其他决定；任何会改变用户看到的行为、验收标准或架构方向的
决定，都必须先问用户，不得自己定了再记成"已对齐"。

返回之前检查整条相关需求链，让相关缺口被一并识别，同时仍然一次只问一个有实质
影响的问题。次要实现细节自行决定，除非它们变得有实质影响。保持只读：不要准备
开发、不要派发工作者；除写入需求文件外，不修改任何项目内容。所有问题解决之后，
呈现完整整合后的需求与技术方案，并等待用户明确确认——"确认"指呈现完整整合需求
与技术方案并取得用户最终确认。取得确认后，把整合后的完整需求与决策写入需求文
件（受理阶段、正式流程启动之前，作为本 run 的验收输入与事实来源）。只有在取得
用户最终确认之后才返回 PASS。
