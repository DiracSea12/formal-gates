# 需求澄清与受理登记

主代理先从仓库事实与已确认记录解决事实问题，仅澄清影响范围、公开行为、验收或主要
架构的未决选择；无待澄清问题时明确说明。把用户明确要求、仓库事实、自主实现选择
分别记录，不把既有实现、测试或执行输出当作新增授权。

完整需求与方案写入唯一正式 UTF-8 Markdown 文件，先确定性结构预检，再展示全文与
精确 revision，单独等待用户确认。预检只核结构、字段、唯一性与边界，不替代语义审查。
修订仍更新同一文件并重新预检、展示与确认；确认前不启动开发 run、不派发后续代理。

确认后用 typed intake receipt 启动；首次 drive 自动登记同一确认，不再要求全文确认
或派发另一个澄清任务。receipt 是受理材料，不是原生模型调用记录。产品审、技术审、
开发和 QA 只消费当前已确认 revision。实际字段与调用形式唯一见
[正式流程公共合同](../../references/formal-flow.md)。

需求/方案材料范围与 intake artifacts 一致；在途修订通过当前 REQUEST Ask 冻结推进，
取得实际用户决定后按同一提交路径登记。主代理不能自行修改 run 状态、制造 PASS 或
替代用户批准主要选择。项目边界唯一以 `prompts/reviewer-base.md` 为准。
