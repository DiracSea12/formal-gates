# 需求澄清

本动作在受理阶段、正式流程启动之前由主代理以交互方式进行。拷问并对齐所有有实质
影响的细节，不留任何需要猜测或假设的余地。不区分产品问题还是技术问题：目标动机
、用户场景、范围边界/非目标、细节与默认值、异常与失败路径、验收标准、约束与取
舍、风险——只要实质且含糊，就逐维追问到明确。拷问不是连珠炮：仍然一次只问一个
有实质影响的决策，用日常语言讲清背景与选项。本动作只做澄清、确认并把整合后的完
整需求写入需求文件，不执行任何后续流程步骤的登记或内容核对。

自己检视仓库事实，而不是让用户来提供。只把用户的简述、明确决策、已批准的需求记
录和当前作为唯一事实来源的规格说明，当作需求证据。既有实现、测试、任务勾选框、
旧的流程输出和长期记忆都不足以授权改变范围；它们只能用于确立仓库事实和既有约束
。

记录拷问轨迹：问了什么、用户答了什么。记录"考虑过但放过"的项——放过须有理由，
且不构成实质猜测。返回 PASS 之前自检"是否还有任何有实质影响的细节是我不得不猜
的"；有就不返回 PASS。次要实现细节自行决定，除非它们变得有实质影响。

不得跳过澄清：除非确无会实质改变范围、验收、公开行为或架构的决策需要澄清（此时
记录"无剩余缺口"），否则返回 PASS 之前必须已经与用户完成过澄清问答，并将对齐结
论总结呈现给用户让用户最终确认。PASS 记录只写用户实际确认的内容。用户确认过范围
或路线，不等于确认了其他决定；任何会改变用户看到的行为、验收标准或架构方向的决
定，都必须先问用户，不得自己定了再记成"已对齐"。

返回之前检查整条相关需求链，让相关缺口被一并识别，同时仍然一次只问一个有实质影
响的问题。保持只读：不要准备开发、不要派发工作者；除写入需求文件外，不修改任何
项目内容。所有问题解决之后，呈现完整整合后的需求与技术方案，并等待用户明确确认
——"确认"指呈现完整整合需求与技术方案并取得用户最终确认。取得确认后，把整合后
的完整需求与决策写入需求文件（受理阶段、正式流程启动之前，作为本 run 的验收输入
与事实来源），该文档也是后续产品审（Part 1）的输入对象。只有在取得用户最终确认
之后才返回 PASS。
