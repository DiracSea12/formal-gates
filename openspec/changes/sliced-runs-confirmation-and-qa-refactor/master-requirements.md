# Sliced-Runs Confirmation and QA Refactor

Date: 2026-08-04
Status: confirmed
Route: full

## 术语

- **轻量**（原 lightweight）：普通 vibe coding，不创建流程状态或正式任务切片。
- **正式**（原 formal/full/custom）：完整开发流程；其路线再分 **full**（黑盒 QA + 白盒
  QA + 全部门）与 **custom**（黑盒 QA、白盒 QA 与各门任意组合、可省略任一）。

## Complete confirmed requirements

1. **是否拆分由用户确认（仅高置信要拆时触发）。** 拆分决定在 Part 2 技术审
   （`start-readiness`）完成后处理：
   - **高置信要拆**：主代理呈现拆分建议（如何拆、哪些子任务可并行），用户**确认**拆分
     方案后设置分片。
   - **非高置信要拆**（高置信不拆或不确定）：走快速路径——黑盒 QA 设计可与 start-
     readiness 并行；主代理**必填留痕**说明"建议不拆（原因）"（在对话中可见、表示未忽
     略，存在不确定性时注明），不要求用户确认拆分，记录为不拆，按单一 run 进行。
   拆分建议对**所有正式 run**必填呈现并留痕；仅高置信要拆时需用户确认拆分。
   `prepare-action development-worker` 前必须已记录拆分决定（与需求确认同级）。调度分类只
   是启发式。对话留痕（快速路径、与 start-readiness 并行）与 CLI 拆分决定记录
   （start-readiness PASS 后）为两层：留痕是对话可见的软记录，CLI 记录才是正式拆分决定
   ——**CLI 记录即绑定点**（确认后二元、不重切）；快速路径的留痕在记录前可见，用户可在
   记录前提出改拆。子任务实例继承主任务 run 的拆分决定记录，开发 worker 门对子任务实例
   经继承满足。
   拆分建议含：拆分理由、如何拆分、哪些子任务可并行、以及**改拆后果说明**（若改拆，黑盒
   QA 设计按新拆分拓扑展开、已覆盖用例复用）。

2. **必填范围。** 拆分建议呈现与留痕对所有正式 run 必填；**仅高置信要拆**时用户确认拆
   分方案，其余情形留痕即可不需确认。拆分决定只作用于发起的主任务 run，子任务实例作为
   拆分产物不再单独确认。分片场景下整体级产品审/技术审足够，切片继承整体审查结果，不单
   独重跑。

3. **Part 2 开发前阶段按拆分决定分道。** 高置信要拆：呈现拆分建议、用户确认后设置分片。
   非高置信要拆：start-readiness 与黑盒 QA 设计并行、"建议不拆（原因）"必填留痕、按单一
   run 进行。拆分确认使黑盒 QA 设计按已确定的拆分拓扑展开，避免整体级 QA 设计在拆分场
   景下重做。

4. **QA 拆分：黑盒 QA 与白盒 QA。** 现有 QA 机制拆为两种模式，各自可选、均由独立代理
   执行，遵循"独立代理设计 → review 批准 → 执行 → FAIL 返工"的完整循环：
   - **黑盒 QA**：开发前（默认选分片后）由独立代理从已确认需求设计**可观察行为执行用
     例**（对已构建快照执行文档化公开入口，不看实现），经 review 批准，开发后执行；每个
     黑盒 QA 集保留至少一个行为执行用例。拆分场景下，各子任务实例的黑盒 QA 只设计该子任
     务范围内的用例。需求修订或 start-readiness FAIL 时，黑盒 QA 用例**增量修订**——只增
     删改确实受影响的用例；用户改拆（含不确定最终落到拆）时，整体级设计按子任务范围分
     发、已覆盖用例复用、按新拓扑展开，**跨切片边界的整体级用例并入合并 QA**。快速路径
     （非高置信要拆，含高置信不拆与不确定）下，黑盒 QA 设计先于拆分决定与 start-readiness
     并行开始——这是固有取舍；此时路线尚未确认，若最终路线不含黑盒 QA，并行设计即废弃
     （风险小）。
   - **白盒 QA**：开发后由独立代理读实现设计并执行**面向实现结构的测试**（如单元、系
     统、集成测试，职责式定义、不限定具体类型），经 review 批准；验证实现的内部正确性。
     白盒模式的 review 批准阶段读实现（结构测试充分性依赖实现），与黑盒的零上下文 review
     不同。
   两者默认在选择分片之后进行；非高置信要拆的快速路径下，黑盒 QA 设计先于拆分决定并行开
   始（固有取舍），"建议不拆（原因）"留痕在该设计开始前完成。开发后阶段黑盒 QA 执行、白
   盒 QA 与各门审查并行。**质量下限随选择而定**：黑盒被选中 → 每集至少一个行为执行用
   例；白盒被选中 → 每集至少一个结构测试用例；full 两者都选 → 行为+结构双覆盖。旧的"每
   集至少含一个静态与一个行为用例"下限被上述逐模式下限取代。构建/vet/包检查等工具类检
   查由主代理在开发后、门审前的便宜健全性检查承担（SKILL.md 已有机制），不属 QA 黑白盒
   专用下限。增量修订与改拆分发为流程层保证（提示词约束，非 CLI 强制）。

5. **是否并行由用户确认，流程层保证。** 存在可并行条件时，主代理在拆分建议中给出哪些
   子任务可并行，用户确认后才并发；并发子任务各自使用独立的原生 VCS 工作树。并行确认
   是提示词/流程层面保证——CLI 只记录并行建议，不强制并发行为。

6. **合并验证专用化。** 分片 ≥ 2 时，保留总任务实例在合并后自动附加**合并门**与**合并
   QA** 作为其合并后验证：
   - **合并门**：审查合并引入的变更（合并冲突的解决、集成修复、跨切片接缝）、组合产生
     的**跨切片架构回归**（模块边界、依赖方向、耦合偏移）、以及**合并整体相对完整需求的
     比例/复杂度（是否过度设计）**。合并门审查者**有权查看各分片 worktree 的变更与主线
     总变更（base→merged）**，据此评估跨切片架构与整体比例问题；不重审各切片本地内容
     （那归各切片门）。**分片 worktree 在合并门审查完成前保留**，供审查者查看。切片与合
     并验证覆盖 Git/SVN/P4——隔离映射为对应 VCS 的工作副本/客户端工作区，合并映射为对应
     VCS 的合并/集成，不声明仅 Git。
   - **合并 QA**：跨切片交互用例，由独立代理设计/review（各分片开发期间并行进行、分片
     边界确定后开始），合并后执行于合并快照；不区分黑盒/白盒分类；遵循"设计 → review 批
     准 → 执行 → FAIL 返工"循环；含改拆时并入的跨切片边界整体级用例。用例集可为零/极少，
     此时留痕注明"切片基本独立、无跨切片交互用例"，不判 PASS 或覆盖不足。
   合并门与合并 QA 不出现在正常路线选项（`route-candidates` 正常选择列表）中；分片 < 2
   （单一 run）时不存在。保留总任务实例的合并后验证只运行合并门与合并 QA，不重跑常规门
   于 base→merged——常规门已在各子任务实例中审过各自切片内容，重跑即重复；跨切片质量/
   复杂度/架构回归由合并门与合并 QA 覆盖。合并验证**强制**：custom 的省略不延伸到合并验
   证——分片 ≥ 2 时合并门与合并 QA 无论 custom 如何选择都强制附加。

7. **路线选择移到拆分决定之后。** 受理阶段只决定**轻量或正式**，不再定 full/custom。开发
   流程内、拆分决定之后确认路线（full/custom）：
   - **不拆**（单一 run）：在拆分决定（不拆）确认后确认一次路线。
   - **拆**（分片 ≥ 2）：**逐切片确认路线**——主代理给出统一默认路线推荐（基于各切片风
     险/规模），用户拍板；用户只对需要差异化的切片单独调整，不必逐片重新选。逐切片路线
     确认先于该切片黑盒 QA 设计（避免废弃设计）。保留总任务实例只跑强制的合并门+合并
     QA，不涉常规路线选择。
   "路线只问一次"约束相应改为：单一 run 一次、拆后逐切片各一次（带统一默认推荐）。

8. **拆分判据对称化。** `references/sliced-runs.md` 的拆分判据重写：同时避免两个方向的
   错误——过细（子任务小至不值得单独执行一遍完整流程）与过粗（一个子任务包含多个本可
   独立实现、独立验收的逻辑单元，或工作量超出单次完整流程可验证的范围）；介于两者之间
   按独立验证、依赖顺序、拆分收益三点判断切分边界。大而连贯的请求保持单一 run 是正常
   做法。措辞采用正式口吻，与既有提示词文件一致。

9. **路线语义。** `full` 路线 = 黑盒 QA + 白盒 QA + 全部门（复杂度、实现质量等已发现
   门）；`custom` 可从黑盒 QA、白盒 QA 与各门中任意组合、可省略任一（合并验证除外，见
   需求 6）；custom 必须至少选一项（黑盒 QA/白盒 QA/门之一），不允许空路线。

10. **轻量不纳入。** 是否拆分/是否并行的拍板与拆分决定记录仅限正式 run；轻量不增加任
    何拍板或记录。

11. **不设硬门禁。** 不新增 hook 拦截；不设行数/文件数阈值门禁。

12. **需求澄清拆分。** 需求澄清内容拆分为两部分并并入对应审查：
    - **需求细节澄清并入产品审**：目标、用户场景、范围边界、细节与默认值、验收等需求层
      面的澄清与对齐并入产品审（Part 1）。
    - **技术方案选择与对齐并入技术审**：技术方案的选择、对齐、约束与取舍并入
      start-readiness（Part 2）。
    现有 `requirements-clarification` 动作**收窄为纯受理登记**（写入需求文件 + 确认），不
    再承担澄清内容；受理阶段主代理对明显缺口仍提问（轻量澄清兜底）。产品审未发现的实质
    缺口由 start-readiness 或用户主动指出。确认时序：轻量澄清后用户确认需求，深度需求审
    由产品审在确认后以发现项逐项完成。

13. **产品审不重提已定问题（双重保证）。** 主代理在转达发现项时不再重提已定问题（转达
    侧过滤）；CLI 向 product-review 派发时注入已定问题清单，审查者不再重提（审查者侧强
    制）。例外：需求修订（meaning changed）改变了原决定的前提时，可重新提出。

14. **发现项分级与复审边界。** 产品审与 start-readiness 的发现项分级 P0/P1/P2。仅存在
    P2 发现项时，用户处置（接受或指示修订）后，修订需求/方案**不再重新产品审/技术审**，
    直接进入下一步；存在 P0/P1 发现项时，按用户指示修订后重新审。

## 非目标

- 拆分决定确认后不重切/不调整；确需调整时走既有需求变更流程（`requirement
  --meaning changed` 等）。确认前用户可自由提出调整意见（改切片边界、并行范围、各切片
  路线等），确认后即为二元。
- 黑盒 QA 用例不由主代理设计；由独立代理经 `qa-design` 派发产生。

## Confirmed technical solution

- `references/sliced-runs.md`：开头重写——是否拆分由主代理建议、用户确认（双速：高置信
  不拆并行打包确认、拆分可能串行）；拆分判据（过细/过粗对称 + 独立验证/依赖顺序/拆分
  收益三点）；并行确认（流程层保证）；
  分片 ≥ 2 时保留总任务实例合并后自动附加合并门与合并 QA、只跑这两者；路线在拆分决定后
  逐切片确认；确认前可调、确认后不重切。原"流程"段（retained-overall 启动、子任务实
  例、合并集成、集成发现项回投）保留并修订合并验证部分。
- QA 机制：现有 `qa-design`/`qa-review`/`qa-execution` 支持两种模式——黑盒（开发前由独
  立代理设计行为执行用例、经 review 批准、开发后执行，拆分场景只设计本子任务范围，需求
  修订/start-readiness FAIL 时增量修订，改拆时跨边界用例并入合并 QA）与白盒（开发后由独
  立代理读实现设计并执行面向实现结构的测试，职责式定义、经 review 批准）；黑盒 = 行为执
  行、白盒 = 结构测试超集；两者均遵循设计 → review 批准 → 执行 → FAIL 返工循环；质量下
  限随选择而定。
- 拆分调度：仅高置信要拆时呈现拆分建议、用户确认后设置分片；非高置信要拆（高置信不拆或
  不确定）走快速——start-readiness ∥ 黑盒 QA 设计并行、"建议不拆（原因）"必填留痕（存在
  不确定性时注明）、按单一 run 进行。
- 需求澄清拆分：需求细节澄清并入产品审（Part 1），技术方案选择/对齐并入 start-readiness
  （Part 2）；`requirements-clarification` 收窄为纯受理登记；`prompts/actions/
  product-review.md` 与 `start-readiness.md` 相应扩充。
- 产品审不重提：`prompts/actions/product-review.md` 加入"用户已拍板过的发现项与决定不再重
  提"（例外：需求修订改变前提时可重新提出）；CLI 记录已拍板发现项清单，并在 `prepare-
  action product-review` 时注入派发（审查者侧强制），主代理转达时同样过滤（转达侧过
  滤）。
- 发现项分级：`product-review` 与 `start-readiness` 提示词要求审查者将发现项分级
  P0/P1/P2；主代理按需求 14 处置——仅 P2 发现项时用户处置后修订不再复审，存在 P0/P1 时
  修订后重新审。
- 路线重构：受理阶段只定轻量或正式；开发流程内拆分决定后确认路线（full/custom）——单一
  run 一次、拆后逐切片各一次（主代理给统一默认推荐、用户拍板）；保留总任务实例不涉常规
  路线。
- `gates/merge-gate.md`：新增专用门，审合并引入的变更（冲突解决、集成修复、跨切片接
  缝）、组合产生的跨切片架构回归（模块边界、依赖方向、耦合）、以及合并整体相对完整需求
  的比例/复杂度；审查者有权查看各分片 worktree 变更与主线总变更（base→merged）。切片与
  合并验证覆盖 Git/SVN/P4（隔离映射为对应 VCS 的工作副本/客户端工作区、合并映射为对应
  VCS 的合并/集成）。在目录/`route-candidates` 中登记为**条件自动门**——不进正常选择列
  表，仅在保留总任务实例分片 ≥ 2 时自动附加。
- 合并 QA：跨切片交互用例（含改拆时并入的跨边界整体级用例），独立代理设计/review（各
  分片开发期间并行进行），合并后执行于合并快照；不区分黑盒/白盒分类；遵循设计 →
  review 批准 → 执行 → FAIL 返工循环；仅在分片 ≥ 2 时存在。
- `SKILL.md`：删除"需求整体无法作为一个连贯有界单元来实现和验证时，先读
  `references/sliced-runs.md` 再拆分"一句；受理第 4 步从"lightweight/full/custom"改为
  "轻量 / 正式"；正式流程第 4 步（开发前检查）改写为 Part 1 产品审 →
  Part 2（双速）→ 黑盒 QA 设计/审；拆分决定后新增路线确认步骤（单一 run 一次、拆后逐
  切片各一次）；第 5 步（开发）后开发后阶段并行黑盒 QA 执行、白盒 QA 与各门；合并验证
  段改为合并门与合并 QA（分片 ≥ 2 自动附加、合并后只跑这两者）。
- `references/formal-flow.md`：新增 `workflow slicing` 命令映射（技术审之后）；路线命令改
  为拆分决定后确认；同步更新"开发之前"段散文（双速）、QA 模式说明与合并验证段。
- `internal/validate/runstate.go`：`RunState` 与 `RunSummary` 新增 `Slicing`（拆分定位、
  子任务数、并行建议）字段。
- `internal/validate/workflow.go`：新增记录拆分决定的动作；`prepare-action
  development-worker` 增加拆分决定已记录校验；拆分决定只能在 `start-readiness` PASS 后
  记录；分片 ≥ 2 时保留总任务实例自动附加合并门与合并 QA。
- `internal/cli/cli.go`：新增 `workflow slicing` 子命令。
- 测试：拆分决定记录与未记录时 development 准备被拒；拆分确认时序（start-readiness 未
  PASS 时不可记录）；合并门/合并 QA 的分片 ≥ 2 自动附加、正常路线选项不出现；黑盒 QA
  与白盒 QA 在路线中的可选性；双速调度两条路径；拆分后逐切片路线确认；catalog 一致性。

## Acceptance evidence

- `go test ./...`、`internal/validate` 与 `internal/cli` race、`go vet ./...`、原生构建、
  package 校验、portable canary、`git diff --check` 全部通过。
- workflow slicing：记录后 prepare development-worker 放行，未记录时被拒；
  start-readiness 未 PASS 时记录被拒。
- 用户可见行为（提示词内容检查）：拆分建议对所有正式 run 必填呈现并留痕；高置信要拆时
  用户确认拆分方案、非高置信要拆时"建议不拆（原因）"必填留痕；拆分建议包含可并行子任务
  与改拆后果说明。
- 合并门与合并 QA：分片 ≥ 2 的保留总任务实例自动附加；单一 run 的正常路线选项不出现
