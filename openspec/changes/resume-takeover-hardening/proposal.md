# Proposal

停止因"一点小变动"或"半途接手"而强制正式流程全量重跑（需求澄清、QA 设计
/审查、门审全部重来），并修掉返修重审只审返修增量的漏审问题。

三块：

1. **接手 = 新 run + 显式基线。** 接手中断的 run 是新建一个 run，而不是复活旧
   run。对齐后的需求就是契约；审查以整个功能为单位，在途已提交的工作经显式基
   线纳入审查 diff。`workflow start --base-snapshot` 允许指定当前 HEAD 的祖先，
   使已提交的在途工作落在"基线到当前"之内。注册需求之前先跑目标项目的便宜健
   全性检查。

2. **中途变动是判定，不是死刑。** 现在会杀死 run 的三处硬守卫（prompt 目录变
   更、原生 VCS 身份漂移、冻结需求产物变更）改成可报告的 delta，由主代理分类：
   能证明不受影响的结果继承（记录理由），受影响或不确定的重跑或派独立判定。
   开发开始后允许语义未变（meaning-preserved）的需求重绑定，保留不受影响的
   PASS。

3. **返修重审用完整 diff。** 返修后重跑的门审查完整的"基线到当前"交付，绝不只是
   返修增量。组装出的提示词显式声明这一点，审查者必须报告它实际比较的快照对；
   报告不匹配即丢弃结果。

另外，需求澄清动作（`prompts/actions/requirements-clarification.md`）的措辞与 SKILL
冲突、且不强制持久化对齐结论，需要复盘修正。SKILL 层修正随本 run（Phase 1）交付；
提示词文件本身属 catalog 文件，作为 Phase 2 在 B2 目录 delta 容忍落地后的后续 run 交
付。

另外，被中断未产出结果的子代理，宿主能续用（Claude Code SendMessage 等）时优先恢复
原代理继续，不首先重开——作为 Phase 3 在后续 run 落地并追踪。

提示词与文档的改动优先修改既有文件、不新增，保持精简克制。范围外：对抗性加固、
权限/不可变文件故障注入、不受支持平台的兼容路径。
