# formal-gates 硬流水线改造方案（草稿）

> 状态：**草稿，本方案建议的推进流程为「拓扑 → 逐节点对齐规则 → 硬流水线整体设计」；节点规则对齐入口：[WORKFLOW-TOPOLOGY.md](WORKFLOW-TOPOLOGY.md)（N0–N13 节点锚点）**。
> 依据：[RESEARCH-HARD-PIPELINE.md](RESEARCH-HARD-PIPELINE.md)（确定性编排调研）、[RESEARCH-ERROR-RECOVERY.md](RESEARCH-ERROR-RECOVERY.md)（错误/恢复调研）。
> 本方案拟定的方向：**流水线程序驱动（形式 A）**、**尽量少 hook**、**双向路线分类**、**该问才问**、**授权不推断**。

## 1. 现状与问题

### 1.1 现状（已有资产）

- CLI 状态机：`workflow start/show/resume/abort/reset`、`prepare-action`/`record-action`、`prepare-gate`/`record-gate`、`claim-dispatch`、`requirement`、`slicing`、`route`、`settle-findings`、`qa-*`、`snapshot`、`carry`、`authorize-repair`、`seal`。
- 单一临时状态文件 `.gates/tmp/<run-id>/state.json`（CLI 原子更新，禁止手工编辑）。
- 派发规范文件 `.gates/tmp/<run-id>/prompts/<dispatch-id>.md`，`claim-dispatch` 校验内容 hash，不一致即硬阻断——「派发即原样转发」已程序化。
- 生命周期钩子：`hook decide`（改状态/非法迁移判定）、子代理启动/停止捕获。
- VCS 依托：git 基线/快照/对比；正式流程九步由 SKILL.md 拥有。
- 显式授权已有先例：`workflow abort`/`reset` 要求 `--user-confirm`/`--user-approve`。

### 1.2 问题（已观察到的编排错误形态——非穷举）

**问题主体：run 内细节编排错误 → 撞硬阻塞 → 无机械恢复路径 → 整个 run 卡死**（见后果一）。受理阶段的轻量/正式错只是同根因的最轻实例，不是问题主体。

错误形态是**开放的，不止下表这几类**——主代理自由发挥的空间有多大，错误形态就有多丰富；下表只是已观察到的归因分组（实例全部取 run 内）：

| 错误形态 | 实例（run 内） | 根因 |
|---|---|---|
| 路线选择错 | 下一步靠主代理自己从 SKILL.md/记忆拼读而非 CLI 状态：快照前 resume、start 的 base/current 设错、未认领就记录——反复撞硬阻断 | 「下一步是什么」无程序查表，靠模型判断 |
| 询问纪律错 | 该问的不问：修复授权、scope 决策、seal 确认未授权就推进；不该问的反复问（「现在开始吗」） | 该不该问无程序约束，靠模型自觉 |
| 授权推定错 | 把「没反对」当「同意」擅自推进；把「看起来完成」当完成直接记录 | 流程推进无显式授权门，静默被当作同意 |
| 并行/分片拓扑错 | 可并行处全部串行执行（CLI 已有并行检测提示，主代理基本无视）；规则要求分片独立开发/QA/门，主代理把部分工作放主干 | 并行集与分片→worktree 绑定无程序持有 |

另有已知但归不进上类的形态（例）：手写派发提示词、需求改动后不重确认、测试污染仓库、上下文紧反复重启——**分类远未穷尽**。

**改造不逐类拦截**：追着错误形态逐类加拦截永远追不完（这也是「逐点拆解意义不大」的原因之一）；改造消灭的是**根因**——把「下一步/问不问/授权有没有/并行分片」的决策权整体从主代理手里拿走（见 §3、§4），错误形态再多也没有发生入口。

**后果一：run 卡死（最大的痛）。** 各类细节编排错误反复触发当前的硬阻塞规则，而**被阻后的 run 没有机械恢复路径**，整个 run 卡住无法继续——阻塞本身成为新的死点。硬阻塞规则的强度/粒度加剧这一点：细节错得越频繁，撞规则的次数越多，卡死概率越高（hook 判定面过宽也产生误杀，见 4.5）。

**后果二：乱编排导致效果下降。** 即使没被阻塞（失败即放行、规则未覆盖的面），主代理自由组装命令/参数/顺序的「乱编排」也造成反复试错、上下文翻腾、不必要派发，开发效果系统性下降。

**推论（改造的核心约束）**：① 硬阻断必须成对出现——**每个阻断都带机械恢复路径**；② 细节编排（命令、参数、顺序）从主代理手里拿走，由 CLI 指令携带，乱编排没有空间；③ 并行集与分片拓扑在流程定义时声明（对齐 ASL Parallel/Map、LangGraph fan-out），由 CLI 指令一次性下发，主代理只执行不决定。

## 2. 改造目标（一句话）

**formal-gates 的流程由程序驱动：CLI 持有迁移表，「下一步」、必问点、授权判定全部由 CLI 状态机机械决定；主代理只执行 CLI 发下的指令；hook 压缩到窄判定面。以及：每条硬阻断成对出现——阻断必带机械恢复路径，卡死可检测、可恢复。**

## 3. 总体架构（五件套）

1. **迁移表**：CLI 内置，唯一持有「下一步」；非法迁移拒绝。
2. **事件日志**：append-only，恢复点自动推导（配合现有 state.json）。
3. **唯一门命令**：每次迁移前 CLI 校验前置条件，不靠 LLM 自觉（现状已有，需补强度）。
4. **窄 hook**：只转发「改状态/非法迁移」两类到 CLI 判定，决策委托 `hook decide`（现状已有，需收窄 matcher）。
5. **驱动式执行（形式 A）**：每一步的指令由 CLI 输出，主代理执行指令；高风险段每步独立 headless 会话。

> **host 解耦**：管线核心（迁移表/事件日志/门命令/指令输出）与 LLM host 无关；Claude Code 的 hook/skill 只是当前接入层的实现通道（项目已有 claude/codex 双 host 适配先例），换 host 只换接入层——下文提到的 hook/headless 均为当前接入层形态，不是核心机制。

## 4. 改造原则（本方案建议）

### 4.0 改造粒度说明（2026-08-11）

本需求是**大规模重构**（整个工作流重新架构为程序驱动管线），逐点拆解改造意义不大。本方案建议的推进方式：**工作流拓扑（[WORKFLOW-TOPOLOGY.md](WORKFLOW-TOPOLOGY.md)）→ 逐节点对齐规则（N0–N13）→ 节点规则齐备后整体设计硬流水线**。

下方 4.1–4.8 保留为**本方案拟定的改造原则**：不再逐点细化实现形态，统一在节点规则齐备后的整体管线设计中消化。

### 4.1 程序驱动（核心）

- **现状**：主代理在自由会话里逐步调 CLI，下一步靠自己读 SKILL.md 判断。
- **改造 A1（第一期）**：CLI 每次命令的 stdout 输出「下一步唯一指令」+ 必问点标记。指令携带**确切命令与参数**（不只是一句「下一步做什么」）——主代理不再组装编排细节，乱编排没有空间。同令牌纪律：状态名 = 门条件名 = 输出指令文本，从单一源生成，杜绝「对不上号」。
- **改造 A2（第二期）**：每步独立 headless 会话（CLI 按迁移表启动子会话，当前接入层为 `claude -p`）；程序不启动的步骤不存在，「跳步」物理不可能（业界先进形态：claude-orchestrator / brimstone / LangGraph 图遍历）。
- **待细对**：A1 先行的迁移节奏；A2 的触发范围（全部步骤还是仅高风险段：派发/认领/seal）。

### 4.2 双向路线分类（classify 门）

- **新增** `workflow classify <path> <change-type>`：查声明式分类表（内容类型 × 修改类型 → 默认路线：轻量 / 正式 / 需人工），结果写事件日志。
- **分类表草案（待细对）**：

| 内容类型 | 新增 | 修改 | 删除 |
|---|---|---|---|
| 知识/调研文档（RESEARCH-*、PROMPT-ENGINEERING-KNOWLEDGE*） | 轻量 | 轻量 | 需人工 |
| 代码（internal/、cmd/、gates/、prompts/、bin/） | 正式 | 正式 | 正式 |
| 需求/方案文档（openspec/changes/*） | 正式 | 正式 | 正式 |
| 文档（README*、SKILL.md、CLAUDE.md、AGENTS.md） | 需人工 | 需人工 | 需人工 |
| 流程状态（.gates/*） | 禁止直改 | 禁止直改 | 禁止直改 |

- **启动校验**：`workflow start` 时校验需求文件分类——默认轻量却启动正式 → CLI 拒绝，除非 `--user-confirm` 显式覆盖（留痕：谁、何时、为什么）。→ 直接消灭 E1 类错误。
- **反向对称**：分类=正式却走轻量 → 轻量路径上写代码/需求文件被 hook 阻断（扩展现有 `hook decide` 判定面）。
- **待细对**：分类表的具体行；`classify` 的输入形态（路径+修改类型 vs 自动检测）；覆盖理由是否需要模板。

### 4.3 必问点清单（interrupt-before 等价物）

- **新增**：流程定义中声明暂停点清单（可中断点）：需求确认、路线确认、修复授权、seal 确认、abort、reset、adopt-external、scope 决策、start 授权。
- 暂停点上 CLI 输出「待确认项」；record-action / record-gate / seal 前必须已有用户确认记录，否则拒绝（机械校验，不是提醒）。
- 清单外：CLI 指令即执行，主代理不问（消灭 E2 类错误）。
- 确认值类型化（对齐 LangGraph `Command(resume)`）：approve / reject(+理由) / edit(+修订内容)，记录进事件日志。
- **待细对**：清单的完整项集；类型化确认值的表示形态。

### 4.4 授权哨兵（DONE 不推断）

- `--user-confirm` 从布尔扩展为类型化确认（approve/reject/edit），记录值。
- **新增**：`workflow start` 本身要求显式授权（对齐 `abort` 的现有要求）——「用户没反对」不是状态，没有 `approved` 就是未授权。
- 完成判定：派发结果记录 = 显式哨兵（`record-action`/`record-gate` 已要求 dispatch id + 状态）；「看起来完成了」不构成完成。
- **待细对**：start 授权的确认形态（命令行 flag vs 交互确认文件）。

### 4.5 少 hook

- **收窄 matcher**：工具调用钩子只对以下情况委托 `formal-gates hook decide`：
  - Edit/Write 命中 `.gates/` 路径；
  - Bash 命令命中 `.gates/` 或 `formal-gates` 二进制调用。
- 其余工具调用不经过 hook（读操作、普通文件写一律放行，消灭「ls .gates 被拦」类误杀）。
- **0-hook 检测兜底**：state.json + 事件日志哈希链，CLI 每次调用校验完整性——绕过 CLI 改状态 = 链断裂 = 检测即失败（检测式，非预防式）。
- **待细对**：matcher 的精确范围；哈希链的强度（sha256 逐事件 vs 整体文件）。

### 4.6 错误处理 / 恢复语义（接入调研结论）

- **本期（标注分期）**：非法迁移 = 硬停（已有）；事件日志追加（已有）；中断续跑 = `workflow resume`（已有）。
- **后续**：错误路由表（错误名 → 重试/硬停，声明式）、精确撤销 + 分支点重放、心跳判死、每步 headless 会话的自动续跑。
- **非目标（本期明确不做）**：loop engineering（agent 内部循环）、恢复语义全量、平台扩展、P3 边界项。

### 4.7 阻塞可恢复性（每条硬阻断成对出现）

- **每个硬阻断输出必须包含恢复路径**：阻断时 CLI 输出「违反的规则 + 唯一恢复指令」（防线一与防线二合一，阻断信息即下一步指令）。已有先例：现有 hook 的阻断信息已含「dispatch development-worker / 走需求变更流程」。
- **阻断 ≠ 卡死**：被阻后的 run 处于「可恢复」状态，恢复路径由 CLI 声明，主代理照指令执行即可继续；**阻断点没有恢复路径 = 设计缺陷**。
- **卡死检测**：watchdog / 心跳 + 超时识别「无进展 run」（无产出且超时），进入标准恢复流程——`workflow resume` 是常态操作，不是异常操作。
- **减少卡死概率的另一半**：4.5 收窄 hook 判定面（消灭误杀）+ 4.1 指令携带确切参数（消灭细节错），从源头减少撞规则次数。
- **恢复语义对齐调研**：`workflow resume` 续跑（已有）；精确撤销/分支点重放（第二期）。
- **分片级恢复**：每个分片独立可恢复，单分片卡死不拖垮整体（配合 4.8 的分片绑定）。

### 4.8 并行与分片拓扑（声明式指令，对齐 ASL Parallel/Map、LangGraph fan-out）

- **现状**：CLI 已有并行检测（stderr 提示「可并行 X 项（列表），当前并行 Y 项，建议补足」），但只是**提示**——主代理基本全部无视，可并行处一律串行执行。
- **改造：并行集从「提示」升级为「指令」**：进入可并行阶段时，CLI 的下一步输出**一次下发完整并行集**（如开发后阶段 {黑盒 QA 执行, 白盒 QA, 各已选门}）；主代理的职责只是逐个启动、逐个认领，没有「决定串不串行」的输入点。
- **分片绑定**：分片 → worktree → branch 的映射在 `workflow slicing` 决定时绑定并由 CLI 持有；分片开发派发/快照校验 VCS 身份——**分片开发快照只能记录在分片 worktree 上，主干无法记录分片开发快照**，「所有分片独立进行开发/QA/门」由绑定机械保证，不靠主代理记性。
- **待细对**：并行集下发形态（指令式下发 vs 记录结果时校验并行集完整性）；分片绑定的校验强度（快照时强制校验 worktree 身份 vs 仅提示）。

## 6. 验收标准（按改造机制，不按错误形态逐类对）

- **E1 类**：分类=轻量的请求尝试 `workflow start`（正式）→ CLI 拒绝，输出轻量路径与理由；`--user-confirm` 覆盖后留痕可见。
- **E2 类**：清单外步骤不再出现主代理提问；清单内步骤（如 seal）无确认记录时被 CLI 拒绝。
- **E3 类**：无显式授权时任何流程推进被拒（`start` 同 `abort` 一样要求显式确认）；「看起来完成」的派发结果在无哨兵时不被记录。
- **E4 类（卡死）**：任一硬阻断信息包含唯一恢复指令；被阻后的 run 沿 CLI 声明的恢复路径可直接继续；无进展 run 被 watchdog 标记并进入标准恢复流程。
- **E5 类（并行/分片）**：进入可并行阶段时指令包含完整并行集；分片开发派发绑定分片 worktree，主干上记录分片开发快照被拒；单分片卡死可独立恢复、不拖垮整体。
