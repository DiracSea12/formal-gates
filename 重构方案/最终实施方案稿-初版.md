> 生成：2026-08-14

---

## 1. 背景与目标

### 1.1 要解决的问题

当前主代理站在执行环路里，手里握着「下一步调用哪个 workflow 命令、按什么顺序、派发哪些子代理」的决策权。由此产生两类后果：

- **流程卡死**：编排错误反复撞现有硬阻断规则，而现有恢复路径（resume / reset / STALE / 分步 Seal）分散、仍靠主代理自行选择，被阻后的 run 容易卡住——问题不是「没有恢复路径」，而是「恢复路径没被程序接管」。
- **效果下降 + token 浪费**：即便没被卡死，乱编排也造成反复试错、上下文翻腾、不必要派发，开发效果系统性下降，token 被消耗在「推理下一步」而非「干活」上。

### 1.2 目标（两条，均等）

1. **编排流水线化**——让编排像封死的道路，没有犯错空间；每条硬阻断成对出现（阻断必带有限、类型化的后续路径），卡死可检测、可恢复。
2. **减少 token 消耗**——主代理退出环路，从「记流程、推理下一步」变成「读指令、执行」。

### 1.3 根本判断

问题不是「门禁不够多」，而是**主代理站在执行环路里**。CLI 状态机已接近确定性内核——27 个子命令、sha256 完整性、原子写、写阻断 hook、规范提示词写盘双验、`parallelStageTable`、Seal 幂等续跑——这些机制都已存在。缺的不是新机制，而是把主代理从「每步之间谁来按什么顺序调用哪个命令」里抽出来，交给一个**确定性的 Go 引擎**接管环路。

## 2. 边界与反过度设计（本稿的尺子）

**先定边界，再谈设计。** formal-gates 是一个**个人单机 CLI**：单用户、单仓库、单 run 的推进由短命的 `drive` 进程串行完成，**单一 transition authority**（每个 run 同一时刻只有一个进程能推进状态、每 run 串行写入），没有跨进程共识、没有「时间旅行」需求。但 `drive` / `submit` / lifecycle hook 是**多个进程写者**、可能并发重入，写互斥仍用 `filelock`——这是「单一权威 + 串行写入」语义下的并发重入保护，不是多写者共识。凡是以**分布式系统 / 多写者 / 事件溯源重放 / 审计回溯**为前提的机制，在本项目里都是过度设计——它们解决的是这里不存在的问题，却引入数据库迁移、协议定义、投影一致性、跨平台服务一整块维护面。

据此，本稿**明确砍掉**以下机制，并给出理由（审查者若重提，以此节回应）：

| 被砍机制 | 它解决什么问题 | 为什么在这里是过度设计 |
|---|---|---|
| append-only 事件日志 + 纯 `Reduce` 投影 + `Store` 抽象 | 跨进程重放、时间旅行、多写者共识（Temporal 模式） | 单机单 run，写者只有引擎一个角色；现有 `state.json`（原子替换 + sha256 完整性 + 快照 + 派发 + Attempt + 结果）已是完整的权威工作流投影，事件日志投影/重放是自找的第二个真相源 |
| `EffectIntent → ReceiptObserved → Acceptance` 三级回执协议 + `ArtifactCommitted` 外部产物协议 | 副作用与日志的精确因果追踪 | **不建立通用 Effect/Artifact 协议**；派发成功/自述完成/控制面接纳三件事实，已被现有 `claim-dispatch` 的 `ReviewerIdentity` + 独立 validator + `record-action/gate` 的 STALE 恢复路径承载。spawn 与非幂等 HostAction 仅保留最小 issue/ack/acceptance 状态（见 §4.5），不抽象成通用框架 |
| `authorityGeneration`（控制权归属代次）+ lease/heartbeat 自动接管 | 分布式租约下的旧权威结果丢弃 | 单机无多权威并存；旧结果由 `dispatch ID + Attempt + source bindings` 三者验证挡住，人工接管是 `controlMode` 的一次单向翻转，不需要代次计数 |
| 六类错误系统 + `ErrorRoute` | 类型化错误路由表 | 砍掉逐行路由表；错误分类见 §6 第二期第 3 条——注意 `requireResumeInterrupted` 三分支只适用于「代理中断恢复」，不扩张成全局错误系统 |
| watchdog / OS 定时器（cron/launchd/Task Scheduler） | 无人值守的定时兜底 | `drive` 是短命进程（干到 WAITING 就退），watchdog 无处安身；失联靠 deadline 持久化 + 重入检查，不装 OS 服务 |
| repo 级集成队列 / 分片合流 CAS | 多分片写同一 HEAD 的合并 | 交权只限**非分片单 run**；分片是后续，不是本期门槛 |
| 随机 chaos 注入 / 大规模 benchmark / headless adapter | 分布式故障演练、宿主级无 LLM 通道 | 随机 chaos 与 benchmark 后置；headless 是否做按实测搬运成本决定。**但确定性 kill/crash 故障边界测试必须前置到交权门槛**（见 §6 第三期），不属本条 |

**保留的尺子**：每加一个机制，先问「这是单机单 run 必要的最小机制，还是顺手从分布式方案里带进来的？」必要的最小机制只有这些——① 静态迁移表（唯一流程权威）+ 确定性 `Observe + Decide`；② 唯一推进入口（`drive`）+ 外部事件提交入口（`submit`）；③ 引擎/旧命令硬隔离（`controlMode`）；④ 控制面并发重入的互斥（`filelock`）；⑤ spawn 崩溃窗口的对账依据（`pendingActions` + `revision`）。其余一概不进本期。

## 3. 无争议内核

以下作为地基直接写死：

1. **「下一步」由确定性 Go 代码决定，不由主代理临场判断。** 主代理降级为「用户接口 + 受理 + 呈现决定」，不兼任开发 worker——开发走独立 ticket worker。原因：主代理既面向用户又写代码，会随流程积累上下文（违背省 token 目标）、模糊「谁在改代码」的授权边界；开发本就有隔离 worker 派发，主代理不该越位。
2. **`state.json` 是唯一权威工作流投影**（原子替换 + sha256 完整性 + 快照 + 派发 + Attempt + 结果），状态不靠 LLM 记忆；恢复点从已持久化状态推导，不靠重放。它是「唯一权威投影」，不是「所有事实的唯一真相源」——本方案明确依赖 HEAD、需求文件、worktree、lifecycle 观测这些外部事实，`state.json` 只投影流程可判定的那部分。
3. **Task / Dispatch / Result 分离**；结果持久化为不可变记录（写进 `state.json`，已接纳后禁止修改）；agent 自述「完成/PASS」一律视为不可信输入，走独立 validator。
4. **并行由表/DAG 产生**，不由 agent 记性——现有 `parallelStageTable` 从「stderr 提醒」升级为「强制指令」；升级同时修掉它一处缺陷：它现在用「结果不是 PASS」当作「还需审查」，会把已 FAIL 的门继续列进待审清单，但 FAIL 的门走的是修复（先推进修复快照再重审）而非直接重审——强制指令必须区分「PENDING/RUNTIME_ERROR 需审查」与「FAIL 需修复」，否则会催主代理去做一件会被 record-gate 拒绝的事。
5. **每条硬阻断成对出现**：阻断必带有限、类型化的后续路径（重试 / 回退 / NEEDS_OPERATOR），「阻断 ≠ 卡死」——`NEEDS_OPERATOR` 是人工介入点，不是自动恢复。
6. **人工决策 = 持久化的类型化记录**（绑定 snapshot + request ID，`createdRevision` 仅作追踪、不用于判定新鲜度），不是聊天记录里的一句「用户说行」。
7. **复杂度程序内部闭环，不转移给 LLM（全文贯穿约束）**：迁移表、pre 条件、parallel 组、trigger 分类、revision CAS、pendingActions 消费、actionID 校验、filelock、deadline 检查、结果接纳验证——**所有**能闭环的内部机制一律在 Go 里闭环；运行时主代理只收到 `Decide` 产出的外部指令（SpawnRequest / HostActionRequest / AskRequest / WaitReason / OperatorRequest），不读迁移表、不判 pre、不碰任何内部字段——否则 AI 又会对这些机制「自由发挥」，重新引入编排错误。下文每个机制都据此闭环，不再逐个重复声明。

## 4. 关键分歧点的决策

### 4.1 持久化 —— 决策：继续用 `state.json`，不引事件溯源，按需补最小字段

- **决策**：**继续用现有 `state.json`**（原子替换 + sha256 完整性 + 快照 + 派发 + Attempt + 结果结构），**不引事件日志 / `Reduce` / `Store` / 投影**。按需补一批**引擎内部字段**——都只经命令间接作用于它、主代理不读不写：
  1. `controlMode = legacy | engine`——引擎/旧命令硬隔离：legacy run 拒绝引擎命令，engine run 拒绝旧命令，杜绝双权威。
  2. 单调 `revision`——每次写入递增，只作 `state.json` 写入 CAS（写前校验、不匹配就重算，挡控制面并发重入的陈旧写入）。**不用于判定并行任务/人工决定的新鲜度**——pendingActions 与人工决定记 `createdRevision` 仅作追踪，有效性靠 `action/request ID + 当前任务状态 + dispatch ID/Attempt + source bindings` 判断，别的并行任务推进导致的全局 revision 变化不能使它失效。
  3. `pendingActions`（map，key = actionID）——spawn 前在一次锁内原子写入整批（每个要 spawn 的 worker 一条：ticket hash + action id + 交付状态），每个 `SpawnReceipt` 只消费对应 actionID（挡 spawn 崩溃窗口，见 §4.5）。
- **字段取舍（不设「只加 N 个字段」这类人为数字约束，按需补齐）**：除上三字段外，随「一次性交付」（§4.5）、「结果桥」（§4.5）、「任务图」（§5.3）自然配套的引擎内部字段——① `pendingActions` 条目（`actionID / kind / taskKey / payloadHash / status / issuedAt / receiptDeadlineAt`，统一所有 host 动作，见 §4.5）；② **`currentAttemptID` 不单独持久化，从 `PreparedDispatch.ID + Attempt` 推导**（见 §5.3，不是 run 顶层单值、也不新造重复真相；若确需显式引用则改名 `currentDispatchIDByTaskKey`）；③ Seal/Abort 后把最终 request ID / 结果 digest / 回执写进 summary（临时状态删除后仍可幂等重试）；④ **`workflowDefinitionVersion` + `stateSchemaVersion`（两个小 int）**——run 创建时钉死。**这一条我上一稿判断错了**：迁移表随二进制发布**不意味着无版本漂移**——run 用表 v1 启动暂停、formal-gates 升级、新二进制带表 v2、恢复旧 run 时 v2 就在解释 v1 状态。故 run 创建时钉死版本，新二进制要么声明兼容旧版本、要么拒绝恢复并要求显式迁移。**拆两个而非共用一个**：定义版本（迁移表逻辑）与状态 schema（state.json 字段结构）升级频率、兼容策略不同，共用一个值会把「只改定义」或「只改 schema」都夸大成本来不兼容；两个 int 仍不是事件溯源、不算过度设计。
- **旧状态默认语义（存量 run 的解释，防误读）**：`state.json` 里**缺 `controlMode` → 按 `legacy`**（旧 run 就是旧命令在管，引擎不接管）；**缺 `workflowDefinitionVersion` / `stateSchemaVersion` → 按 legacy v0 / v0**（无版本钉死）。**engine drive 不自动迁移旧 run**：存量 legacy run 要继续，要么走显式迁移、要么继续用旧命令，引擎绝不原地把它翻成 engine run。
- **理由（为何不引事件溯源，见 §2）**：事件日志的价值是跨进程重放/审计/时间旅行，单机单 run 不需要；现有 `state.json` 已有完整性校验与 `Attempt` 计数，旧结果由 `dispatch ID + Attempt + 状态 + source bindings` 联合验证（现有 STALE 恢复路径证明快照 + source 绑定已够用），缺的只是「并发重入互斥」「spawn 窗口对账」「工作流版本钉死」几件小而必要的事。SQLite 更不必要——它解决的是「多文件原子提交」，而单 `state.json` 整体原子替换没有跨文件事务。

### 4.2 工作流定义载体 —— 决策：Go 静态迁移表，不做 YAML+编译器

- **决策**：迁移表为 Go 内静态声明 + 启动自检（静态只能查：重复边、未知目标、结构可达性、终态封闭、指令模板可渲染；「每个环一定有进度」这类循环语义**静态自检证明不了**，靠 fixture / property test 保证）。**迁移表从上线起就是唯一流程权威**：`Observe` / `Decide` / `drive` / `requireTransition` 都从这一份定义派生、不各自维护判断逻辑；effect 就是普通 Go handler，不扩张成 YAML/DSL/编译器。**主代理永远不读这张表、不判 pre/parallel**——它只收到 `Decide` 产出的指令，整张表是引擎内部闭环的。
- **注意**：不校验「无环、终态唯一」——本流程有修复环（N12→N10）、需求修订回退环（N3/N4→N2），且有多个终态（SEALED/ABORTED，即现有 `RunState.Status` 的合法终态；不新增 FAILED/CANCELED），「无环、终态唯一」不成立。
- **理由**：`requireTransition`、`parallelStageTable` 已是 Go 表，迁移表是两者的「升级为唯一权威」，而非另开配置语言。不变量（P0/P1 分级、快照 provenance、revision 漂移）无论怎样都在 Go 里；YAML 只能承载「形状」，而 `var transitionTable = []Transition{...}` 已表达形状。`run graph` 可视化可从 Go 表生成。

### 4.3 hook 角色 —— 决策：辅助边界，不作主门禁；写隔离保留

- **决策**：硬门禁落在 Go 引擎自身状态校验里（现有 `requireTransition` + sha256 完整性就是这个正确基础），fail-closed。hook 只作辅助边界，且拆成两件不同的事、不混为一谈：
  - **流程门禁角色**（拦「这一步不该走」）：可以收窄、少 hook——主门禁在引擎里，hook 不承担「封死道路」。
  - **写隔离角色**（拦「主代理/审查代理直接改代码与 run 状态」）：保留 `write_block`（PreToolUse + agent_type 身份隔离），但把时间区间钉死为 `run.status=ACTIVE && development-worker.status!=PENDING`。产品审、技术审及文档修订发生在区间之前，不启用写墙；Seal / Abort 把 run 持久化为非 ACTIVE 后立即解除，即使终态临时文件因收尾重试暂留，也不得继续阻断。空间区间只覆盖承载该 run 的仓库根：窗口 cwd 即使仍在活动仓库，明确写向仓库外路径也必须放行；简单 Bash 写入仅在全部目标都可解析且都在仓库外时放行，混合或未知目标继续保守处理。这是「审查与开发隔离」的墙，与流程门禁无关；边界必须由同一阶段状态派生，不能再退化成「只要存在 ACTIVE run 就阻断」或全局文件锁。
- **理由（已核实官方语义）**：hook **多数事件** fail-open——只有 blocking-capable 事件（PreToolUse/UserPromptSubmit/Stop/SubagentStop/PreCompact）的 exit 2 / `deny` / `block` 硬阻断，exit 1/3/127/无效 JSON/超时全放行。故 hook 当不了「封死道路」的主门禁，主门禁必须在引擎里 fail-closed。写阻断对子代理是否触发，以项目自带 canary（`codex_hook_canary` / `canary`）实测为准，重构硬化前重跑确认，不靠文档断言。

### 4.4 底座 —— 决策：subagents + hooks + 文件状态 + worktree 隔离

- **决策**：确定性引擎自建在 Go 里，底座 = 子代理 + hooks + 文件状态 + worktree 隔离；不依赖 Agent Teams / Dynamic Workflows / LangGraph / Temporal。
- **理由（已核实）**：Agent Teams 仍 experimental（每会话一个 team、不能嵌套、resume 不还原 in-process teammates）；Dynamic Workflows 有 16 并发/单次 1000 agents 硬顶、支持会话内暂停恢复，二者都与 formal-gates「跨 host 确定性控制面」定位冲突。LangGraph/Temporal 对单机 CLI 是第二运行时/运维边界，一致排除。
- **旁证**：Claude Code 自己把 Dynamic Workflows 做成「确定性 runtime + StructuredOutput 结构化交接」，是对「确定性编排 + 结构化交接」这条路线的强验证，但它不是本项目的底座。

### 4.5 宿主执行桥 —— 决策：主代理无判断搬运桥

- **问题**：引擎要 spawn 子代理，但「spawn」这个动作依赖宿主能力——Codex/Claude/Cursor 的子代理由宿主启动（SKILL.md 也明确由 host 启动），Go 进程无法直接 spawn 宿主子代理。
- **决策**：主代理做**无判断搬运**：引擎输出 `SpawnRequest`（**薄指针**：actionID + taskKey + agentType + promptFile + promptHash + worktreeRef，不携带完整 ticket——worker 自己读已写盘的规范提示词 `PromptFile`，主上下文不再灌大段 ticket；**actionID 是 `drive` 在锁内生成的 opaque ID、不在 `Decide` 产出的 `Plan` 里**），主代理只「调宿主工具 spawn → 回填 `SpawnReceipt`（宿主侧 agent/session id）」，不读、不改、不决定 spawn 谁。决策权仍在引擎，主代理从「决定派发谁」降为「照引擎指令机械搬运」。**这是低判断兼容桥、不是零错误/零 token 通道**——只要 spawn 工具仍由顶层模型调用，就仍存在判断空间；真正封死需要宿主级 runner（headless adapter），**是否做、何时做按实测搬运成本决定，非本期必做**。
- **护栏（防 spawn 崩溃窗口 + 所有宿主动作的一次性交付）**：spawn 物理通道仍在主代理手里，引擎必须校验。**`pendingActions` 统一覆盖所有需要回执的宿主动作**——spawn（走 `Ready`）与 resume / terminate（走 `HostAction`），每个条目字段 `actionID / kind / taskKey / payloadHash / status / issuedAt / receiptDeadlineAt`：
  1. **先在一次锁内原子落整批 `pendingActions`（全部标 `QUEUED`）再调宿主**——否则「子代理已启动、receipt 未回填就崩」无从对账。**交付状态 `QUEUED → ISSUED → ACKED`（或 `UNKNOWN`）**：`drive` 每次把一个 actionID 从 `QUEUED` 标 `ISSUED`（记 `issuedAt`）并返回指令，**同一 actionID 只 `ISSUED` 一次**——两个 `drive` 并发重入、第二个看到已 `ISSUED` 就不再重复返回同一份活，杜绝双 worker；receipt 提交标 `ACKED`，receipt 丢失标 `UNKNOWN` 转人工（见第 3 条）。**这个 map 是程序内部闭环，主代理不接触**——它只看到渲染好的指令列表。**不跨宿主一概而论「哪个动作天然幂等」**：每种宿主动作在 adapter 里声明 `SAFE_RETRY / RECONCILE_BEFORE_RETRY / NEVER_AUTO_RETRY` 之一，**未明确证明幂等时默认 `RECONCILE_BEFORE_RETRY`**；只有对应 adapter 明确保证安全时才允许自动重试，`UNKNOWN` 绝不盲目重发。
  2. 回填的回执由 `submit` 按 actionID 消费对应 `pendingActions` 条目。**统一 `HostActionReceipt { actionID, kind, provider, targetIdentity, status, payloadDigest }`**——spawn / resume / terminate 都用它（不只 `SpawnReceipt`），绑 provider + 宿主侧 agent/session id。
  3. **receipt 丢失窗口**（pendingActions 已落、某 actionID 的 agent id 未回填）：机器**不猜、不自动重 spawn**（那个 agent 可能还在跑，重 spawn 就是双 agent）。恢复**先靠 lifecycle 对账自动补**——spawn 时用稳定 `actionID/taskName/correlationID`，receipt 丢失后先查 lifecycle start 观测（现有 `ResolveClaimIdentity` 已能在**唯一** pending start 时自动推导实际身份）：唯一匹配 → 自动补 receipt；已有 receipt 消元后唯一匹配 → 也自动补。**多个候选才进 Operator**，且 Operator 的合法选项**按宿主能力生成**（宿主支持按 id 定位就提供「恢复哪个 id」，不支持就只提供「重开 / 中止」），**不无条件承诺「无 id resume」**——「用户只确认它在跑、程序就知道恢复谁」在多数宿主并不成立。worker 返回结果仍走独立 validator，不信任主代理转述。
  4. **`ISSUED → UNKNOWN` 由 `issuedAt / receiptDeadlineAt` 触发，不新增 watchdog**：标 `ISSUED` 时记 `issuedAt` 并算 `receiptDeadlineAt`；`drive` / 事件重入时机械检查——过了 deadline 且 receipt 未回填，就按「receipt 丢失」路径走 lifecycle 对账（第 3 条），不是再挂一个定时器。与 §6 第二期第 5 条的失联检测共用同一套 deadline 字段与对账流程，不另起炉灶。
  5. **spawn 明确失败**（宿主返回错误，非静默无回执）：提交 `HOST_SPAWN_FAILED(actionID, reason)`——**只有宿主明确保证「agent 未创建」时**才可按策略重试；超时、连接中断、5xx 等「返回错误但无法确认是否已创建」的，走 receipt 丢失 / UNKNOWN 路径转 `NEEDS_OPERATOR`（否则可能生成双 agent），不等 deadline、也不盲目重派。
  6. **并行派发握手串行化（防多个未绑定 worker）**：**宿主没有可靠 correlation 时，每轮最多把一个 spawn 从 `QUEUED` 改成 `ISSUED` 并返回，收到 `ACK` 后才发下一个，其他任务保持 `QUEUED`；宿主明确支持可靠 correlation 时才允许批量 `ISSUED`**。否则主代理在「批量已 ISSUED、只实际启动一个」时崩溃，剩余任务会被误判成「可能已经启动」。已 `ACK` 的 worker 可继续并行运行，所以只串行化毫秒级启动握手、不损失实际并行度。若宿主不能向 `submit-result` 自动附调用者身份，还需给每个 dispatch 一个一次性 submission capability/token（状态只存摘要），否则「提交者身份由宿主限定」只是目标、不是可实现的协议。
- **人工决定桥（用户决定进流程，与 spawn 桥同构）**：必问点 = 迁移表里的人工事件节点（`Ask`）。引擎输出 `AskRequest`（问题 + 有限类型化选项 = 当前节点的合法出边，每个选项声明允许的 payload schema）。用户决定按宿主能力走三条路，LLM 一律只搬运、不替用户决定：
  1. **结构化问询**（宿主有 AskUserQuestion 类 tool，如 Claude Code）：主代理把 `AskRequest` 交给宿主问询，用户点选，返回结构化值，主代理原样 `submit`。一次决定、不二次确认。
  2. **代码态**（宿主无 ask——如 codex 的「ask」被转 deny——或用户想直接敲）：用户直接运行 `submit --event USER_*` 或编辑决策文件给类型化决定，LLM 完全不参与。
  3. **对话口述**（用户在平台里说话、不敲命令，codex 上的主要形态）：自然语言 → 类型化值必然经过 LLM 翻译，但翻译**不具决定权**——纯枚举无附言（「approve」「继续」「abort」）识别一次落地、不二次确认；带附言（「approve，但先把测试补完」）是 schema 外输入，不先走决定边、转 `CLARIFICATION_REQUIRED`；edit 负载（自由文本）走内容修订节点被天然确认；只有用户说得模糊、LLM 拿不准才回显确认一次（兜底、不是默认）。

  **纪律（对齐业界「审批疲劳」）**：确认只花在少数高影响必问点上，能一次就一次、不逢决定必确认；LLM 翻译只是提议、被 CLI 校验（节点匹配 + 选项合法 + 幂等）fail-closed 兜底，决定权始终在用户。「拉」取代「推」——流程走到必问点主动问、选项封闭（= 合法出边），用户不用预想发什么指令，完备性由迁移表保证、不由「预测用户想干什么」保证。

- **结果桥（worker 结果回流，与 spawn 桥对称）**：spawn 桥管「怎么把活发出去」，结果桥管「结果怎么收回来」。主代理不再读 worker 输出、判断语义、拼 `record-action`/`record-gate` 参数（这是当前主要 token 与错误来源之一）：
  1. 每种 action / gate 的产出是**严格 JSON schema**（结构由 action/gate 定义），worker 结果持久化为不可变记录（写进 `state.json`、已接纳禁止修改）。**运输通道选定「受限 receipt inbox / `submit-result`」**——worker 只能提交匹配自己 dispatch 的严格 JSON，提交者身份由宿主侧 agent 身份限定；`submit` 里由 Go 机械校验 dispatch、当前 Attempt、source bindings、schema、幂等性（见第 2 条）。**不选「宿主按 agent ID 获取 final output 再 pipe 给 submit」**——它在 Codex / Claude 间未必有统一能力，而且一旦输出先进入主代理上下文、token 环实际上还在。主代理不读、不转述、不摘要重写、不判语义（现有写阻断边界规定审查代理和开发后的主代理都不得直接改 run 状态——这正是不让主代理读输出再转述的理由）。**hook 只放行这一个封闭入口**，仍禁止 worker 直接修改 run 状态；**不新增权限系统或复杂身份协议**。
  2. `submit` 里由 Go 机械校验：schema 合不合法、snapshot / binding / attempt 对不对、是否当前权威 dispatch、是否重复提交（幂等）——这些是程序判的，不是 LLM 判的。
  3. **结果接纳的「不可变」是状态语义，不另建 receipt 文件**：worker 调 `submit-result` → Go 校验 schema / dispatch / Attempt / bindings / event ID → **在同一次 state 锁内写入规范化结果、event ID、digest**。`state.json` 本来就存完整结果，「不可变」由「已接纳结果禁止修改」保证，不需要额外的 receipt 文件、孤儿文件恢复、两文件提交顺序。**幂等/冲突三情形**：已接纳 → 同 ID 同内容幂等返回原响应、不同内容硬拒绝；未接纳且无记录 → 正常 submit 一次。**两个正常乱序场景**：worker result 先于 SpawnReceipt 到达 → 先挂起或利用 lifecycle 自动补 receipt，不能直接报非法；`ISSUED` 等待 SpawnReceipt 用 `issuedAt / receiptDeadlineAt`，与 worker 执行的 `startedAt / deadlineAt` 分开，不混用。只有 Seal/Abort 后状态会删除，才在 summary 留终态回执（见 §8）。
  4. **语义核验做选择性处理，不新增「给每个 PASS 再派 LLM validator」**：PASS、RUNTIME_ERROR、绑定和 schema 由 Go 机械校验后入账，不再多派一个 LLM；**P0/P1/P2 候选 finding 与 QA FAIL 均需结构化核验**（产生固定 `VERIFY_FINDINGS` / `MAIN_AGENT_DECISION` ticket，强制逐项返回需求前提、正常入口、复现步骤、证据、因果、严重度和 accept/dismiss，主代理只能填表、不能决定下一步），但**仅确认的 P0/P1 finding 与 QA FAIL 形成 FAIL/阻塞，P2 只作非阻塞建议**（对齐 reviewer-base：P0/P1 阻塞、P2 随 PASS 返回）。这既保留现有独立核验边界，又不把省下的 token 花在给每个 PASS 派 validator。
     - **`PASS + P2/P3` 的确定性去向**：通过结构与语义接纳后先形成权威 `PASS`，P2/P3 另存为不可静默丢弃的 `AdvisoryObligation`，不得自动改判 FAIL。若来源是 `product-review` / `start-readiness`，`Decide` 把全部 Advisory 合并成一个类型化 `AskRequest`，逐项只接受 `confirm`（纳入需求/开发范围）或 `dismiss`（作废），`settle-findings` 全部落账后才推进；确认 P2/P3 本身不触发 `NeedsReReview`，但随后需求修订若改变语义，仍按需求修订边重审。若来源是开发后 gate，Advisory 保持可见并进入 Seal 摘要，默认不阻塞、不自动修复；同轮存在 QA FAIL/P0/P1 时随修复包一并处理，只有建议时须用户明确要求才创建修复任务。
  5. 目标：「编排推理 token 接近零」，**不是**「所有语义判断 token 为零」。

## 5. 目标架构

```
用户 / 主代理（UI + 受理 + 呈现决定）
        │  typed human event / 状态查询
        ▼
┌─────────────────────────────────────┐
│  确定性引擎（Go，确定性内核）        │
│                                     │
│  迁移表（唯一流程权威）             │
│  state.json（原子替换，权威投影）   │
│  Observe + Decide → NextResult      │
│  入口：workflow drive / submit       │
│  controlMode 硬隔离 + revision CAS   │
└──────────────┬──────────────────────┘
               │ 不可变 ticket / receipt
               ▼
      子代理 worker（开发/审查/QA）
```

### 5.1 核心不变量

```
每次 `Decide` 都产出**一个** directive kind（Ready / HostAction / Ask / Wait / Operator 之一，或明确的 Complete），并返回该 kind 下的完整 eligible frontier = **EligibleSet**（本状态下所有合法可推进的项；EligibleSet/IssuedSet/QueuedSet 三集合的区分见 §5.2 容量协议）。
```

两条都要：① **完备性**——不存在「没有可派任务、没有等待原因、没有人工介入点、也没有结束」的无声死端；② **唯一性**——`Decide` 是状态到下一步的**函数**，同一状态必须产出同一组固定排序、内容唯一的 `Plan`（`IssuedSet` 再由 `SelectIssued` 按 capacity 切出），否则主代理又有了「挑哪个」的选择权、岔路没封死。注意：这里的「一个」指**每次 Decide 只有一个 directive kind**——人工节点仍可同时有多条合法事件边（approve/reject/edit），它们作为该 kind 下的 eligible frontier 一起返回，不冲突。**`single directive kind` 是 v1 的简化策略、不是确定性成立的必要条件**：确定性只要求「同一状态 → 同一输出」，不要求输出只有一个 kind；v1 用它封死主代理的选择权，未来若出现明显可并行、却被单一 kind 卡住的场景，可以升级为多 kind 的确定性结构、而不违背确定性。

### 5.2 Next 函数签名（Observe + Decide 两段，单一结果）

「下一步」不只取决于 `state.json`，还取决于需求文件、HEAD、prompt catalog、QA worktree、生命周期日志这些**外部事实**。所以拆成两段：`Observe` 只读环境，`Decide` 才是可重复测试的纯函数——「读事实」和「决定下一步」分开，`Decide` 不碰环境、只吃两个入参，同一入参永远产出同一 `Plan`；`SelectIssued` 再把完整决定按容量切成这轮实际发出的子集（见下方容量协议）。

```go
func Observe(root string, state RunState, now time.Time) Observation  // 只读外部事实（需求/HEAD/catalog/worktree/生命周期），不含容量
func Decide(state RunState, obs Observation) Plan                      // 纯函数：产出不含 actionID 的 PlannedAction 集合（完整 EligibleSet），字节级稳定、可重复测试
func SelectIssued(plan Plan, admission Admission) IssuedSet            // 纯选择函数：按 Admission 从 EligibleSet 切本轮子集；availableSlots==0 → 空，等待 WAITING_HOST_CAPACITY

type Admission struct {                                                // 宿主能力输入（不进 Observation、不影响 EligibleSet）
    AvailableSlots      int  // 剩余可用槽位，按「唯一活跃 agent identity」计数
    MaxUnattachedStarts int  // 无可靠 correlation 时为 1；宿主支持可靠 correlation 才 >1
}
// drive 在锁内为 IssuedSet 生成 opaque actionID、持久化 pendingActions，再返回可执行的 SpawnRequest
```

`Decide` 对同一 `state + obs` 产出**单一 `Kind`** 的 `Plan`——顶层只一个 `Kind`，不出现「派发 + 问用户 + 等待」并存、让主代理判断先处理哪个：

```go
type NextResult struct {
    Kind       NextKind            // Ready | HostAction | Ask | Wait | Operator | Complete，恒为单一值
    Ready      []SpawnRequest      // Kind==Ready：只表示 spawn（要派发的 worker，薄指针，见 §4.5）
    HostAction []HostActionRequest // Kind==HostAction：只表示 resume/terminate（Go 进程做不了、必须宿主会话完成的动作）
    Ask        []AskRequest        // Kind==Ask：要问用户的必问点（类型化确认形态 approve/reject/edit）
    Wait       []WaitReason        // Kind==Wait：阻塞当前推进的等待原因（含 WAITING_HOST_CAPACITY）
    Operator   []OperatorRequest   // Kind==Operator：需要人工介入的点
}
```

**能由 Go 直接做的动作绝不进 Ready/HostAction**：Go 里能跑的（写盘、状态推进、内部校验）由 `drive` 直接执行。**spawn 只走 `Ready`（SpawnRequest），`HostAction` 只收 `resume`（恢复宿主侧 agent/session）、`terminate`（终止宿主侧 agent/session）两类**——同一种动作绝不出现两个输出类型。其余凡能被 Go 直接操作文件系统 / VCS 完成的（建/注入 QA worktree、需求注入、Git/SVN/P4 操作）一律是 Go 的**确定性 handler**、由 `drive` 直接执行，不进 Ready 也不进 HostAction——否则又把「搬运 spawn」扩成「搬运一堆宿主动作」，主代理的判断面变大、与本稿「主代理只机械搬运」的定位矛盾。`Ready`/`HostAction` 是类型化的宿主动作、不是故障，也不是「问用户」。

**本地非幂等 handler 同样非原子，也要最小对账协议**：`pendingActions` 只护住宿主动作，Go handler 里的 VCS/文件操作（Seal squash、QA worktree 创建、物化结果文件）没有这种保护——它们同样「先改外部事实、再写 state」，中间崩溃会留下「HEAD 变了、state 还引用旧快照」的窗口（现有 Seal 就是：先 `squashGitRangeToBase` 改 HEAD、再 `rebindCurrentSnapshot`、落盘在更后）。故每个非幂等本地 handler 也实现 `persist intent → execute → observe/reconcile → commit result`，**不恢复通用 Effect 框架**：如 Seal 先落 `SealSquashIntent { oldHead, base, expectedTree, messageDigest }`，恢复时「HEAD 仍是 oldHead → 执行；HEAD 已满足预期树和父关系 → 认定已执行、继续入账；其他 → 明确 Operator，绝不再次 squash」。QA worktree 创建、物化结果文件同此。

**单一结果的纪律**：同一 `state + obs` 只产出一种 `Kind`；一个 `Ready` 批次可含多个 worker（并行），但「派发」和「问用户」绝不塞进同一轮——需要两者时引擎拆成两步，先整批派发、回执提交后下一步再问。各数组按 task ID 固定排序，`now` 只参与 deadline 判断、不进动作身份。**结构层硬校验**：`NextResult` 的 Go 结构仍允许 `Kind == Ready` 时 `Ask` 也非空这类非法组合——既然目标是没有犯错空间，实现时要么用真正的 tagged union，要么给 `NextResult.Validate()` 加硬校验：只有与 `Kind` 对应的字段允许非空、`Complete` 时所有 payload 为空；CLI 输出前、测试 fixture 加载后都必须验证。

**容量协议（三集合，区分「能推进的全部」与「这轮发几个」）**：`Decide` 只产完整 `EligibleSet`（本状态下所有合法可推进的项），`SelectIssued(plan, admission)` 才按 `Admission` 切出这轮实际发出的 `IssuedSet`——`QueuedSet = EligibleSet − IssuedSet`，其余保持 QUEUED、等下一轮 slot 空出再发。**admission 不进 Observation、也不影响完整 EligibleSet，也不让主代理现场填数**：`AvailableSlots` 由 `configured provider limit − 当前唯一活跃 agent identity 数` **机械计算**——同一 worker 的 `ACKED` 和 `RUNNING` 是同一个 identity、不重复计，resume/terminate 不占新 worker slot；`MaxUnattachedStarts` 无可靠 correlation 时为 1、支持可靠 correlation 才 >1。它只决定「这轮裁剪多少」，不是 `state.json` 的一部分、也不是 spawn 失败：引擎一次算出 5 个 worker、宿主只有 2 个槽位，`IssuedSet` 就切出 2 个、其余 3 个 QUEUED；**但无可靠 correlation 时每轮实际 `ISSUED` 只 1 个、其余继续 QUEUED（见 §4.5 第 6 条），有 correlation 才一次 `ISSUED` 这 2 个**——**容量不足绝不重算、不报错，只是「这轮发不完、下轮继续」**；`availableSlots == 0` 时 `drive` 产出 `WAITING_HOST_CAPACITY`（一个 Wait reason），**不能返回空 Ready**；宿主还有不可见占用时返回结构化 `CAPACITY_UNAVAILABLE`，这只影响吞吐、不改变正确性。`SelectIssued` 是纯选择、不持久化；真正把 `IssuedSet` 生成 actionID、标 `ISSUED`、写入状态，由 `drive` 在一次锁内完成，其余保持 `QUEUED`。三个集合由程序算出、主代理只看到 `IssuedSet` 里渲染好的指令，QueuedSet 留在引擎内部、不暴露给主代理。

**确定性**：同一 `state + obs` 下 `Plan` 必须**字节级稳定**（`Kind` 唯一、各数组固定排序、内容唯一、不含随机 actionID/时间戳——`Plan` 里的动作是 `PlannedAction`，没带 actionID），同一 `Plan + admission` 下 `IssuedSet` 必须稳定（由 `SelectIssued` 按固定顺序切出）。**「字节级稳定」验收只针对 canonical `Plan`，不针对含随机 ID/时间戳的已签发 `SpawnRequest`**。**这不是把选择权交还主代理**：程序一次算出这一批「该做什么」，主代理照单执行、不挑；排序和内容都是程序定的，岔路没有封死以外的空间。**`project(state)`、迁移表、pre 条件、parallel 组、`pendingActions`、`revision` CAS、actionID 消费、数组排序这些复杂度全部程序内部闭环**——主代理只收到渲染好的 `SpawnRequest` / `HostActionRequest` / `AskRequest` / `WaitReason`，不读迁移表、不判 pre、不碰任何内部字段，不把复杂度转移给 LLM。砍掉 `EffectSpec`/`EffectExecutor`/`ErrorRoute`——主代理不执行 effect（只搬运 spawn），错误处理见 §6 第二期第 3 条。

### 5.3 迁移表字段（一行 = 一条合法迁移）

**两层分离**：迁移表是**状态机**（run-level 阶段的合法转移）；动态子任务、修复轮次、并行依赖属于**任务清单**（TaskKey 集合），不由静态迁移表表达——修复/复审/超时是动态循环，静态 DAG 表达不了，两层分开、不混成一张图。**节点/阶段不是 state.json 里存的字段**：现有 `RunState` 没有 N0–N13 阶段标记，只有业务字段（Actions/Gates/Dispatches/PreRepairSnapshot/轮次计数等）。**单个 `project(state) → Node` 表达不了并发**：N7 开发和 N8 黑盒 QA 本就同时活跃、N11 又有多个并行门，塞进一个 Node 只会逼出几百行「节点×组合子状态」。故拆成三个确定性函数——`project(state) → RunPhase`（迁移表只管理少量 run-level 阶段：PRE_REVIEW / DEVELOPMENT_PARALLEL / SNAPSHOT_READY / POST_REVIEW / REPAIR / TERMINAL）、`expectedTasks(state, phase) → []TaskKey`、`taskStatus(state, TaskKey) → status`；动态 gate / QA mode / review wave 继续由 expected set 管，迁移表的 `from` 匹配的是 RunPhase 投影、不是某个不存在的节点字段。**task 自身也有独立的状态迁移（`TaskTransitionTable`）**：单个 Task 走 `QUEUED / ISSUED / RUNNING / VALIDATING / TERMINAL`，task 事件先推进 TaskStatus、再聚合 expected set、满足 join 才推进 RunPhase——否则实现时容易又把并发任务状态塞回单一 RunPhase。

**任务清单不是「通用持久化 DAG」，而是「可重算的 expected set」**（上一稿写「持久化任务图」是空头承诺——字段设计里没有它、又踢进开放项）：

```go
TaskKey = kind + target + mode + reviewWave   // 任务的身份证，稳定不变
```

- **expected set**（这个 run 该有哪些任务）= 从路线、gate catalog、QA mode、review wave **确定性派生**，算出来一份清单；**漏派检测** = 拿清单对「实际已派/已完成的 TaskKey」，差哪个补哪个——这是集合求差，不是图遍历。
- **复用现有 `PreparedDispatch`**（已有 `Target`/`TargetKind`/`Mode`/`ReviewWave`/`Attempt`/`PromptFile`）保存 Attempt、binding、结果，不新造结构。
- **`currentAttemptID` 不单独持久化，从 `PreparedDispatch.ID + Attempt` 推导**——每个 TaskKey 的「当前权威 attempt」= 该 TaskKey 下 Attempt 最大的那条 dispatch。它本就是 `ID + Attempt` 编码的事实，再存一份是重复真相；若确需显式引用，改名 `currentDispatchIDByTaskKey`（语义更准确），不复用 Attempt 的语义。**「当前 Attempt」切换点**：新 Attempt 的 pending spawn intent 在**同一事务中提交落盘时**才成为当前权威，只存在于临时计算、尚未落盘的 Attempt 不抢旧结果的权威性。
- **`actionID` 是持久化的 opaque ID，不靠 hash 重建，且只在 `drive` 锁内生成**：`Decide` 产出的 `PlannedAction` 不带 actionID（否则破坏「纯函数、字节级稳定」——随机 ID 不是 state+obs 的函数），`next --compact` 只展示计划、不产生可提交的 actionID；`drive` 在锁内为 `IssuedSet` 生成 opaque ID 存进 `pendingActions`，**同一次副作用重试复用同一 actionID、新动作生成新 ID**；配合 `attempt`（执行代次 fencing）与 `payloadDigest`（内容校验）就够，不需要 `hash(runID, taskKey, attempt, hostActionKind, operationSequence)` 的确定性重建——ID 已落盘存着，重建只是增加复杂度和碰撞面。当前「同一个任务重派时身份稳定」容易被理解成重派仍复用 actionID，这里明确：重派 = 新 Attempt = 新 actionID。
- **`pendingActions` 只存所有 host 动作的交付状态**（见 §4.5），不存任务图。

**并行度与分片各有其家，不在 TaskKey 里**：几路并行 = `TaskGroupSpec`/`expectedTasks` 的并行成员（现有 `parallelStageTable` 的 `active`+`tasks` 从 state 确定性算出，升级成指令）；分几片 = `Slicing.SplitCount/Slices/Parallel`（slicing 决策持久化进 master state）。**本期保持现有 master/child run 模型**：每个分片是独立 run，master 按 `sliceID → childRunID` 跟踪，TaskKey 只在单个 run 内唯一、不引入跨分片的 scope/sliceID 维度；真要改成单 run 多分片时再给 TaskKey 加 scopeKey/sliceID。这两处上一稿没串起来，本稿补上打通。

**trigger 分两类、全写在同一份表里**（对齐 LangGraph `interrupt` / Step Functions `waitForTaskToken` / Temporal `signal`）：同一 phase 的出边既有**自动事件**（到了就自动推进），也有**人工事件**（phase 暂停、等类型化决定后走对应边）。人工事件不是表外逻辑——它就是「这条边需要外部类型化输入才能走完」，与自动事件平级。**整张表（from/trigger/pre/next/output）是引擎内部闭环**，动态并行不在这张表里、归 `TaskGroupSpec`/`expectedTasks`：主代理唯一看到的是 `output` 渲染出的 `NextResult` 指令（SpawnRequest / HostActionRequest / AskRequest / WaitReason），pre 条件、任务并行成员、trigger 分类它一概不接触。

```
TransitionTable = {          // 只管 RunPhase → RunPhase，动态并行不在这张表里
  from     RunPhase          // 如 SNAPSHOT_READY
  trigger  Event             // 自动事件：领域事件（SPAWN_RECEIPT_SUBMITTED / WORKER_RESULT_SUBMITTED / SUBAGENT_STOP）
                             // 人工事件：类型化决定（USER_*：续跑 / 重开 / 中止 / 返修 / 推进）
  pre      [Precondition]    // 只查「对应 expected set 是否已满足」+ 证据要求（人工事件 = 类型化决定已落盘，有效性靠 request ID + 任务状态，不靠 revision）+ VCS 身份 + 轮次计数
  next     RunPhase | [Cond] // 固定目标 或 条件迁移（if 字段值匹配）
  output   OutputTemplate    // 下一步唯一指令（渲染为 SpawnRequest / HostActionRequest / AskRequest / WaitReason）
}

TaskGroupSpec / expectedTasks = {  // 动态任务、并行成员、join，由 expectedTasks(state, phase) 派生，不在 TransitionTable 里
  members  []TaskKey         // 该阶段应并行的任务
  join     allTerminal       // 全部终态才推进（现有 parallelStageTable 升级成指令）
}

TaskTransitionTable = {       // 单个 Task 的生命周期，与 RunTransitionTable 分开
  from     TaskStatus        // QUEUED / ISSUED / RUNNING / VALIDATING / TERMINAL
  trigger  Event             // SPAWN_RECEIPT_SUBMITTED / WORKER_RESULT_SUBMITTED / SUBAGENT_STOP ...
  next     TaskStatus        // task 事件先推进 TaskStatus
}
// task 事件 → 推进 TaskStatus → 聚合 expected set → 满足 join 才推进 RunPhase
```

**Task 生命周期事件示例（`TaskTransitionTable`——spawn 与 worker 运行是两个不同 TaskStatus，不是 RunPhase）**：

```
WAITING_HOST_SPAWN
  + SPAWN_RECEIPT_SUBMITTED    → RUNNING                 // 自动：宿主确认已启动，进入运行
  + HOST_SPAWN_FAILED          → RETRY / NEEDS_OPERATOR  // 自动：宿主明确保证未创建才可重试；无法确认是否创建走 UNKNOWN 转人工（防双 agent）
  + USER_CONFIRMED_RUNNING     → RESUME                  // 人工：续跑优先（receipt 丢失但 agent 其实起来了，宿主侧 resume 补 receipt）
  + USER_CONFIRMED_NOT_RUNNING → PREPARE_NEW_ATTEMPT     // 人工：重开（操作者确认没起来）
  + USER_CHOSE_ABORT           → ABORTED                 // 人工：中止

RUNNING / WAITING_WORKER
  + WORKER_RESULT_SUBMITTED    → VALIDATING          // 自动：worker 结果落盘，推进
  + USER_CHOSE_ABORT           → ABORTED             // 人工：中止（失联超时转 NEEDS_OPERATOR 后的人工决定，见 §6 第二期第 5 条）
```

砍掉 `confirm`（必问点/授权哨兵）与 `effect`（副作用声明）、`on_error`（错误路由）三列：`confirm` 的语义并入 trigger 的人工事件 + pre 的证据要求；状态推进是引擎执行 `NextResult` 的实现细节、不属表声明；错误处理见 §6 第二期第 3 条，不逐行配路由表。

## 6. 落地步骤（分期）

> 每期可独立验证、可回退。**可靠内核先于交权**：在把真实控制权交给自动 `drive` 之前，先备好字段/filelock/错误分类。原因：引擎自动推进后，自身崩溃若不能靠已持久化状态恢复，会比现状更糟——现状主代理在环路里，卡住尚能靠重读 SKILL.md 续上；确定性引擎一旦丢状态，没人能「靠自觉」补回。

**实施节奏总览（对齐审查者给出的最稳路径）**：阶段 0（冻结语义）→ 只读 Decide + fixture → shadow / advisory → 补齐 HostAction / receipt / 容量协议 → lightweight canary → Git 非分片 → whitebox → blackbox → SVN/P4 → split 最后。交权不是一步到位，而是沿这条复杂度递增的路线逐级接管，每一级都是上一级验证通过后才放行下一级；split 放最后，因为它最复杂、需要分片合流与 worktree 绑定，不是本期可靠性门槛（见 §2）。下面各期是这条路径的具体展开。

### 阶段0：冻结现有语义（先于一切改造）

- 补版本握手 + 行为测试：只冻结 `drive` 依赖的状态结果、合法顺序、关键外部行为（接收什么、产出什么、状态怎么变）作为重构基线——**不必把 27 个命令的偶然实现细节全部固化**，冻结的是「引擎要复用的那部分语义」，防止重构过程中语义漂移、旧 run 行为被悄悄改掉。**冻结对象明确含**：语义核验边界（主代理记录前的独立核查）、宿主身份语义（spawn/resume/terminate 的回执与身份绑定）、本地副作用恢复（Seal squash 等 VCS/文件操作的对账语义）、明确支持平台、成功指标（省 token / 可恢复性 / 失败率）。

### 第一期：只读 Observe/Decide + shadow 对比（零风险，立即可做）

- **一步到位建立静态迁移表**（`var transitionTable = []Transition{...}`），`Observe` / `Decide` 直接读这份表——不先写临时 `switch Next()` 再迁成表，避免两套逻辑、二次重构；**但第一期不动现有 `requireTransition` / 旧 guard**（保持零风险、只读），`Observe + Decide + workflow next --compact` 只算不写、不派任何副作用。旧 guard 和 `drive` 切到同一份权威表，是 parity 达标之后（第二、三期）的事，不在第一期。
- 新增只读命令 `formal-gates workflow next --compact`（紧凑输出下一步）。
- **shadow 模式**：主代理照旧编排，每次它调用命令时，`Next` 后台算「期望下一步」。对比口径是 **下一步集合 / 最终状态**（引擎期望的下一步、最终到达的状态），**不是**主代理执行任务的先后顺序——但「顺序差异」不能放宽成「一律不比较」：**只有同一声明并行组内部的顺序差异可忽略**（并行本无顺序），**有依赖关系的步骤顺序必须比较**（后一步不得先于其前置发生）。shadow 验证五条：实际事件是否属于当时的 eligible frontier、实际 fan-out 是否完整、实际事件是否违反依赖/阶段、提交后的投影是否与预期一致、并行组内部顺序不比较。**不靠长期统计「偏离率」来证明主代理是病根**——那已经有真实事故证据；shadow 的目的是 parity 达标：用历史 fixture、golden trace 和少量 canary，写死退出条件（「影子与权威结果一致」即退出）。**shadow 指标存独立 telemetry、不写回权威 run state**——否则就不再是严格只读。
- **拆两段**：① **被动 shadow**——只记录偏离率、不输出给主代理（此时不省 token，反而多算一点）；② **advisory Next**——把 `Next` 结果输出给主代理照做。token 收益从 advisory 开始，不是从 shadow 开始。
- **收益**：① 产出证明「主代理在环路里是病根」的硬数据；② advisory 起主代理从「读 SKILL.md 推理下一步」转向「读引擎指令」，从此开始省 token。

### 第二期：可靠控制内核（交权前，仍不自动推进）

> 第二期交权前，按项目**明确支持的平台和 CI 能力**安排 kill/crash 小实验验证 `filelock` 与 `state.json` 原子替换；这不是只读第一期的前置门槛，也不必等到三平台全绿才动手。

1. **字段补齐 + 结果接纳验证**：
   - `workflowDefinitionVersion` + `stateSchemaVersion`（两个小 int）：run 创建时钉死，新二进制要么声明兼容、要么拒绝恢复并要求显式迁移（见 §4.1）；两个字段分开——定义版本（迁移表逻辑）与状态 schema（字段结构）升级策略不同、不共用一值。
   - `controlMode = legacy | engine`：引擎/旧命令硬隔离，杜绝双权威。**存量 state 无 `controlMode` → 按 `legacy`、无 `workflowDefinitionVersion`/`stateSchemaVersion` → 按 legacy v0 / v0**；engine drive 不自动迁移旧 run（要么显式迁移、要么继续旧命令）。
   - 单调 `revision`：每次写入递增，只作 `state.json` 写入 CAS（并发重入互斥）；**不用于判定并行任务/人工决定新鲜度**，pendingActions 与人工决定记 `createdRevision` 仅作追踪。
   - `pendingActions`（map，key = actionID）：drive 返回 ReadySet 前在一次锁内写入整批，**统一覆盖所有需要回执的宿主动作**（spawn 走 Ready、resume/terminate 走 HostAction），每个条目字段 `actionID / kind / taskKey / payloadHash / status / issuedAt / receiptDeadlineAt`（见 §4.5），每个回执（统一 `HostActionReceipt`）只消费对应 actionID。
   - `currentAttemptID`：**不单独持久化，从 `PreparedDispatch.ID + Attempt` 推导**——每个 TaskKey 的当前权威 = 该 TaskKey 下 Attempt 最大的 dispatch；接纳结果只认它，已有新 Attempt 时旧 attempt 结果 `OBSOLETE_RESULT` 永久拒绝、不重新接纳（见本条第 3 条的分类；配现有 `PreparedDispatch.Attempt` 挡住同快照旧代次）。**切换点**：新 Attempt 的 pending spawn intent 在同一事务中提交落盘时才成为当前权威，临时计算未落盘的 Attempt 不抢旧结果权威。
   - **结果接纳验证靠 action/request ID + 当前任务状态 + dispatch ID/Attempt + source bindings，不靠单个 `Attempt` 也不靠 revision**：现有 `PreparedDispatch.Attempt` 只是次数、单独挡不住旧结果；接纳结果时验证 task 的 `dispatch ID + Attempt + 状态 + source bindings`（现有 `STALE` + source 绑定校验 workflow.go:1710 已含一部分），三者一起挡住「同快照、旧代次」的迟到结果，不新造代次机制。
   - **terminal receipt**：Seal/Abort 后把最终 request ID / 结果 digest / 回执写进 summary——临时状态删除后仍可幂等重试（见 §8）。
2. **继续用 `state.json`，不引事件日志/投影**：原子替换 + sha256 完整性 + 快照 + 派发 + Attempt + 结果。`revision` 写前校验、不匹配重算；整体替换没有「半条 append」问题，故无截断/修复负担。**控制面写入口只有 `drive` 和 `submit`**，两者用同一把 `filelock` 和同一 `revision` CAS；其他公开命令（`show`/`status`/`next`）纯只读、无写副作用，不产生额外并发入口。**事务边界必须覆盖外部事实漂移**：`revision + filelock` 只锁住 `state.json`，锁不住 Git 和文件系统——需求文件或 HEAD 可能在 Observe 后改变、而 `state.revision` 不变。故推进事务明确为：读 state → `Observe` 并产生 observation fingerprint/source bindings → `Decide` → 加锁重读 state → 校验 `revision` → **重新校验决定所依赖的外部 fingerprint** → 不一致则释放锁并重算 → 落盘动作、`revision+1`、原子保存。否则引擎可能依据已经过期的 HEAD 或需求摘要发出合法但错误的任务。
3. **结果与错误分类（不设「三类」人为数字约束，按需区分）**：上一稿把「旧 Attempt 永久 OBSOLETE」和「STALE 结果验证后接受」塞进同一套分类，是自相矛盾。拆成两层：

   **结果接纳层**（决定一个迟到/过期结果要不要推进状态）：
   - `RECOVERABLE_CURRENT_RESULT`：仍是当前 dispatch/Attempt，只是生命周期被标记停止（如中断）；bindings 未变时可验证接纳。
   - `OBSOLETE_RESULT`：已有新 Attempt，旧结果**永久拒绝**，绝不推进状态——与 `currentAttemptID`（每个 TaskKey 一份）配合判定。

   **中断恢复层**（`requireResumeInterrupted` 三分支，**只适用于代理中断恢复**，不扩张成全局错误系统）：
   - 客观瞬态 API 原因 + 一切未变 → 续用原 agent（现有 `isObjectiveInterruptionReason`）。
   - 条件变了 / 非客观原因已记录 → 放行新派发。
   - 一切未变但无客观原因 → 强制询问用户。

   全局仍需区分：invalid event（非法事件，硬拒）、retryable I/O（瞬态重试）、reconciliation required（需对账）、fatal corruption（致命损坏）；`Ask`/`Wait` 是**正常 directive**，不是错误。
4. **`internal/filelock` 独立通用原语**（替代「按时间无主删锁」）：极小包，只做「给文件加一把跨进程互斥锁」。对外一个接口 `filelock.WithLock(lockPath, func() error) error`——拿锁、执行、defer 释放，释放不可能被忘；平台差异关进两个 build-tag 文件（`lock_unix.go` 用 `flock`、`lock_windows.go` 用 `LockFileEx`）。锁的是独立 `*.lock` 文件，每次写 `state.json` 短暂持有、只护「读 revision → 校验 → 原子替换」这几毫秒。**为何需要锁**：控制面并发重入是正常使用——subagent stop hook 触发一次 drive、主代理收到 worker 完成又调一次 drive、两个并行 worker 几乎同时结束，都会让两个 drive 进程同时读 `revision=N` 再各写 `N+1`，丢失更新。进程崩溃由 OS 自动释放锁，`*.lock` 文件长期存在、不删，故无残留锁所有权、不需要 owner token / 超时 / 30 秒无主删锁那套。**为何不能只检测不加锁**：检测式来得太晚，`revision` 重复被察觉时某个进程可能已执行外部副作用（如 spawn 出 worker），事后 fail-closed 拦不住，反而把正常 run 送进 NEEDS_OPERATOR。开发并发（两个 worker 写同一需求代码）是异常，靠 worktree 隔离解决，不靠锁。
5. **失联检测（deadline 持久化 + 重入检查，非 OS 定时器）**：在 Task/Dispatch 上明确加 `startedAt` / `deadlineAt` 字段（不是「持久化进现有 Attempt」——Attempt 是整数装不下）；worker 派发时落 `startedAt` 并算 `deadlineAt`；`drive` 重入时机械检查超时，超过 deadline 只转 NEEDS_OPERATOR（**不自动重派**），先核对宿主生命周期（subagent 是否真停、receipt 是否漏记），操作者确认后才处置该 worker。**不装 OS 定时器（cron/launchd/Task Scheduler）**：`drive` 停在 WAITING 就退进程，watchdog 无处安身；OS 定时器改了状态却无法主动通知当前主代理，收益薄，却引入全局登记表 / 安装卸载 / 跨平台一整块维护面。`show`/`status` 只展示 `overdue=true` 与建议动作，不偷偷改状态。**故失联恢复只在下次 `drive`/事件重入时发生，无人唤醒时不会自动恢复**——这是明确的承诺边界，不假装有无人值守兜底。
6. **本地非幂等 handler 的对账 + fake host adapter 崩溃测试**：`pendingActions` 只护宿主动作，Go handler 的 VCS/文件副作用（Seal squash、QA worktree、物化结果）同样非原子，也要 `persist intent → execute → observe/reconcile → commit result`（见 §5.2 的 `SealSquashIntent` 例子）。用 **fake host adapter** 在这些边界注入崩溃点做确定性测试，而不是随机 chaos。

### 第三期：唯一 drive 入口 + 外部事件入口 + canary 交权

1. 公开入口收敛为三个，外部输入统一从 `submit` 进迁移表：
   - `workflow drive`——计算并执行内部迁移，机械推进到任一外部边界（`Ready` / `HostAction` / `Ask` / `Wait` / `Operator` / `Complete` 中第一个需要外部输入的），返回 `NextResult`。
   - `workflow submit --event <...>`（等价 `drive --event`）——提交外部事件：SpawnReceipt / worker 结果 / 用户类型化决定 / 生命周期事件。**这些外部输入不再各走各的命令，统一进迁移表 trigger**；**接纳事件后 `submit` 直接推进并返回新的 `NextResult`，主代理不额外再调一次 `drive`**。`submit` 统一幂等契约（防「提交成功但主代理没收到 CLI 响应就再提交」把正常流程打错）：同 event/action/request ID + 同内容重复提交 → 返回原结果、不重复推进；同 ID + 不同内容 → 硬拒绝；已消费的 SpawnReceipt 消费结果保留在对应 Dispatch 中，不因 `pendingActions` 条目删除变成「未知事件」；worker result 与人工决定遵守同样规则。
   - `show` / `status` / `next`——纯只读，无写副作用。
2. engine run 下**禁止主代理直接调用旧的推进命令**；`record-action` / `record-gate` / `claim-dispatch` 保留为**引擎内部 handler**（`drive` 执行迁移时调用），不再是绕过迁移表的公开编排入口。
3. `drive` 返回的 `NextResult`（ReadySet）由主代理无判断搬运（spawn 搬运见 §4.5）——主代理只查询/转达用户决定/起停监督/展示结果，**不照抄命令**。
4. 必问点 = 迁移表里的人工事件节点（§5.3）：需求、路线、修复授权、scope、abort、reset、adopt-external；**正常 Seal 自动完成、不问用户**，只有 skip/override/异常 Seal 才问。类型化确认（approve/reject/edit 落 `state.json`）；「没反对」≠「同意」。
5. canary 分两阶段：① 只读 shadow（引擎照旧算、只记录不写状态）＋ 隔离复制 run 对比；② 引擎作为**唯一权威**跑少量真实新 run——只限**非分片、单 run**，从**当前宿主 + Git** 这条最简单路径起步，验证权威模式的崩溃恢复；**首个真实 canary 只实现一个真实宿主 adapter（当前宿主），其余宿主（Codex/Claude/Cursor 中未选中的）等它跑通后再扩展，避免为多宿主兼容提前抽象**。**Git 是 canary 起步的 VCS、不是唯一支持的 VCS——SVN/P4 仍是后续扩展（见实施节奏总览「SVN/P4 → split 最后」），只是不放进首个 canary 证明**。**canary ② 至少跑通一次完整流程**：产品审 → start-readiness → 开发/黑盒并行 → snapshot → QA/门并行 → FAIL → repair → 重审 → Seal（lightweight 可先做 smoke，但它几乎不覆盖 spawn、结果桥和修复，**不能作为交权证明**）。**交权闸门**：确定性 kill/crash 测试 + deadline 重入检查 + 单权威 canary 全部通过，才切默认权威；否则留 shadow。**确定性 kill/crash 测试（逐个已知持久化边界、用 fake host adapter 注入崩溃点，非随机 chaos）至少覆盖**：intent 写入前后；spawn 后、attach 前；worker result 先于 spawn receipt；submit 成功但响应丢失；Git squash 后、state 保存前；临时文件同步和 replace 前后；两个并发 submit；旧 attempt 迟到。回退 = 停止/导出诊断/显式 authority-handoff，不旁路 controller。**闸门十项验收**（全部通过才算达标）：① 相同 state + observation 产出字节级稳定的 canonical `Plan`（不含 actionID/时间戳；不针对含随机 ID 的已签发结果）；② 非终态无空结果；③ capacity 裁剪不漏任务；④ 同 actionID 不重复 spawn；⑤ result-before-receipt 可恢复；⑥ 当前 Attempt 可恢复、旧 Attempt 永久不推进；⑦ 并发 submit 不丢更新；⑧ HostAction 各崩溃窗口可对账；⑨ terminal state 删除后最后事件仍可幂等重试；⑩ engine/legacy 双向旁路均被拒绝。

## 7. 省 token 机制（如何达成目标 2）

省 token 不是靠「少派代理」，而是靠**把主代理从环路抽出来**：

1. 主代理不再背 20+ 命令顺序 → 读引擎吐出的下一步；
2. 产出即 receipt，主上下文只收摘要+文件引用，不转述 worker 全文（顺带解决提示词漂移与上下文爆炸）；
3. SKILL.md 从「流程引擎规范」瘦身为「怎么和 Controller 交互」（现 284 行/23KB 里大量是流程规则）；
4. worker 只收 Task、不收整个流程；
5. （后续）每张语义 ticket 一个会话——机械步骤不启模型，上下文不随流程累积。

**度量（把「省 token」变成可测指标）**：分控制面 token 与语义 worker token、cache 命中/未命中/写、turns / dispatch / retry 次数、成功率 / 回退率 / 人工干预次数 / 单 run 延迟 / 成本。第一期 shadow 时先记录基线，后续各期对同一任务对比，用数据验证「省 token」而非口头宣称。

**成功标准（如实界定 token 收益）**：近期主代理仍执行 `SpawnRequest → SpawnReceipt` 宿主搬运，退出的是**编排决策环**、不是物理执行环。目标写成可测的：① 编排推理 token 接近零（主代理不再想「下一步是什么」）；② 每次宿主搬运只消费固定、短小的上下文；③ 漏搬运只能进 `WAITING_HOST_SPAWN`，不能造成非法状态；④ headless adapter 是否开发由实测搬运成本决定，不预设。

## 8. 验证与回退

- **回退**：第一期纯只读，随时可停，不改变任何现有 run 行为；第二期起旧命令保留兼容别名，**交权前或旧 run** 可退回手工模式；**`authority-handoff` 只作 canary 期间的临时逃生口、不长期承诺维护两套控制权**——它是迁移表里的一条**显式、原子、单向**迁移，锁内把 `controlMode` 从 `engine` 翻转到 `legacy`（`revision` 递增记账），翻转后旧 27 命令接管、`drive`/`submit` 拒绝操作。**翻转只能在静止检查点进行**——没有在途 task、没有 pendingAction、没有 engine-only 中间状态；否则先 drain（等当前 task 终态）或终止，不能带着进行中的 worker 硬翻，否则旧命令与引擎会对同一状态双写。这是 `controlMode` 的一次翻转、不是 `authorityGeneration`（代次计数），不需要租约。**硬分界（防双权威）**：`state.json` 带 `controlMode = legacy | engine`；旧 run 不原地自动迁移；legacy 命令拒绝操作 engine run、`workflow drive` 拒绝操作 legacy run。
- **验证**（后续期）：property 测试（非法转移不存在、Seal 安全、审批新鲜度、Task 不可变）。验证仍遵守 `prompts/reviewer-base.md` 的现有项目边界。
